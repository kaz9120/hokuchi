# 登壇資料を、理解される順に組み立てる

このスキルは、登壇資料を対話から描画まで一続きで作るためのものです。完成の姿は、lint を通した `talks/<YYYY-MM-slug>/deck.yaml` と、そこから描画した `out/` です。書き手は Claude で、話すのも決めるのも話者です。Claude が書くのは配置ではなく意図で、配置・色・サイズはテーマとレンダラが導出します (ADR-0001, ADR-0014)。

土台は Nancy Duarte『slide:ology』です。ページ番号はすべて同書のものです。進め方は ADR-0024 で決めています。

## 3 つの原則

1. 理解が先です。芯にするのは、聴衆に理解してほしいこと (中核メッセージ) です。締めは、話全体を総括するまとめにします。本は成功を「新たな見識を得た・行動を起こそうと思った・態度を改めようと思った」のどれかとしていて (p.269)、感動は疑問が解けて腑に落ちた瞬間に生まれると書いています (p.277)。行動は、理解した聴衆が自分で選ぶものです。画面で押しつけません
2. 完全版から削ります。持ち時間は最後の段で扱います。時間から先に枚数を決めると、削る元がないまま薄い中身を埋めることになります。本の Reduce も、全文から段階を踏んで削ります (p.241, p.243)
3. 文脈を持たない目で読みます。Claude も話者も、題材の文脈を持ちすぎています。「自分の頭では明快でも、他人には分かりにくい」(p.54) ので、話者に見せる前に、文脈を渡さない読み手に読ませて直します

## 着手前に開くファイル

SPEC は着手前に開きます。references は各 Phase の入口で開いてください。

- `tools/slides/SPEC.md` — スキーマの規範仕様です。要素・レイアウト・lint を定めています
- `references/audience.md` — 聴衆の描き方です。Phase 1 で開きます
- `references/message-map.md` — 章の順序と厚みの決め方です。Phase 3 で開きます
- `references/slide-design.md` — 1 枚の設計です。最初に読む 1 文、読む順、載せる量を扱います。Phase 4 で開き、以降も手元に置きます
- `references/element-guide.md` — 伝えたいことの形から要素を選ぶ判断ガイドです。Phase 4 で開きます
- `references/language.md` — スライドの言葉です。表記の約束と、避ける言い回しを扱います。Phase 4 と Phase 7 で開きます
- `references/audience-review.md` — 聴衆役のサブエージェントに渡す依頼文です。Phase 5 で開きます
- `references/reduce.md` — 削り方と粗密です。Phase 6 で開きます
- `references/style-defaults.md` — 話者固有の型です。Phase 3 以降で開きます

## 全体の流れ

Phase 0 から 8 まで順に進みます。Phase 2・3・5 は、話者の承認を取る関門です。ここを飛ばすと、合意していない前提の上に YAML を積むことになります。

| Phase | すること | 関門 |
|---|---|---|
| 0 | 前提を聞き、素材を読む | |
| 1 | 聴衆を 1〜2 人の具体的な人として描く | |
| 2 | 中核メッセージを 1 文にする | 承認 |
| 3 | メッセージマップで、章の順序と厚みを決める | 承認 |
| 4 | 時間を気にせず、完全版を書く | |
| 5 | 聴衆役に読ませて直し、話者に見せる | 承認 |
| 6 | 持ち時間に合わせて削る | |
| 7 | 言葉を仕上げ、描画して確かめる | |
| 8 | 話者のフィードバックで磨く | |

話者が構成そのものに触れるフィードバックを返したら、Phase 2〜3 に戻って合意し直してから書き換えてください。

## Phase 0 — 前提を聞き、素材を読む

次のことを聞きます。文脈や素材から分かるものは聞き直しません。

1. 発表の場と、イベントのテーマ。イベントページがあれば URL を聞きます
2. 持ち時間と締切
3. 登壇の立場。個人か、MOSH を代表するか。テーマの選択 (Phase 4) に使います
4. 資料を公開・配布するか。話者なしで読まれるなら、スライド単体で意味が通る文が要ります (p.258)。対面だけなら、スライドは話の背景に徹してかまいません (p.239)
5. 既存の素材。過去の登壇資料・記事・社内ドキュメント・画面・データ

素材は、聞くだけでなく Phase 1 の前に読んでください。話者がすでに言語化したことを読まずに設計すると、同じことを設計し直したうえで食い違います。

- イベントページは WebFetch で読みます。募集文にある課題の言葉は、スライドの言葉を選ぶときの基準になります
- 過去の登壇資料と記事を読みます。話者が繰り返し使う概念や、たどり着いている論がここに出ています
- 社内ドキュメントや議事録は、話者が指定したものを読みます。社内の用語は、ここにある正式な定義を使います
- スクリーンショットや図は Read で開き、何の画面かを自分の目で確かめます。取り違えたまま書くと、事実誤認が最後まで残ります

読んだものと、読んで分かったこと (話者の論・使っている言葉・まだ言語化されていないこと) を、短く話者に返します。

## Phase 1 — 聴衆を描く

`references/audience.md` を開きます。聴衆を集団の 1 行ではなく、名前のある 1〜2 人として描きます (p.35-36)。聴衆層が分かれるなら、層ごとに 1 人ずつ描きます。

核心の問いは次の 4 つです。「どんな人か」「何を得に来たか・なぜここにいるか」「何に悩んでいるか」「聞き終えて何が得られるか」。行動への誘いは、ここでは任意の問いです。7 問を尋問のように順番に聞かず、素材から埋まるものは埋め、埋まらない核心だけを対話で聞きます。

描いた聴衆から、この発表で扱うべき論点の候補を 3 つほど導きます (p.36)。結果を `deck.audience` に書きます。

## Phase 2 — 中核メッセージを 1 文にする (関門)

聴衆に理解してほしいことを、1 文で確定します。これが `deck.message` になり、以降のすべてのスライドの採否の基準になります。

- 話者の言葉で書きます。素材の中から面白い材料を拾って逆算しないでください。材料から組むと芯がぶれ、話が周辺の細部に流れます。話者がまだ言語化していないなら、候補を作る前に、話者が普段考えていることを聞きます
- 理解の形で書きます。「〜してほしい」という行動ではなく、「〜は〜である」「〜が〜を変える」という主張にします。行動への誘いを持たせたいときは、別の欄 (`audience.action`) に書きます
- 聴衆の「何を得に来たか」「何に悩んでいるか」に答えているかを確かめます
- 反論できる形になっているかを確かめます。誰も反対しない一般論は、芯として機能しません

1 文を話者に提示し、同意を取ってください。同意が取れるまで Phase 3 には進みません。

## Phase 3 — メッセージマップで章の順序と厚みを決める (関門)

`references/message-map.md` と `references/style-defaults.md` を開きます。章ごとに「この章で聴衆が理解すること」と「厚み」を 1 枚の表にします (p.39)。スライドの 1 行リストはまだ作りません。

表を作るときは、次の順序を基準にします。

- 聴衆がすでに持っている前提から始め、本題の前に要る前提・用語を先に置きます
- 課題を、取り組みより前に置きます。課題を共有しないまま取り組みを出すと、聴衆は取り組みの意味を読めません
- 最後にまとめの章を置き、話全体を総括して中核メッセージに戻ります (p.41, p.245)

厚みは章ごとに、相対的な配分で書きます (例:「本題 5 : 前提 2 : 周辺 1」)。本題の章をいちばん厚くし、本題でない章は薄く通過させます。本題にしない話題 (別の発表で扱った話、今回は触れない領域) は、薄い章として「扱わないこと」を明示します。

新しく出す用語と概念を数えてください。1 回の発表で聴衆が受け取れるのは 10 程度までです (p.254)。社内用語は、初出の章と定義を置く場所を表に書きます。

骨組みの案は、質の違うものを少なくとも 2 つ考えます。最初に浮かんだ案をそのまま採らないためです (p.47)。中核メッセージがいちばん伝わる案を 1 つ選び、選んだ理由と一緒に話者に提示して承認を取ってください。

## Phase 4 — 完全版を書く

`references/slide-design.md`、`references/element-guide.md`、`references/language.md` を開きます。持ち時間はいったん忘れて、1 時間の枠があるつもりで書きます。聴衆が理解するのに要るものを、すべてスライドにします。削るのは Phase 6 です。

### 手順

1. 表記の約束を先に決めます。statement と headline の文末 (体言止めか文か)、句点の有無、読点の扱いをデッキ全体で揃えます (p.171、`language.md`)
2. テーマを登壇の立場で選びます。個人は `tools/slides/themes/hokuchi.yaml`、MOSH としては `tools/slides/themes/mosh.yaml` です (ADR-0010)。相対パスで参照し、コピーはしません。この 2 つ以外のテーマは作りません
3. `deck` ブロックを書きます。`title`、`message` (Phase 2)、`audience` (Phase 1)、`theme` です。タイトルスライドの副題には、イベント名や日付を入れることを検討します
4. メッセージマップの章ごとに、スライドを書きます。各スライドは `id` (安定キー)・`role`・`idea`・`chapter`・`layout`・`elements`・`notes` を持ちます

### 1 枚ずつ決めること

1 枚ごとに、次の順で決めてください。詳しくは `slide-design.md` にあります。

- `idea` に、このページで聴衆に伝えることを 1 行で書きます。1 行で言えないなら、2 つのアイデアが混ざっています。分割してください。言えることが無いなら、そのスライドは作りません
- 聴衆が最初に読む 1 文を決め、主役のスロットに入れます。前提や問いを先に読ませたいときは、statement-stage の `headline` (上) に置き、主張を中央に大きく置きます。`support` は、主役を読んだあとに読む補足だけに使います (p.113-118)
- 要素は `element-guide.md` で選びます。形は関係を語るので、言いたい関係と要素の形を一致させます (p.124)
- 画面の文字は 3 秒で読める量にします (p.160)。入りきらないなら、文字を小さくするのではなく分割します (p.126, p.172)
- `notes` には、話者が話す内容を全文で書きます。話者が読んで、自分の言葉に直せる下書きにします

### SPEC で間違えやすい点

- 要素には `slot` か `id` のどちらか一方だけを持たせます (SPEC §6)
- chart には `message` が必須です。chart-stage の `headline` を省くと、`message` が見出しとして描かれます。系列を強調するときは `emphasis` に系列ラベルを書きます。`annotations` の `at` は、x 配列の値と完全に一致させます
- diagram の `emphasis` はノード id の配列で、statement の `emphasis` (強調語の配列) とは別物です。`edges` が参照するノード id は `nodes` に存在させます
- 色・書体・サイズは書きません。テーマから導出されます
- image には `src` か `prompt` の少なくとも一方を持たせます (ADR-0006)
- 段階表示は、`bullets.reveal: one-by-one`、`diagram.reveal: sequential`、スライドの `build` で書きます。静的な出力 (shot) では全部を表示した姿が描かれます

## Phase 5 — 聴衆役に読ませ、話者に見せる (関門)

`references/audience-review.md` を開きます。完全版を、会話の文脈を持たないサブエージェントに読ませます。渡すのは聴衆プロフィールと、デッキ (スライドの文字と notes) だけです。題材の背景・社内事情・この会話の経緯は渡しません。

聴衆役には、各スライドで何を言っているかを 1 行で答えてもらい、分からない語・唐突な転換・存在意義の分からないページを挙げてもらいます。返ってきた指摘を 1 件ずつ判断して直します。直さない指摘には理由を残します。

直したら、Phase 7 と同じ手順で lint・render・shot を回し、話者に見せます。人間の細かいレビューには `hokuchi serve` を提案します。聴衆役の指摘と、直した内容・直さなかった理由も一緒に渡してください。話者の承認を得たら Phase 6 に進みます。

## Phase 6 — 持ち時間に合わせて削る

`references/reduce.md` を開きます。ここで初めて持ち時間を扱います。削る順序と基準は次のとおりです。

- メッセージマップの厚みの配分に合わせて、章ごとの時間を決めます
- 削るのは、中核メッセージに効かないスライドと、話者が自分のために置いた覚え書き (notes に移す) です (p.240)。聴衆の理解に要る前提・定義・課題・まとめは残します (p.267)
- 本題でない章は、粗く通過させます。本題の章は、実物に留まって厚く見せます。粗密は、この段で当てます (ADR-0023 の考え方)
- notes の末尾に `【N秒】` を書き、`node .claude/skills/crafting-presentation/scripts/wave.mjs <deck.yaml>` で合計と並びを確かめます

削った結果、聴衆役の指摘が戻ってくる (前提が消えて唐突になる) なら、削りすぎです。

## Phase 7 — 言葉を仕上げ、描画して確かめる

`references/language.md` を開き、画面の言葉を点検します。そのうえで、画面の文字を proofreading-ja-with-gemini スキルで Gemini に添削させます。修正案は 1 件ずつ採否を判断し、意味や主張を変える案は採りません。

`hokuchi` コマンド (`tools/slides/cli.mjs` を npm link したもの) で確かめます。コマンドが見つからないときは、`tools/slides` で `npm link` を一度実行してください (nodenv 環境では続けて `nodenv rehash`)。

```sh
hokuchi lint <deck.yaml>
hokuchi render <deck.yaml>     # 出力は deck と同じ場所の out/ (-o で変更可)
hokuchi shot <outdir>
hokuchi serve <outdir>         # 人間レビュー用のアノテーション付きプレビュー (ADR-0011)
```

1. `lint` の error は、直すまで先へ進みません。warn は原則すべて解消します。info の `glance` (3 秒で読めない長さ)、`layers` (情報のレイヤーが多い)、`min-type` (字が小さい) は、1 枚の設計を見直す合図として扱います。残す指摘があれば、理由を添えて話者に報告します
2. `render` で単一ファイル SPA を描画し、`shot` でスクリーンショットを作ります
3. スクリーンショットを自分の目で確かめます。1 枚ずつに加えて、全体を並べて見ます。画像の様式がデッキの中で揃っているか (p.180, p.192)、同じ種類の要素で見出しの位置や言い回しが揃っているかを確かめます
4. 話者に見せます。`serve` ではユーザーが ← → でページを送り、`g` で一覧モードに切り替え、要素をクリックしてメモを付けます。Send を押すと `<outdir>/annotations.md` に追記されます

lint レポートは、捨てずに残す一級の成果物です (ADR-0002)。逸脱を黙って常態化させないでください。

## Phase 8 — 話者のフィードバックで磨く

ユーザーから「アノテーションを送った」と言われたら、`<outdir>/annotations.md` を読みます。反映はスライドの `id` 単位で行います。

- 変更するのは、指示された `id` のスライドだけです。他のスライドには触りません (ADR-0004)
- 人間が手編集した YAML は、再生成で上書きしません
- 同じ種類の指摘が 2 回来たら、デッキ全体に同じ問題がないかを探して、まとめて直します。話者に同じ指摘を 3 回させないでください
- 反映のたびに lint / render / shot を回し、意図どおりかを目で確かめます

## 発表後 — 凍結と振り返り

1. 最終レンダリングを `talks/<slug>/final/` にコミットして凍結します (ADR-0009)
2. 振り返りをします。完全版・削った版・最終版の差分と、話者の指摘を読み、修正を 3 つに分けます。「何を伝えるか (芯・構成・前提)」「言葉」「見せ方」です。話者の型として残すべき学びは、理由と一緒に `references/style-defaults.md` に追記します。スキーマやレンダラで表現できなかったものは、ツール側の課題として起票します
