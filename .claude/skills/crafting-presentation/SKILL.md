# 登壇資料を、理解される順に組み立てる

このスキルは、登壇資料を対話から実装まで一続きで作るためのものです。完成の姿は、話者と合意した `talks/<YYYY_MM_DD_タグ_演題>/storyboard.md` (絵コンテ) と、`check` を通したシーンの実装 (`talk.tsx` と `scenes/`) です。書き手は Claude で、話すのも決めるのも話者です。

発表は「1 枚ずつのスナップショットの連続」ではなく、「シーンが移り変わる映画」として作ります (p.212)。シーンの中の要素は役者として残り続け、クリックごとに移動・変形・強調されます。フレームワーク `packages/stage` が再生と部品を持ち、配置と図は Claude が毎回シーンのコードで作り込みます。公開は slides.y-kaz.com で行います。

土台は Nancy Duarte『slide:ology』です。ページ番号はすべて同書のものです。その上に、聞きに来たくなる・人に勧めたくなるための型 (`references/story.md`) を重ねます。

## 4 つの原則

1. 理解が先です。芯にするのは、聴衆に理解してほしいこと (中核メッセージ) です。締めは、話全体を総括するまとめにします。本は成功を「新たな見識を得た・行動を起こそうと思った・態度を改めようと思った」のどれかとしていて (p.269)、感動は疑問が解けて腑に落ちた瞬間に生まれると書いています (p.277)。行動は、理解した聴衆が自分で選ぶものです。画面で押しつけません
2. 完全版から削ります。持ち時間は最後の段で扱います。時間から先にシーンの数を決めると、削る元がないまま薄い中身を埋めることになります。本の Reduce も、全文から段階を踏んで削ります (p.241, p.243)
3. 文脈を持たない目で読みます。Claude も話者も、題材の文脈を持ちすぎています。「自分の頭では明快でも、他人には分かりにくい」(p.54) ので、話者に見せる前に、文脈を渡さない読み手に読ませて直します
4. 素材と判断は話者から受け取ります。共有される技術トークの強い部分は、どれも話者しか持っていない実物 (再現した対話、日付つきの事例、自分の失敗、選んだ理由) でした。AI っぽさは、判断と素材を AI に任せたときに出ます。話者が初版を「内容が薄い」「つまらない」と返したときは、Claude が素材の外から場面や結論を作っていました。実物と、話者がそれを選んだ理由が手元に無いシーンは、画面の言葉を書く前に話者に聞きます

## 着手前に開くファイル

references は、各 Phase の入口で開いてください。

- `references/story.md` — 面白さと残り方の型です。反論と賭け金、実物、一般化の章、予告と回収、比喩 1 本、覚えて帰る瞬間を扱います。Phase 2・3・5 で開きます
- `references/audience.md` — 聴衆の描き方です。Phase 1 で開きます
- `references/message-map.md` — 章の順序と厚みの決め方です。Phase 3 で開きます
- `references/storyboard.md` — 絵コンテの形式と書き方です。Phase 4 で開きます
- `references/slide-design.md` — 1 シーンの設計です。最初に読む 1 文、読む順、載せる量を扱います。Phase 4 で開き、以降も手元に置きます
- `references/element-guide.md` — 伝えたいことの形から、見せ方と動きを選ぶ判断ガイドです。Phase 4 と Phase 7 で開きます
- `references/language.md` — 画面の言葉です。表記の約束と、避ける言い回しを扱います。Phase 4 と Phase 7 で開きます
- `../writing-note/references/voice.md` — 話者の声です。「使わない言葉」と「話し言葉を、中身で書き直す」を「話すこと」にも当てます。Phase 4 で開きます
- `../writing-note/references/ai-tells.md` — AI っぽさの型です。話者の実際の直しから集めています。画面の言葉と「話すこと」に当てる行は、ファイルの冒頭に書いてあります。Phase 4 の終わりと Phase 5 で使います
- `references/audience-review.md` — 聴衆役のサブエージェントに渡す依頼文と、合成音声で通しを見る手順です。Phase 5 で開きます
- `references/reduce.md` — 削り方と粗密です。Phase 6 で開きます
- `references/build-scenes.md` — シーンの実装と、確かめるループです。Phase 7 で開きます。あわせて `packages/stage/README.md` を開きます
- `references/style-defaults.md` — 話者固有の型です。Phase 3 以降で開きます

## 全体の流れ

Phase 0 から 8 まで順に進みます。Phase 2・3・5・6 は、話者の承認を取る関門です。ここを飛ばすと、合意していない前提の上にシーンを作り込むことになります。シーンの実装は手間がかかるので、構成と言葉は Phase 6 の削った版まで絵コンテの上で固めます。

| 5 | 聴衆役に読ませて直し、話者に見せる | storyboard.md | 承認 |

## Phase 0 — 前提を聞き、素材を読む

次のことを聞きます。文脈や素材から分かるものは聞き直しません。

1. 発表の場と、イベントのテーマ。イベントページがあれば URL を聞きます
2. 持ち時間と締切
3. 登壇の立場。個人か、MOSH を代表するか。テーマの選択に使います
4. 公開するか。公開するトークは slides.y-kaz.com に載ります。閲覧者は話者なしで資料を読み、話したことはテキストの書き出しで読みます (p.258)。社内向けの発表は公開せず、このリポジトリ (GitHub で公開) の外に置きます
5. 既存の素材。過去の登壇資料・記事・社内ドキュメント・画面・データ

素材は、聞くだけでなく Phase 1 の前に読んでください。話者がすでに言語化したことを読まずに設計すると、同じことを設計し直したうえで食い違います。

- イベントページは WebFetch で読みます。募集文にある課題の言葉は、画面の言葉を選ぶときの基準になります
- 過去の登壇資料と記事を読みます。話者が繰り返し使う概念や、たどり着いている論がここに出ています
- 社内ドキュメントや議事録は、話者が指定したものを読みます。社内の用語は、ここにある正式な定義を使います
- スクリーンショットや図は Read で開き、何の画面かを自分の目で確かめます。取り違えたまま書くと、事実誤認が最後まで残ります

読んだものと、読んで分かったこと (話者の論・使っている言葉・まだ言語化されていないこと) を、短く話者に返します。

そのうえで、話者にしか出せない実物を集めます。画面・ログ・数字・写真・失敗・反対されそうな意見と、それを選んだ理由です (`story.md` の 3)。素材に出来事が並んでいても、出来事の間の「なぜ」は無いことが多いので、ここで聞きます。問いは 3 つまでにし、話者が音声入力で答えやすい形にします。話者の答えは、言い回しも含めて「話すこと」の原料として扱います。

## Phase 1 — 聴衆を描く

`references/audience.md` を開きます。聴衆を集団の 1 行ではなく、名前のある 1〜2 人として描きます (p.35-36)。聴衆層が分かれるなら、層ごとに 1 人ずつ描きます。

核心の問いは次の 4 つです。「どんな人か」「何を得に来たか・なぜここにいるか」「何に悩んでいるか」「聞き終えて何が得られるか」。行動への誘いは、ここでは任意の問いです。7 問を尋問のように順番に聞かず、素材から埋まるものは埋め、埋まらない核心だけを対話で聞きます。

描くのは、主催者や選考委員ではなく、そのセッションを自分から聞きに来たいと思う人です。その人が聞き終えて翌日やることを 1 つ書けるかを確かめます (`story.md` の 2)。聞きに来る人と、聞いたあとの行動を具体に決め直すと、同じ題材でも「つまらない」から「面白そう」に変わります。

描いた聴衆から、この発表で扱うべき論点の候補を 3 つほど導きます (p.36)。結果は、Phase 4 で絵コンテの冒頭に書きます。

## Phase 2 — 中核メッセージを 1 文にする (関門)

聴衆に理解してほしいことを、1 文で確定します。これが絵コンテの `中核メッセージ:` になり、以降のすべてのシーンの採否の基準になります。

- 話者の言葉で書きます。素材の中から面白い材料を拾って逆算しないでください。材料から組むと芯がぶれ、話が周辺の細部に流れます。話者がまだ言語化していないなら、候補を作る前に、話者が普段考えていることを聞きます
- 理解の形で書きます。「〜してほしい」という行動ではなく、「〜は〜である」「〜が〜を変える」という主張にします。行動への誘いを持たせたいときは、別の欄 (`行動:`) に書きます
- 聴衆の「何を得に来たか」「何に悩んでいるか」に答えているかを確かめます
- 反論できる形になっているかを確かめます。誰も反対しない一般論は、芯として機能しません。「〜ではない」と言う人を 1 人思い浮かべられるかで見ます
- 賭け金を書きます。聴衆がこれを受け入れると何が変わり、受け入れないと何を失うかです (`story.md` の 1)
- 中核メッセージの中の抽象語 (「やり方が変わった」「磨いた」) を 1 つずつ指し、それぞれの中身を素材から 1 つ言えるかを確かめます。言えない抽象語は、絵コンテを書く前に話者に聞きます。芯の中身が空のまま書くと、構成がどれだけ整っていても、聴衆は「で、何が変わったの」と思ったまま帰ります

1 文を話者に提示し、同意を取ってください。同意が取れるまで Phase 3 には進みません。

## Phase 3 — メッセージマップで章の順序と厚みを決める (関門)

`references/message-map.md` と `references/style-defaults.md` を開きます。章ごとに「この章で聴衆が理解すること」と「厚み」を 1 枚の表にします (p.39)。シーンの一覧はまだ作りません。

表を作るときは、次の順序を基準にします。

- 聴衆がすでに持っている前提から始め、本題の前に要る前提・用語を先に置きます
- 課題を、取り組みより前に置きます。課題を共有しないまま取り組みを出すと、聴衆は取り組みの意味を読めません
- 事例の章のあとに、事例を聴衆の仕事へ一般化する章を置きます。事例の中で終わると「小さい話」になります。厚みは、その章に置ける実物の量で決めます (`story.md` の 4)
- 中核メッセージは、持ち時間の 3 分の 1 までに一度言います。冒頭に問いを置く型でも、答えを最後まで伏せません (`story.md` の 5)
- 序盤で見せる地図 (全体の図や、後で開く出来事の印) と、それを回収する場所を決めます (`story.md` の 5)
- 最後にまとめの章を置き、話全体を総括して中核メッセージに戻ります (p.41, p.245)

厚みは章ごとに、相対的な配分で書きます (例:「本題 5 : 前提 2 : 周辺 1」)。本題の章をいちばん厚くし、本題でない章は薄く通過させます。本題にしない話題は、薄い章として「扱わないこと」を明示します。

新しく出す用語と概念を数えてください。1 回の発表で聴衆が受け取れるのは 10 程度までです (p.254)。社内用語は、初出の章と定義を置く場所を表に書きます。

骨組みの案は、次の順で作ります。素材を見ながら章を立てると、話者が話した順や元の記事の順に引きずられます。

1. 素材の事実と発言を、話した順を崩して 3 つに分けます。①結論 (中核メッセージを支えるいちばん強い数字・到達点)、②転換点 (いちばん動いた場面、答えが出た瞬間)、③前提と経緯 (聴衆が知らないと聞けない最小限)
2. 質の違う骨組みを少なくとも 2 つ考えます。最初に浮かんだ案をそのまま採らないためです (p.47)。③から始めて時系列に並べる案は、比べる相手として以外は作りません
3. 話者の言葉の中から、全体を貫く物差しを 1 つ探します (比べ方を表す話者の言葉)。見つかったら、その物差しで前と後を同じ形で 2 回説明する章を作り、1 枚の図にします。聴衆が自分の仕事に当てはめて持ち帰れるのは、この物差しです。物差しは話者の言葉から取り、Claude が新しく作りません。話者が取り消した理由は、物差しに使いません
4. 演題と冒頭と本編の役割を決めます。演題を問いや逆説 (「〜が思い出せない」) にするなら、本編がその問いに答え、矛盾しない (本編で普通に思い出して理由を並べない) ようにします
5. 承認を取る前に、文脈を持たない新しいサブエージェントに、演題・メッセージマップ・素材だけを渡して確かめさせます。章の並びが素材の話した順をなぞっていないか、中核メッセージを持ち時間の 3 分の 1 までに言える並びか、演題と本編が食い違わないか、の 3 つです

中核メッセージがいちばん伝わる案を 1 つ選び、選んだ理由と一緒に話者に提示して承認を取ってください。

## Phase 4 — 完全版の絵コンテを書く

`references/storyboard.md`、`references/slide-design.md`、`references/element-guide.md`、`references/language.md` を開きます。持ち時間はいったん忘れて、聴衆が理解するのに要るものを、すべてシーンにします。完全版の大きさの目安は、5 分の LT なら 10〜15 分、10〜20 分のトークなら 1 時間です (Dev's Garden の 10 分は、1 時間のつもりの完全版から削って良くなりました)。削るのは Phase 6 です。

### 手順

1. `talks/<YYYY_MM_DD_タグ_演題>/storyboard.md` を作り (命名は過去資料と同じ。タグはイベントやコミュニティの名前)、冒頭に演題・中核メッセージ・聴衆 (Phase 1)・持ち時間・場・公開・テーマ・表記を書きます
2. 表記の約束を先に決めて `表記:` に書きます。見出しと大きな文の文末 (体言止めか文か)、句点の有無、読点の扱いをトーク全体で揃えます (p.171、`language.md`)
3. テーマを登壇の立場で選びます。個人は `hokuchi`、MOSH としては `mosh` です。この 2 つ以外のテーマは作りません
4. メッセージマップの章を `## ` で並べ、章ごとにシーンを書きます

### 1 シーンずつ決めること

詳しくは `slide-design.md` と `storyboard.md` にあります。

- `伝えること:` に、このシーンで聴衆に伝えることを 1 行で書きます。1 行で言えないなら、2 つのアイデアが混ざっています。分割してください。言えることが無いなら、そのシーンは作りません
- `前から受けるもの:` に、直前のシーンから何を受けて始まるかを書きます
- `見せ方:` に、画面の主役と、それがどう変わっていくかを書きます。見せ方と動きは `element-guide.md` で選びます。形と動きは関係を語るので、言いたい関係と一致させます (p.124, p.208)
- 状態を、話す順に 1 つずつ書きます。状態ごとに、聴衆が最初に読む 1 文を決めます。まだ話していない要素は出しません (p.203)
- 動きを付ける状態には、動きの役割を〔 〕で書きます。5 役割のどれにも当たらない動きは付けません (p.205)
- 本題の章の各シーンに、固有名詞・数字・実物のどれかを 1 つ以上置きます。無ければ話者に聞きます
- 聴衆が 1 週間後に覚えているシーンを 1 つ指名し、`見せ方:` に「覚えて帰る瞬間」と書きます (`story.md` の 7)
- 各状態の文字は 3 秒で読める量にします (p.160)。入りきらないなら、文字を小さくするのではなく状態を分けます (p.126, p.172)
- `> ` の行に、話者が話す内容を全文で書きます。原料は Phase 0 で集めた話者の言葉です。話者の口調は残し、耳で 1 回聞いて分かる文 (1 文に 1 つの内容) に整えます (`language.md` の 7)。Claude が足すのはつなぎと前提の説明だけにします。話者が言っていない場面・数字・感情・因果は書きません

話すことを書く前に、記事と同じく、素材の箇所 (何番目の発言か) と対応づけた抜き出しの作業メモを作ります (トークのフォルダの `extract.md`)。素材に無い中身が要るシーンには、絵コンテの冒頭に `<!-- 聞く: 〜 -->` を優先順に書きます。聞くのは素材と話者の答えに無い事実だけで、構成やシーンの取捨の相談は聞くことにせず、直した版を出して `check.md` の「話者に見せる変更」に書きます。素材の外で見つけた事実と、誤変換らしい語の扱いは、`../writing-note/SKILL.md` の Phase 4 と同じです。聞くことは 5 つまでにし、先頭には中核メッセージの抽象語の中身か、本題の実物を聞く問いを置きます。答えを入れる枠として時間を空けるなら、そのシーンの `粗密:` に「いまの話す字数での秒数」と「答えの枠の秒数」を分けて書きます。

書き終えたら、`../writing-note/references/ai-tells.md` と `../writing-note/references/voice.md` の「使わない言葉」を、画面の言葉と話すことの両方に当てます。

## Phase 5 — 聴衆役に読ませ、話者に見せる (関門)

`references/audience-review.md` を開きます。完全版の絵コンテを、会話の文脈を持たないサブエージェントに読ませます。渡すのは聴衆プロフィールと、状態ごとの画面と話すことだけです。題材の背景・社内事情・この会話の経緯は渡しません。

聴衆役には、各シーンで何を言っているかを 1 行で答えてもらい、分からない語・唐突な転換・存在意義の分からない場面を挙げてもらいます。あわせて、どのシーンを覚えて帰ったか、人に勧めるならどう紹介するかも聞きます。返ってきた指摘を 1 件ずつ判断して直します。直さない指摘には理由を残します。

実装の下書きのシーンがあるときは、合成音声で通しを見ます (`references/audience-review.md` の「合成音声で通しを見る」)。2026-10 KomeKaigi では、絵コンテを動画にして通しで見たことで「今なんの話をしているのか分からなくなる」「実装の話が細かすぎる」が見つかり、Gemini に動画を見せた講評で伏線の回収漏れが見つかりました。話者は、この進め方を続けたいと言っています。

聴衆役の読みは、studio の絵コンテの画面の「聴衆役の読み」からも頼めます。読み手は話者が `personas/` のプリセットから選び、`<トークのフォルダ>/readers.yaml` に入ります。話者が頼むと、アンケート 8 項目とコマへの感想が `reads/<番号>.yaml` に入り、コマへの感想は `feedback.yaml` のスレッドにもなります。読み終わると、studio が感想の判断を頼んできます。

指摘と判断は、会話の中の要約で済ませず、`feedback.yaml` のスレッドに残します。形と扱い方は `references/audience-review.md` にあります。

素材と照らす検査は、ここでは通しません。完全版は Phase 6 で大きく削るので、削った版に 1 回だけ通します。

直したら、絵コンテを話者に見せます。studio (`apps/studio`) の中で動いているときは、絵コンテの画面に、シーンごとのコマ (縮小画像と話すこと) と流れ (時間) が出ます。話者はコマの話すことをその場で直すか、コマを指して話します。指した場所は「指している場所:「シーン名」のコマ 2」の形で届きます。実装の前でも、絵コンテから画面を作る下書きのシーンで `talk.tsx` を置けば、縮小画像が撮れます。トークのフォルダは、話者が構成を確定したときに studio が作り、場所は作品の文脈にあります。返事には、聴衆役の指摘と、直した内容・直さなかった理由を書きます。話者が「この絵コンテで作る」を押したら承認です。ターミナルで進めるときは、Markdown をそのまま見せます。

## Phase 6 — 持ち時間に合わせて、絵コンテの上で削る (関門)

`references/reduce.md` と `references/story.md` を開きます。ここで持ち時間を当てます。実装の前に削るので、作らずに済むシーンが出ます。`story.md` の時間に関わる規則 (中核メッセージは持ち時間の 3 分の 1 までに、一般化の章の厚み) は、この段で確かめます。削る順序と基準は次のとおりです。

- メッセージマップの厚みの配分に合わせて、章ごとの時間を決めます
- 削るのは、中核メッセージに効かないシーンと、話者が自分のために置いた覚え書き (話すことに移す) です (p.240)。聴衆の理解に要る前提・定義・課題・まとめは残します (p.267)
- 本題でない章は、粗く通過させます。本題の章は、実物に留まって厚く見せます。粗密は、この段で当てます
- 各シーンの `粗密:` に時間を書き、`node .claude/skills/crafting-presentation/scripts/wave.mjs talks/<slug>/storyboard.md` で合計と並びを確かめます。中核メッセージを最初に言うシーンには `中核: <状態の番号>` を書きます。wave.mjs が、そこまでの時間が持ち時間の 3 分の 1 を超えていないかを見ます
- 一般化の章が、話者の過去形の報告 (「私の開発のやり方が変わった」) で終わらず、聴衆が自分の仕事に当てはめられる基準になっているかを確かめます
- 中核メッセージに効かない周辺の章は、原則として丸ごと削ります。残すなら、残す理由を絵コンテに書きます

`wave.mjs` の出力 (合計、話す字数からの見積もり、中核メッセージの位置) は、`check.md` に書き写します。`wave.mjs` の受けと割合の警告は、読み直す場所の印です。数を合わせるために、体感を言い切りにしたり、実物のあるシーンを削ったりはしません。

削り終えたら、削った版に次の 2 つの検査を 1 回ずつ、この順に通します。素材照合で直してから聴衆役に読ませます (並べて起動すると、聴衆役が直す前の版を読みます)。

1. 素材と照らす検査。文脈を持たない新しいサブエージェントに、`../writing-note/references/ai-tells.md`・`../writing-note/references/voice.md`・絵コンテ・素材 (話者の言葉)・`extract.md` (先頭に中核メッセージ) を渡します。合意した中核メッセージと演題は出どころに数えるよう伝えます。頼むのは `../writing-note/SKILL.md` の Phase 6「素材と照らして検査する」の 1〜7 と同じで、「見出し」を「画面の言葉」と読み替え、話した順のなぞりも挙げてもらいます。です・ます の割合と読点の規則は記事の規範なので当てません。削った版に当てるので、3 の「落ちた言葉と具体」は、中核メッセージと本題のシーンに要るものだけを戻します (削ったシーンの言葉は戻しません)。話すことは口で言う言葉なので、話者の口癖は 1 シーンに 1 つまでなら残してかまいません
2. 聴衆役の読み (`references/audience-review.md` の依頼文)

指摘は 1 件ずつ判断して直します。直すときに守るのは「素材に無い中身を足さない」だけです。直したあとは `wave.mjs` をもう一度回し、直した文の出どころを自分で `extract.md` と照らします。シーンを並べ替えたときだけ、2 つの検査をもう 1 回ずつ通します。削った結果、聴衆役の指摘が戻ってくる (前提が消えて唐突になる) なら、削りすぎです。

Phase 6 は、次の 4 つがそろったら通りです。どれが通ったかと検査の記録は、トークのフォルダの `check.md` に書きます (絵コンテには書きません)。

1. `wave.mjs` の持ち時間と中核メッセージの位置の警告が無い。ほかの警告は直したか、直さない理由を記録した
2. 素材照合の検査と聴衆役の指摘を 1 件ずつ判断し、直したか、直さない理由を記録した。素材に出どころの無い文が残っていない
3. まとめの最後の文が、周辺の章の感想ではなく、中核メッセージで閉じている
4. `<!-- 聞く -->` が残っていない。残っているなら、1〜3 がそろった時点で「聞くことの答え待ち」として話者に渡し、Phase 7 (実装) に進まない。「直さず話者に渡す」のは、話者にしか決められないことだけです

削った版を話者に見せ、承認を取ってから実装に入ります。Phase 5 の承認は完全版に対して取ったものです。

## Phase 7 — シーンを実装し、確かめる

`references/build-scenes.md` と `packages/stage/README.md` を開きます。そのうえで、画面の言葉を `references/language.md` で点検し、consulting-gemini スキルで Gemini に添削させます (studio の中では agy を呼べないので飛ばし、返事にそう書きます)。修正案は 1 件ずつ採否を判断し、意味や主張を変える案は採りません。直した言葉は絵コンテにも反映します。

1. `talk.tsx` と、絵コンテのシーンごとに `scenes/<id>.tsx` を作ります。シーンの `id` と状態の数は、絵コンテと一致させます。ノートと名前は絵コンテから流し込まれるので、シーンには書きません
2. 座標と大きさの型 (`build-scenes.md` の 2) を守り、部品 (`Headline`・`Reveal`・`Morph`・`Connect`・`CountUp`) で状態遷移を書きます。部品で足りないところは素の React・SVG・Motion で書きます
3. 型検査と `check --motion` を回し、`out/check.md`・`out/states/`・`out/motion/` を自分の目で確かめます。検査の指摘と絵コンテとの食い違いは、すべて直します
4. 静止画は 1 状態ずつと、全体を並べた形の両方で見ます。見出しや本文の左端がシーンをまたいで揃っているか、写真の様式がトーク全体で揃っているか (p.180, p.192) を確かめます。コマ撮りでは、動きが〔役割〕どおりの意味を語っているか、「付けてはいけない動き」に当たらないかを見ます
5. 話者に見せます。studio は常駐しているので、立てる必要はありません。コマの縮小画像は、ファイルを直すたびに撮り直されます。通しで見るときは、studio の「通しで見る」か作業用サーバ (`bun run dev <名前の先頭>`) を使います。公開した姿 (トップページからの導線・URL) で見るときは、サイト全体の開発サーバ (`http://localhost:5280/`) を使います。studio が中で立てています。studio を使わないときは `bun run dev` で立てます。← → で送り、`n` でノート、`o` で一覧、`p` で発表者ビューです。公開用の画面は `?public` を付けると確かめられます。サイトに載せずにファイルで共有するときは、`bun run single <トーク>` で 1 つの HTML と PDF に書き出します

## Phase 8 — 話者のフィードバックで磨く

反映は、シーンの `id` と状態の番号の単位で行います。studio の中では、話者の指摘はコマを指した会話で届きます。聴衆役の感想は `feedback.yaml` のスレッドに入っています。

- 聴衆役の感想は、直したら `replies` に `by: Claude`・`thinking` (考えたこと)・`change` (変えたこと) を足して `ball: none`・`closed: 直した`、直さないなら `closed: そのままにした` にして、理由を `thinking` に書きます。返事に「直した n 件・見送った n 件」と見送った理由を書きます。話者は見送りを戻せます
- 話者に確かめたいことは、返事で番号付きで聞き、`proposals.yaml` の `ask` に書きます。絵コンテの「話すこと」の中に覚え書きを書かないでください (話者と聴衆役が読む文に混ざります)
- 部品 (`packages/stage/src/kit/`・`parts/`) を直す必要があるときは、studio の中では書けません。返事で伝え、話者が「部品を直すのを許す」を押すと、次の 1 回だけ書けます

細かい指摘は、作業用サーバの agentation から Markdown で貼られることもあります。見出しの `## Page Feedback: /#/<scene-id>/<step>` が状態で、各メモのセレクタと周辺の文字が対象の要素です。

- 変更するのは、指示されたシーンだけです。他のシーンには触りません
- 話者が手で直した絵コンテ・シーンは、書き直しで上書きしません
- 同じ種類の指摘が 2 回来たら、トーク全体に同じ問題がないかを探して、まとめて直します。話者に同じ指摘を 3 回させないでください
- 構成や言葉の指摘は、絵コンテを先に直し、実装を追従させます
- 反映のたびに `check --motion` を回し、意図どおりかを目で確かめます

## 発表後 — 公開・収穫

1. 公開する前に、ノートを公開物として仕上げます。登壇までのノートは話者が自分の言葉に直す下書きでよいのですが、公開すると、ノートはトーク全体のテキスト (「テキストをコピー」と `talk.md`) に入り、閲覧者や AI が全文を読みます。全状態のノートを、会場にいなかった人の目で読み直します。直すのは、次のような話者なしでは通じない言葉です
   - 指さしと会場の前提。「こちらをご覧ください」「このあと交流会が」「このイベントの」。指す先は名前で書きます (資料なら作者と題名)。ノートはプレーンテキストなので、リンクは押せません
   - 前のシーンでしか定まらない指示語。「その間に」の起点の期間は、画面にもノートにも書きます
   - 年の無い日付と、社外の人が知らない社内の名前。初出で何者かを補います
   - 事実が素材で確かめられないときは、推測で埋めずに話者に聞きます
2. 公開するトークは `talk.tsx` の `public: true` を確かめ、`bun run site` でサイトを組み立てます。凍結はしません。全トークを最新のフレームワークでビルドし、前回と見た目が変わった状態があれば止まります。変化を確かめて話者に報告し、意図したものなら `--accept` で受け入れます。各トークの `talk.md` (トーク全体のテキスト) と PDF も開いて、話者なしで読める形になっているかを確かめます。デプロイは話者の確認を取ってから `bun run deploy` で行います。手順とつまずいたときの対処は `apps/slides/README.md` にあります
3. 振り返りをします。完全版・削った版・最終版の絵コンテの差分と、話者の指摘を読み、修正を 3 つに分けます。「何を伝えるか (芯・構成・前提)」「言葉」「見せ方」です。話者の型として残すべき学びは、理由と一緒に `references/style-defaults.md` に追記します
4. 部品を収穫します。このトークで素の React で書いた表現のうち、別のトークでも使えるものは `packages/stage/src/kit/` (中身を持たない汎用の部品) か `parts/` (自己紹介のように中身を持つもの) への昇格を検討します。2 本以上のトークで同じものを書いていたら、昇格します
