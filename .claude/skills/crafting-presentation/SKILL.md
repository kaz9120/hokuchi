# 登壇資料を、理解される順に組み立てる

このスキルは、登壇資料を対話から実装まで一続きで作るためのものです。完成の姿は、話者と合意した `talks/<YYYY_MM_DD_タグ_演題>/storyboard.md` (絵コンテ) と、`check` を通したシーンの実装 (`talk.tsx` と `scenes/`) です。書き手は Claude で、話すのも決めるのも話者です。

発表は「1 枚ずつのスナップショットの連続」ではなく、「シーンが移り変わる映画」として作ります (p.212)。シーンの中の要素は役者として残り続け、クリックごとに移動・変形・強調されます。フレームワーク `packages/stage` が再生と部品を持ち、配置と図は Claude が毎回シーンのコードで作り込みます (ADR-0026)。公開は slides.y-kaz.com で行います (ADR-0027)。

土台は Nancy Duarte『slide:ology』です。ページ番号はすべて同書のものです。進め方は ADR-0024 と ADR-0028 で決めています。

## 3 つの原則

1. 理解が先です。芯にするのは、聴衆に理解してほしいこと (中核メッセージ) です。締めは、話全体を総括するまとめにします。本は成功を「新たな見識を得た・行動を起こそうと思った・態度を改めようと思った」のどれかとしていて (p.269)、感動は疑問が解けて腑に落ちた瞬間に生まれると書いています (p.277)。行動は、理解した聴衆が自分で選ぶものです。画面で押しつけません
2. 完全版から削ります。持ち時間は最後の段で扱います。時間から先にシーンの数を決めると、削る元がないまま薄い中身を埋めることになります。本の Reduce も、全文から段階を踏んで削ります (p.241, p.243)
3. 文脈を持たない目で読みます。Claude も話者も、題材の文脈を持ちすぎています。「自分の頭では明快でも、他人には分かりにくい」(p.54) ので、話者に見せる前に、文脈を渡さない読み手に読ませて直します

## 着手前に開くファイル

references は、各 Phase の入口で開いてください。

- `references/audience.md` — 聴衆の描き方です。Phase 1 で開きます
- `references/message-map.md` — 章の順序と厚みの決め方です。Phase 3 で開きます
- `references/storyboard.md` — 絵コンテの形式と書き方です。Phase 4 で開きます
- `references/slide-design.md` — 1 シーンの設計です。最初に読む 1 文、読む順、載せる量を扱います。Phase 4 で開き、以降も手元に置きます
- `references/element-guide.md` — 伝えたいことの形から、見せ方と動きを選ぶ判断ガイドです。Phase 4 と Phase 7 で開きます
- `references/language.md` — 画面の言葉です。表記の約束と、避ける言い回しを扱います。Phase 4 と Phase 7 で開きます
- `references/audience-review.md` — 聴衆役のサブエージェントに渡す依頼文です。Phase 5 で開きます
- `references/reduce.md` — 削り方と粗密です。Phase 6 で開きます
- `references/build-scenes.md` — シーンの実装と、確かめるループです。Phase 7 で開きます。あわせて `packages/stage/docs/design.md` を開きます
- `references/style-defaults.md` — 話者固有の型です。Phase 3 以降で開きます

## 全体の流れ

Phase 0 から 8 まで順に進みます。Phase 2・3・5 は、話者の承認を取る関門です。ここを飛ばすと、合意していない前提の上にシーンを作り込むことになります。シーンの実装は手間がかかるので、構成と言葉は Phase 5 までに絵コンテの上で固めます。

| 5 | 聴衆役に読ませて直し、話者に見せる | storyboard.md | 承認 |

## Phase 0 — 前提を聞き、素材を読む

次のことを聞きます。文脈や素材から分かるものは聞き直しません。

1. 発表の場と、イベントのテーマ。イベントページがあれば URL を聞きます
2. 持ち時間と締切
3. 登壇の立場。個人か、MOSH を代表するか。テーマの選択に使います
4. 公開するか。公開するトークは slides.y-kaz.com に載り、閲覧者は話者なしでノートを読みます (p.258)。社内向けの発表は公開せず、このリポジトリ (GitHub で公開) の外に置きます
5. 既存の素材。過去の登壇資料・記事・社内ドキュメント・画面・データ

素材は、聞くだけでなく Phase 1 の前に読んでください。話者がすでに言語化したことを読まずに設計すると、同じことを設計し直したうえで食い違います。

- イベントページは WebFetch で読みます。募集文にある課題の言葉は、画面の言葉を選ぶときの基準になります
- 過去の登壇資料と記事を読みます。話者が繰り返し使う概念や、たどり着いている論がここに出ています
- 社内ドキュメントや議事録は、話者が指定したものを読みます。社内の用語は、ここにある正式な定義を使います
- スクリーンショットや図は Read で開き、何の画面かを自分の目で確かめます。取り違えたまま書くと、事実誤認が最後まで残ります

読んだものと、読んで分かったこと (話者の論・使っている言葉・まだ言語化されていないこと) を、短く話者に返します。

## Phase 1 — 聴衆を描く

`references/audience.md` を開きます。聴衆を集団の 1 行ではなく、名前のある 1〜2 人として描きます (p.35-36)。聴衆層が分かれるなら、層ごとに 1 人ずつ描きます。

核心の問いは次の 4 つです。「どんな人か」「何を得に来たか・なぜここにいるか」「何に悩んでいるか」「聞き終えて何が得られるか」。行動への誘いは、ここでは任意の問いです。7 問を尋問のように順番に聞かず、素材から埋まるものは埋め、埋まらない核心だけを対話で聞きます。

描いた聴衆から、この発表で扱うべき論点の候補を 3 つほど導きます (p.36)。結果は、Phase 4 で絵コンテの冒頭に書きます。

## Phase 2 — 中核メッセージを 1 文にする (関門)

聴衆に理解してほしいことを、1 文で確定します。これが絵コンテの `中核メッセージ:` になり、以降のすべてのシーンの採否の基準になります。

- 話者の言葉で書きます。素材の中から面白い材料を拾って逆算しないでください。材料から組むと芯がぶれ、話が周辺の細部に流れます。話者がまだ言語化していないなら、候補を作る前に、話者が普段考えていることを聞きます
- 理解の形で書きます。「〜してほしい」という行動ではなく、「〜は〜である」「〜が〜を変える」という主張にします。行動への誘いを持たせたいときは、別の欄 (`行動:`) に書きます
- 聴衆の「何を得に来たか」「何に悩んでいるか」に答えているかを確かめます
- 反論できる形になっているかを確かめます。誰も反対しない一般論は、芯として機能しません

1 文を話者に提示し、同意を取ってください。同意が取れるまで Phase 3 には進みません。

## Phase 3 — メッセージマップで章の順序と厚みを決める (関門)

`references/message-map.md` と `references/style-defaults.md` を開きます。章ごとに「この章で聴衆が理解すること」と「厚み」を 1 枚の表にします (p.39)。シーンの一覧はまだ作りません。

表を作るときは、次の順序を基準にします。

- 聴衆がすでに持っている前提から始め、本題の前に要る前提・用語を先に置きます
- 課題を、取り組みより前に置きます。課題を共有しないまま取り組みを出すと、聴衆は取り組みの意味を読めません
- 最後にまとめの章を置き、話全体を総括して中核メッセージに戻ります (p.41, p.245)

厚みは章ごとに、相対的な配分で書きます (例:「本題 5 : 前提 2 : 周辺 1」)。本題の章をいちばん厚くし、本題でない章は薄く通過させます。本題にしない話題は、薄い章として「扱わないこと」を明示します。

新しく出す用語と概念を数えてください。1 回の発表で聴衆が受け取れるのは 10 程度までです (p.254)。社内用語は、初出の章と定義を置く場所を表に書きます。

骨組みの案は、質の違うものを少なくとも 2 つ考えます。最初に浮かんだ案をそのまま採らないためです (p.47)。中核メッセージがいちばん伝わる案を 1 つ選び、選んだ理由と一緒に話者に提示して承認を取ってください。

## Phase 4 — 完全版の絵コンテを書く

`references/storyboard.md`、`references/slide-design.md`、`references/element-guide.md`、`references/language.md` を開きます。持ち時間はいったん忘れて、1 時間の枠があるつもりで書きます。聴衆が理解するのに要るものを、すべてシーンにします。削るのは Phase 6 です。

### 手順

1. `talks/<YYYY_MM_DD_タグ_演題>/storyboard.md` を作り (命名は過去資料と同じ。タグはイベントやコミュニティの名前)、冒頭に演題・中核メッセージ・聴衆 (Phase 1)・持ち時間・場・公開・テーマ・表記を書きます
2. 表記の約束を先に決めて `表記:` に書きます。見出しと大きな文の文末 (体言止めか文か)、句点の有無、読点の扱いをトーク全体で揃えます (p.171、`language.md`)
3. テーマを登壇の立場で選びます。個人は `hokuchi`、MOSH としては `mosh` です。この 2 つ以外のテーマは作りません
4. メッセージマップの章を `## ` で並べ、章ごとにシーンを書きます

### 1 シーンずつ決めること

詳しくは `slide-design.md` と `storyboard.md` にあります。

- `伝えること:` に、このシーンで聴衆に伝えることを 1 行で書きます。1 行で言えないなら、2 つのアイデアが混ざっています。分割してください。言えることが無いなら、そのシーンは作りません
- `前から受けるもの:` に、直前のシーンから何を受けて始まるかを書きます
- `見せ方:` に、画面の主役と、それがどう変わっていくかを書きます。見せ方と動きは `element-guide.md` で選びます。形と動きは関係を語るので、言いたい関係と一致させます (p.124, p.208)
- 状態を、話す順に 1 つずつ書きます。状態ごとに、聴衆が最初に読む 1 文を決めます。まだ話していない要素は出しません (p.203)
- 動きを付ける状態には、動きの役割を〔 〕で書きます。5 役割のどれにも当たらない動きは付けません (p.205)
- 各状態の文字は 3 秒で読める量にします (p.160)。入りきらないなら、文字を小さくするのではなく状態を分けます (p.126, p.172)
- `> ` の行に、話者が話す内容を全文で書きます。話者が読んで、自分の言葉に直せる下書きにします

## Phase 5 — 聴衆役に読ませ、話者に見せる (関門)

`references/audience-review.md` を開きます。完全版の絵コンテを、会話の文脈を持たないサブエージェントに読ませます。渡すのは聴衆プロフィールと、状態ごとの画面と話すことだけです。題材の背景・社内事情・この会話の経緯は渡しません。

聴衆役には、各シーンで何を言っているかを 1 行で答えてもらい、分からない語・唐突な転換・存在意義の分からない場面を挙げてもらいます。返ってきた指摘を 1 件ずつ判断して直します。直さない指摘には理由を残します。

直したら、絵コンテを話者に見せます。聴衆役の指摘と、直した内容・直さなかった理由も一緒に渡してください。話者の承認を得たら Phase 6 に進みます。

## Phase 6 — 持ち時間に合わせて、絵コンテの上で削る

`references/reduce.md` を開きます。ここで初めて持ち時間を扱います。実装の前に削るので、作らずに済むシーンが出ます。削る順序と基準は次のとおりです。

- メッセージマップの厚みの配分に合わせて、章ごとの時間を決めます
- 削るのは、中核メッセージに効かないシーンと、話者が自分のために置いた覚え書き (話すことに移す) です (p.240)。聴衆の理解に要る前提・定義・課題・まとめは残します (p.267)
- 本題でない章は、粗く通過させます。本題の章は、実物に留まって厚く見せます。粗密は、この段で当てます (ADR-0023 の考え方)
- 各シーンの `粗密:` に時間を書き、`node .claude/skills/crafting-presentation/scripts/wave.mjs talks/<slug>/storyboard.md` で合計と並びを確かめます

削った結果、聴衆役の指摘が戻ってくる (前提が消えて唐突になる) なら、削りすぎです。

## Phase 7 — シーンを実装し、確かめる

`references/build-scenes.md` と `packages/stage/docs/design.md` を開きます。そのうえで、画面の言葉を `references/language.md` で点検し、proofreading-ja-with-gemini スキルで Gemini に添削させます。修正案は 1 件ずつ採否を判断し、意味や主張を変える案は採りません。直した言葉は絵コンテにも反映します。

1. `talk.tsx` と、絵コンテのシーンごとに `scenes/<id>.tsx` を作ります。シーンの `id` と状態の数は、絵コンテと一致させます。ノートと名前は絵コンテから流し込まれるので、シーンには書きません
2. 座標と大きさの型 (`build-scenes.md` の 2) を守り、部品 (`Headline`・`Reveal`・`Morph`・`Connect`・`CountUp`) で状態遷移を書きます。部品で足りないところは素の React・SVG・Motion で書きます
3. 型検査と `check --motion` を回し、`out/check.md`・`out/states/`・`out/motion/` を自分の目で確かめます。検査の指摘と絵コンテとの食い違いは、すべて直します
4. 静止画は 1 状態ずつと、全体を並べた形の両方で見ます。見出しや本文の左端がシーンをまたいで揃っているか、写真の様式がトーク全体で揃っているか (p.180, p.192) を確かめます。コマ撮りでは、動きが〔役割〕どおりの意味を語っているか、「付けてはいけない動き」に当たらないかを見ます
5. 話者に見せます。作業用サーバ (`bun run dev <名前の先頭>`) は、話者に別ターミナルで立ててもらいます。← → で送り、`n` でノート、`o` で一覧、`p` で発表者ビューです

## Phase 8 — 話者のフィードバックで磨く

反映は、シーンの `id` と状態の番号の単位で行います。

- 変更するのは、指示されたシーンだけです。他のシーンには触りません
- 話者が手で直した絵コンテ・シーンは、書き直しで上書きしません
- 同じ種類の指摘が 2 回来たら、トーク全体に同じ問題がないかを探して、まとめて直します。話者に同じ指摘を 3 回させないでください
- 構成や言葉の指摘は、絵コンテを先に直し、実装を追従させます
- 反映のたびに `check --motion` を回し、意図どおりかを目で確かめます

## 発表後 — 公開・収穫

1. 公開するトークは `talk.tsx` の `public: true` を確かめ、`bun run site` でサイトを組み立てます。凍結はしません。全トークを最新のフレームワークでビルドし、前回と見た目が変わった状態があれば止まります (ADR-0029)。変化を確かめて話者に報告し、意図したものなら `--accept` で受け入れます。デプロイは話者の確認を取ってから行います
2. 振り返りをします。完全版・削った版・最終版の絵コンテの差分と、話者の指摘を読み、修正を 3 つに分けます。「何を伝えるか (芯・構成・前提)」「言葉」「見せ方」です。話者の型として残すべき学びは、理由と一緒に `references/style-defaults.md` に追記します
3. 部品を収穫します。このトークで素の React で書いた表現のうち、別のトークでも使えるものは `packages/stage/src/kit/` (中身を持たない汎用の部品) か `parts/` (自己紹介のように中身を持つもの) への昇格を検討します。2 本以上のトークで同じものを書いていたら、昇格します
