# note を研ぎ澄まして書く

このスキルは、題材から公開までを一本で通します。完成の姿は 2 つです。`articles/note/drafts/<slug>/index.md` に置いた原稿と、そこから note に貼って公開した記事です。

書くのは Claude で、決めるのは人間です。Claude が担うのは 4 つです。芯を 1 文に絞る手伝い、フックの発見、密にする場所の選択、そして削ることです。

## この 4 つを外さない

1. 読後感は「カフェで聞いた話」にします。一方で、書く姿勢は徹底的にロジカルに保ちます。出てくる文章はカジュアルに見えます。それでも、何を伝えるか・誰に届けるか・どう構成するかは戦略的に設計しています。この二層構造がこのスキルの核です
2. 濃度をいちばん優先します。濃度とは、読者が受け取る発見の量 ÷ 文字数のことです。長い記事は読まれません。短くても薄い記事は読まれません。だから削って濃くします
3. 密は徹底的に密、粗は思いきり粗にします。Claude の初稿は、どの段落にも同じだけ手をかけた、強弱のない文章になります。1 文ずつは欠点がなくても、通して読むと目が滑ります。密にする場所を 1 つ選んで描き切り、残りは通過してください (ADR-0023)
4. 文章は一方向的なものとして書きます。「私はこう思う」「私はこうした」を書き、共感は求めません。自己開示の結果として共感が生まれるなら、それで十分です

## 着手前に開くファイル

- `references/voice.md` — 人格と文体の規範です。実測値つきです。Phase 4 の前に必ず開いてください
- `references/somitsu.md` — 粗密の付け方です。どこを密にし、どこを通過するかを扱います。Phase 3 で開き、Phase 4・5 でも手元に置きます
- `references/density.md` — 削る技術で、Phase 5 の手順書です。このスキルの中心になります
- `references/structure.md` — 構成・タイトル・タグ・画像です。Phase 3 と Phase 7 で開きます
- `references/review.md` — 評価の観点です。Phase 6 で開きます
- `references/examples.md` — 公開済み 44 本から抜いた実例です。Phase 3〜5 で開きます

### 実物を読む

`articles/note/` に公開済みの記事があります。抽象的なルールより、実物のほうが多くを伝えてくれます。書く前に、題材が近い記事を 2〜3 本読んでください。

- エッセイ・考えたこと系 → `2026-08-16-tired-of-quick-builds`、`2026-07-26-meeting-ideas-i-lack`
- 技術・やってみた系 → `2026-08-23-rewrite-docs-for-ai`、`2026-08-09-ai-builds-shogi-ai`
- イベントレポート系 → `2026-05-24-tskaigi-2026`、`2026-03-08-emconf-jp-2026`
- 月次振り返り → `2026-08-30-monthly-review`

新しい記事ほど研ぎ澄まされています。2025 年 12 月前後の記事には、いま避けたい書き方が残っています。「本記事では〜ご紹介します」「共感していただけると思うのですが」のような言い回しです。古い記事は反面教師として読んでください。

## 全体の流れ

Phase 0 から 7 まで順に進みます。Phase 2 と Phase 3 は、ユーザーの承認を取る関門です。ここを飛ばすと、合意していない芯の上に本文を積むことになります。

Phase 5 (削る) は独立した工程です。書きながら削るのではなく、書き切ってから削ります。この順序は崩さないでください。

原稿を持ち込まれたときは Phase 5 から入ります。「見てほしい」「レビューして」は、削る作業の依頼だと解釈してください。最初に見出しごとの字数を並べ、どこが密でどこが粗かを言い当てます。そのうえで削り始めます。密が見当たらない原稿なら、削る前に密の場所を決め直します (Phase 3 の後半)。

## Phase 0 — 題材を受け取る

題材は、音声入力の書き起こし、箇条書きのメモ、「これについて書きたい」の一言など、いろいろな形で来ます。どの形でも、まず材料を揃えます。

- 題材について書いた過去の note があれば読みます (`articles/note/`)
- 登壇資料が元になるなら `talks/<slug>/deck.yaml` を読みます
- イベントレポートなら connpass ページを WebFetch で読みます
- スクリーンショットや図があれば Read で開き、何が写っているかを自分の目で確かめます

ネタ出しの質問はしません。書きたいことはすでにある前提で、整理に集中します。

---

## Phase 1 — 読者と持ち帰り

決めるのは 2 つだけです。長く聞かず、文脈から埋まるなら埋めて確認だけ取ります。

1. 誰に向けて書くか。「エンジニア全般」では広すぎます。「AI でツールを作り始めたものの、作って満足して使わなくなっている人」くらいまで絞ります
2. 読者に何を持ち帰ってほしいか。知識なのか、視点なのか、行動なのかを決めます

候補を出す前に、材料の中を読んでください。書き手はたいてい、材料のどこかで読者に向けた言葉をすでに書いています。とくに最後の段落に出やすいです。そこを読まずにこちらで読者の候補を作ると、書き手はこちらが用意した枠の中でしか選べなくなります。読者を取り違えると、本題が最後の章に唐突に現れる構造になります。

読者が決まると、説明の量が決まります。読者が知っていることは書かず、知らないことだけを書きます。ここが濃度の第一歩です。

---

## Phase 2 — 芯を1文に (関門)

この記事で言いたいことは何か。それを 1 文で書きます。

書けないなら、まだ書く段階ではありません。題材が 2 つ以上あるなら記事を分けます。1 記事に 1 メッセージです。

芯の 1 文は、次を満たすようにします。

- 主張になっている (「〜について書く」は題目であって、主張ではありません)
- 自分の体験から出ている (借り物の一般論ではありません)
- 読者にとって新しい (自明なことを言っていません)

悪い例: 「AI 開発ツールについて書く」「個人開発の学びをまとめる」
良い例: 「なんでも作れることに価値はない。価値があるのは、作ったものを使い続けられるかどうかだった」

ユーザーに芯の 1 文を提示し、これでいいか確認を取ってください。承認されるまで Phase 3 には進みません。

---

## Phase 3 — フックと骨組み (関門)

`references/structure.md`、`references/somitsu.md`、`references/examples.md` を開きます。

### フックを見つける

冒頭で、読者が読み進めるかどうかが決まります。時系列では始めません。いちばん面白かったことや、自分が引っかかった瞬間を冒頭に置きます。

公開済み記事の冒頭は中央値 41 字で、短めです。

> 自分が欲しいツールがその日のうちに動く。 最初はそれだけで楽しかった。
> 7月25日の大吉祥寺.pmで、wabiさんがこんな話をしていました。

フック候補を 2〜3 案出して、選んでもらいます。

### 骨組みを組む

見出しレベルの構成案を出します。分量は `references/structure.md` の 3 つの型から選びます。迷ったらショート (800字前後) に寄せてください。短いほうが読まれるからです。

骨組みと一緒に、画像の入る位置も置きます。X のポストや外部記事の埋め込みは、URL だけの行を 1 行置きます。note のエディタに貼るとカードになります。公開後に `sync` が取り込む `index.md` も同じ形になります (ADR-0021)。

### 密にする場所を決める

骨組みの各ブロックに「密」か「粗」と、字数の予算を書き添えます。「中」は作りません。密は見出し 1 つ分で、長い記事でも 2 つまでにします。選ぶのは、芯の 1 文を読者が信じる根拠になる場面です。用語の定義、議論の経緯、一般論は密にしません。

粗にするとは、論点を落とすことです。粗のブロックは 150 字までを目安にし、論点は 1 つだけ運びます。登壇資料や長いメモが素材のときは注意してください。素材が全論点を均等に語っているので、写すと均等な記事になります。何を書かないかを、ここで決めます。

ここを決めずに書くと、全ブロックを均等に丁寧に書くことになります。それが Claude の既定の書き方で、記事がつまらなくなる原因です。決め方と実例は `references/somitsu.md` にあります。

密の場所が決まったら、そこについてだけ材料を聞きます。何が見えていたか、誰が何と言ったか、数字、順番、そのときの感情です。密は材料がないと書けません。想像で補うと、誰の体験でもない文章になります。粗の場所については聞きません。

ユーザーに骨組みと粗密の割り振りを提示し、承認を取ってください。ここで構成を固めておかないと、Phase 5 で削るときに骨ごと崩れます。

## Phase 4 — 書く

`references/voice.md` を開いてから書きます。出力先は `articles/note/drafts/<slug>/index.md` です。front matter は公開済み記事と同じ形にします。

```yaml
---
title: サクッと作れる楽しさに、飽きた
hashtags:
  - エンジニア
  - 個人開発
---
```

密の場所は長さを気にせず書きます。聞いた材料を全部使い、その場にカメラを置いたように書いてください。削るのは次の Phase の仕事です。書きながら削ると、削るべきでないものまで削れてしまいます。

粗の場所は最初から短く書き、1〜3 行で通過します。あとで削ればいいと丁寧に書くと、削るときに惜しくなります。結局どの段落も同じ重さで残ってしまいます。

次の 4 つは書きながら守ります。後から直すのが難しいものです。

- 一人称は「私」にします
- フック・ファーストで書きます。背景説明から始めません。冒頭で世界観を丁寧に描くと、眠い導入になります
- 具体を入れます。数字・固有名詞・実際に起きたことです。「さまざまな工夫をした」ではなく「レイアウト案を 100 個作らせて 12 個選んだ」と書きます
- 具体は密の場所に集めます。全段落に均等に撒くと、どこも少しずつ具体的で、どこも山になりません

---

## Phase 5 — 削る

このスキルの中心です。`references/density.md` を開き、そこに書かれた順に実行します。

目標は明確に置きます。書き上げた原稿から 2 割削ります。削れないと思ったところからも、たいてい 2 割は出てきます。ただし、接続語と文末の受けは 2 割の出どころにしません。

2 割は粗から取ります。密の場所には手を付けません。均等に 2 割ずつ削ると、均等に薄い文章が短くなるだけです。密の場所に抽象語が残っていたら、削るのではなく事実に置き換えます。

削り終えたら、見出しごとの字数を並べて波を見ます (`references/somitsu.md` の手順 5)。どのブロックも同じ重さなら、まだ平らです。粗と付けたブロックが 150 字を超えていたら、ラベルを付けただけで書き方が変わっていません。論点を 1 つに絞って畳むか、ブロックごと落とします。

削る前と後を並べて、ユーザーに見せます。何をなぜ削ったかを短く添え、見出しごとの字数も一緒に出します。

### 往復はブラウザで受ける

ここから先の往復は、ターミナルではなく `serve` で受けます (ADR-0022)。書き上げたら立てて、URL を伝えます。

```
hokuchi-note serve articles/note/drafts/<slug>/
```

`hokuchi-note` が見つからないときは、リポジトリのルートから `node tools/notes/cli.mjs <サブコマンド> ...` で同じように動きます。このスキルの `hokuchi-note` コマンドは、すべてこの形に読み替えられます。

ユーザーはブラウザで文を選び、その場の入力欄に一言書いて Enter で送ります。コメントは `drafts/<slug>/feedback.md` に節ごと追記されます。ユーザーが「ターミナルに貼る」でまとめて貼ってきたときや、「フィードバック見て」と言ってきたときは、次を回します。

1. `feedback.md` を読みます (貼られた本文と同じ内容です)。節ごとに、段落番号・見出し・引用した本文・コメントが入っています
2. 原稿を直します。画面は原稿の変更に追従するので、直したら報告するだけで大丈夫です
3. 反映した節を `feedback.md` から消します。このファイルは往復の受け渡し口で、記録ではありません。残った節は「未反映」として画面に出ます

コメントが構成そのものに及ぶなら、Phase 2〜3 に戻って合意し直します。

## Phase 6 — 検査

### 機械で検査する

```
hokuchi-note lint articles/note/drafts/<slug>/index.md
```

lint が見るのは、文の長さ、段落の長さ、ぼかし表現の密度、型どおりの言い回し、共感を求める表現、結びの重さ、漢字率です。閾値は公開済み 44 本の実測から決めています。そのため、警告は「自分の水準から外れている」という意味になります。`serve` を立てていれば、同じ指摘がサイドバーに出ます。クリックすると該当段落に飛べます。

warn はすべて潰すつもりで直します。潰せないなら、その理由を言えるようにしておいてください。lint が見ているのは数えられるものだけで、濃いかどうかは見ていません。

### 人が読んで検査する

`references/review.md` の観点で読み返します。特に次の 4 つは、lint では拾えません。

- 芯の 1 文が伝わるか。読者が読み終えて、自分の言葉で言い換えられるかを見ます
- フックが効いているか。冒頭 3 行で読む気になるかを見ます
- 具体があるか。抽象語で済ませた箇所がないかを見ます
- どこが密か指させるか。読み終えて覚えている場面が 1 つあるかを見ます。全段落が同じ重さなら、平らなまま残っています

最後に声に出して読みます。カフェで話して違和感があるところは直します。

## Phase 7 — 出す

`references/structure.md` を開きます。

1. タイトルを 3 案出します。先頭 25 字に核を置き、内容を隠しません
2. タグを 3〜5 個付けます。主題タグ 2〜3 と、ジャンルタグ 1〜2 です。note 公式のお題があれば 1 つ足します
3. 見出し画像を用意します。1280×670px です。有無で PV とスキ数が変わります
4. 本文の画像は密の場所に寄せます。枚数の目安は 800 字に 1 枚です。ただし均等には撒きません。スクリーンショットや当時のポストは密の核になります

本文は `serve` の画面の「note に貼る本文をコピー」か、`paste` でクリップボードに入れて、note のエディタに貼ります。見出し・強調・埋め込みの URL 行はそのまま入ります。画像行は `（画像 n/N: ファイル名 ｜ キャプション: …）` に置き換わります。note 側でその行を消して、画像を入れてください (「assets を開く」で Finder が開きます)。

```
hokuchi-note paste articles/note/drafts/<slug>/index.md
```

公開したら、次を回してアーカイブに凍結します。

```
hokuchi-note sync
```

公開日と note key が入った `articles/note/<公開日>-<slug>/` ができます。`articles/note/slugs.json` に slug を足しておくと、ディレクトリ名が読める形になります。凍結を確認したら、`drafts/<slug>/` は消してかまいません。

## 振り返り

公開して反応が見えたら、`references/voice.md` の末尾に学びを 1 行足します。うまくいった言い回し、滑った構成、読まれた記事の傾向などです。このスキルは 44 本の実測の上に立っています。記事が増えるほど、規範を更新できます。

数値を測り直すときは、`articles/note/` 全体に lint を回します。

```
hokuchi-note lint
```

公開済み記事が error を出さず、warn が改善余地として出る状態を保ちます。error が出るようになったら、閾値か規範のどちらかがずれています。
