# note を研ぎ澄まして書く

このスキルは、題材から公開までを一本で通します。完成の姿は 2 つです。`~/Hobby/hokuchi-private/notes/<slug>/index.md` (公開リポジトリの外) に置いた原稿と、そこから note に貼って公開した記事です。

決めるのは話者で、Claude は話者の言葉を記事に組み立てます。Claude が担うのは 4 つです。話者から言葉を引き出すこと、芯を 1 文に絞る手伝い、話者の言葉を書き言葉に直して並べること、そして削ることです。

## この 4 つを外さない

1. 話者の言葉が原料です。Claude は作文しません。記事の文はどれも、元になった素材 (話者の言葉・画像・ログ・ページ・公開されている事実) の箇所を指せます。複数の箇所を 1 文に畳んでもかまいません。判定の基準は、話者がその文を読んで「そう考えている」と言えるかです。足りなければ話者に聞きます。話者の下書きへの指摘 (「AI っぽい」「ポエム感」「主張が謎」) の大半は、Claude が素材の外から足した文に向いていました。そのまま公開された版は、どれも話者の言葉を書き言葉に直したものです
2. 中身は話者から、組み立ては大胆に。Claude が作らないのは中身 (描写・数字・気持ち・教訓) で、組み立ては Claude の仕事です。いちばん強い数字や場面を冒頭に置く、見出しに読者が先を読みたくなる主張を立てる、話者が答えにたどり着いた瞬間 (計算して数字が出た、比べて違いが見えた) を場面として見せる。ここを控えると、正確でも誰も最後まで読まない記事になります。面白さは、話者しか持っていない細部と、その見せ方から来ます (`references/interest.md`)
Claude が作らないもの・Claude がすること・話者に聞くことの境界は次のとおりです。

| 区分 | 中身 |
|---|---|
| 作らない | 様子の描写、数字、気持ちの推測、教訓、因果 (話者が言っていない「だから」「そのせいで」) |
| Claude がする | 複数の発言を 1 文に畳む、順序を入れ替える、節の主張を話者の語で 1 文にする、冒頭と見出しを立てる、前提・場面・話の向きを示す言葉を足す、話者が言った問い・理由・決めたことを、考えた順の 1 本の線につなぐ (つなぎ目のどちらの端も素材にある) |
| 聞く | 理由と因果が素材に無いとき、芯の中の抽象語の中身が無いとき、密の場面の細部が無いとき |

3. 密は徹底的に密、粗は思いきり粗にします。Claude の初稿は、どの段落にも同じだけ手をかけた、強弱のない文章になります。密にする場所を 1 つ選んで描き切り、残りは通過してください (`references/somitsu.md`)
4. 話者の声で書きます。です・ます でつなぎ、接続語を残し、読点を減らします。Claude からは常体を足さず、短文の連打で「リズム」を作りません (`references/voice.md`)。文章は一方向的なものとして書き、「私はこう思う」「私はこうした」を書きます。共感は求めません

## 着手前に開くファイル

- `references/interest.md` — 読まれて勧めたくなる記事の条件と、話者に聞く問いです。Phase 0〜3 で開きます
- `references/voice.md` — 人格と文体です。実測値つきです。Phase 4 の前に必ず開いてください
- `references/ai-tells.md` — AI っぽさの型です。話者の実際の直しから集めています。Phase 4 の終わりと Phase 6 で使います
- `references/somitsu.md` — 粗密の付け方です。Phase 3 で開き、Phase 4・5 でも手元に置きます
- `references/density.md` — 削る手順です。Phase 5 で開きます
- `references/structure.md` — 構成・記事の種類ごとの約束・タイトル・タグ・画像です。Phase 3 と Phase 7 で開きます
- `references/review.md` — 評価の観点です。Phase 6 で開きます
- `references/eyecatch.md` — 見出し画像の作り方です。Phase 7 で開きます
- `references/examples.md` — 公開済みの記事から抜いた実例です。Phase 3〜5 で開きます

### 実物を読む

`articles/note/` に公開済みの記事があります。ルールより、実物のほうが多くを伝えます。Phase 4 の前に、公開日が新しい順に 2 本と、題材が近い記事 1 本を、最後まで通して読んでください。新しい記事ほど、話者が直し終えた声に近いです。2025 年 12 月前後の記事は、「本記事では〜ご紹介します」のような避けたい書き方を残しています。

題材が近い記事の目安は `references/examples.md` の末尾の表にあります。

## 全体の流れ

Phase 0 から 7 まで順に進みます。Phase 2 と Phase 3 は、ユーザーの承認を取る関門です。Phase 6 は、検査が通るまで Phase 7 に進まない関門です。ここを飛ばすと、合意していない芯の上に本文を積むことになります。

Phase 5 (削る) は独立した工程です。書きながら削るのではなく、書き切ってから削ります。この順序は崩さないでください。

記事は、studio (`apps/studio`) の中でも、ターミナルでも同じ流れで進みます。studio の中では、ユーザーは作品の画面で話して候補を選び、進むボタンを押します。Claude は studio が起こした作品の会話の中で、このスキルに沿って書きます。どの Phase が studio のどのステップとファイルに当たるかは、次のとおりです。

| Phase | studio のステップ | ファイル |
|---|---|---|
| 0〜2 題材・読者・芯 | 伝えたいこと | `~/Hobby/hokuchi-private/works/<id>/proposals.yaml` (候補)・`work.yaml` (確定した値) |
| 3 フックと骨組み | 構成 | `~/Hobby/hokuchi-private/notes/<名前>/outline.yaml` |
| 4〜6 書く・削る・検査 | 原稿 | `notes/<名前>/index.md`・`extract.md` (抜き出し)・`check.md` (検査の記録)・`feedback.yaml`・`readers.yaml`・`reads/` |
| 7 出す | 公開 | `notes/<名前>/index.md` の front matter・`assets/` |

studio の中で動くときは、studio が渡す作品の文脈 (システムプロンプトの「hokuchi studio の中での作業」) に従います。要点は次の 3 つです。

- 候補 (読者・芯・フック・タイトルなど) は会話の文に埋めず、`proposals.yaml` に書きます。確定した値 (`work.yaml`) は書けません。ユーザーが画面で押すと確定します
- 返事の最後に、ユーザーに求めることを `proposals.yaml` の `ask` に 1 つ書きます
- 関門 (Phase 2・3 の承認) は、ユーザーが画面の進むボタンを押すことで通ります

原稿を持ち込まれたときは Phase 5 から入ります。「見てほしい」「レビューして」は、削る作業の依頼だと解釈してください。最初に見出しごとの字数を並べ、どこが密でどこが粗かを言い当てます。そのうえで削り始めます。密が見当たらない原稿なら、削る前に密の場所を決め直します (Phase 3 の後半)。

## Phase 0 — 話者の言葉を集める

題材は、音声入力の書き起こし、箇条書きのメモ、「これについて書きたい」の一言など、いろいろな形で来ます。どの形でも、まず材料を揃えます。

- 題材について書いた過去の note があれば読みます (`articles/note/`)
- 登壇資料が元になるなら、トークの絵コンテ `talks/<トーク>/storyboard.md` を読みます (社内向けは `~/Hobby/hokuchi-private/talks/`)
- イベントレポートなら connpass ページを WebFetch で読みます
- スクリーンショットや図があれば Read で開き、何が写っているかを自分の目で確かめます

次に、記事の原料になる話者の言葉が足りているかを見ます。話者は無からは話しません。足りないときは、材料を手がかりにこちらから聞きます。聞くのは、書きたいことの中身を引き出す問いです (`references/interest.md` の 11)。題材そのものを探す質問 (「何を書きたいですか」) はしません。

- 出来事と出来事の間の「なぜ」。材料には出来事が並んでいても、理由が無いことが多いです。聴衆役に「理由が書かれていない」と言われた記事は、ここを聞いていませんでした
- いちばん意外だったこと、人に話して笑われたり驚かれたりしたこと
- 感情の語の中身。「楽しかった」なら、何が楽しかったか

問いは 3 つまでにして、話者が音声入力で答えやすい形 (はい・いいえで終わらない形) にします。studio の中では、問いを返事に番号付きで書き、`proposals.yaml` の `ask` には「問いに答えてください」と書きます。答えは言い回しも含めて素材として扱います。

## Phase 1 — 読者と持ち帰り

決めるのは 2 つだけです。長く聞かず、文脈から埋まるなら埋めて確認だけ取ります。studio の中では、決めた読者と持ち帰りは作品の文脈の「確定した値」に入っています。まだ無ければ `proposals.yaml` の `reader`・`takeaway` に案を書きます。

1. 誰に向けて書くか。「エンジニア全般」では広すぎます。「AI でツールを作り始めたものの、作って満足して使わなくなっている人」くらいまで絞ります
2. 読者に何を持ち帰ってほしいか。知識なのか、視点なのか、行動なのかを決めます

候補を出す前に、材料の中を読んでください。書き手はたいてい、材料のどこかで読者に向けた言葉をすでに書いています。とくに最後の段落に出やすいです。そこを読まずにこちらで読者の候補を作ると、書き手はこちらが用意した枠の中でしか選べなくなります。読者を取り違えると、本題が最後の章に唐突に現れる構造になります。

読者が決まると、説明の量が決まります。読者が知っていることは書かず、知らないことだけを書きます。ここが濃度の第一歩です。

## Phase 2 — 芯を1文に (関門)

この記事で言いたいことは何か。それを 1 文で書きます。

書けないなら、まだ書く段階ではありません。題材が 2 つ以上あるなら記事を分けます。1 記事に 1 メッセージです。

芯の 1 文は、次を満たすようにします。

- 主張になっている (「〜について書く」は題目であって、主張ではありません)
- 自分の体験から出ている (借り物の一般論ではありません)
- 読者にとって新しい (自明なことを言っていません)
- 芯の中の抽象語 (「やり方が変わった」「楽しかった」) の中身を、素材から 1 つずつ言える。言えないなら、承認を取る前に話者に聞きます
- 話者がいちばん動いた所を含んでいる。人に話して驚かれたこと、意外だったことが芯の近くにあるかを確かめます。Claude が材料を整理して作った芯は、正しくても誰も読みたくならないことがあります

悪い例: 「AI 開発ツールについて書く」「個人開発の学びをまとめる」
良い例: 「地方カンファレンスは、ご当地まで味わって完成する」「音声入力が合うかどうかは、そのときの開発のやり方で変わる」

芯を「A ではない。B だ」の対句にしないでください。対句はその場では強く見えますが、後で「ポエム」と撤回されやすい形です (`references/ai-tells.md` の 2)

ユーザーに芯の 1 文を提示し、これでいいか確認を取ってください。承認されるまで Phase 3 には進みません。studio の中では、候補を `proposals.yaml` の `core` に 3 つほど書き、ユーザーが画面で選んで「この内容で構成へ」を押すと承認になります。確定した芯は作品の文脈の「確定した値」にあります。あとから芯を直したくなったら、`coreRevision` に案を書きます。

## Phase 3 — フックと骨組み (関門)

`references/structure.md`、`references/somitsu.md`、`references/interest.md`、`references/examples.md` を開きます。

### フックを見つける

冒頭で、読者が読み進めるかどうかが決まります。冒頭は、場面・他人の発言・告白のどれかにします (`interest.md` の 6)。ただし、フックをタイトルが担うとき (逆説や問いのタイトル) は、冒頭でそれを繰り返さず、事実から入ってかまいません (公開済みの例: タイトル「音声入力を再開した。やめた理由が、もう思い出せない」、冒頭「6月末に音声入力をやめたのですが、11月から Aqua Voice の課金を再開しました。」)。公開済み記事の冒頭は中央値 44 字で、短めです。

> 自分が欲しいツールがその日のうちに動く。 最初はそれだけで楽しかった。
> 7月25日の大吉祥寺.pmで、wabiさんがこんな話をしていました。
> 発表は1分オーバーしました。

フック候補を 2〜3 案出して、選んでもらいます。案は質の違うものにします (場面 / 他人の言葉 / 告白)。どの案も、話者の言葉か素材から取ります。

仮のタイトルも、ここで決めます。タイトルと冒頭は役割を分けます。タイトルが結論や数字を言うなら、冒頭はそれを裏づける事実から入り、最初の節でタイトルの約束 (数字・結論) を回収します。最後のタイトルは Phase 7 で選び直してかまいません。

### 骨組みを組む

見出しレベルの構成案を、次の順で作ります。素材をそのまま見ながら見出しを立てると、話者が話した順に引きずられます。話者は思いついた順に話すので、その順に組むと、記事が会話の書き起こしになります。

1. 素材の中の事実と発言を、話した順を崩して 3 つに分けて書き出します (手元のメモで、原稿には書きません)。①結論 (いちばん強い数字・到達点)、②転換点 (いちばん動いた場面、答えが出た瞬間。密の候補)、③前提と経緯 (読者が知らないと読めない最小限)
2. 骨組みを質の違う 2 案で作ります。1 案は、出来事が起きた順に進む形です。もう 1 案は、①か②から始めて、そこへ至る経緯をあとに置く形です。経緯の説明 (③) だけで始まる案は作りません
3. 2 案のうち、素材を知らない読者が迷わず追えて、芯がいちばん伝わるほうを選びます。変化や経緯を語る記事 (やめた話・戻した話・参加記) は、時系列のほうが追いやすいことが多いです。結果を先に書いてから過去に戻ると、読者は同じ時期を 2 回読むことになります。見出しはその節の主張にし (`references/structure.md`)、並びは読者の頭に浮かぶ問いの順にします
4. 承認を取る前に、文脈を持たない新しいサブエージェントに、仮のタイトル・骨組み・素材だけを渡して確かめさせます。見出しの並びが素材の話した順をなぞっていないか、タイトルの約束が冒頭か最初の節で回収されるか、各見出しが主張になっているか、タイトルやフックが問いや逆説 (「〜が思い出せない」) なら本編がそれを打ち消していないか (本編で普通に理由を並べない)、密にした節に書ける材料 (場面・数字・比べた事実) が素材にあるか、の 5 つです。指摘があれば組み直します。密の材料が無く、話者も書かないと決めているなら、材料のある節を密にします

分量は、話者の言葉の量で決めます。迷ったら短いほうに寄せてください。選ばなかった案は、選んだ理由と一緒に返事に書きます。

骨組みと一緒に、画像の入る位置も置きます。X のポストや外部記事の埋め込みは、URL だけの行を 1 行置きます。note のエディタに貼るとカードになります。公開後に `sync` が取り込む `index.md` も同じ形になります。

### 密にする場所を決める

骨組みの各ブロックに「密」か「粗」と、字数の予算を書き添えます。「中」は作りません。密は見出し 1 つ分で、長い記事でも 2 つまでにします。選ぶのは、芯の 1 文を読者が信じる根拠になる場面です。用語の定義、網羅的な経緯、一般論は密にしません。

判断の密に入れるのは 4 つです。比べた選択肢、それぞれの限界や障害、決めたこと、決め手です。判断を支える数字や比べた相手 (いまの人数、率、ほかの案) は、別の粗の節に切り出さず、密の節に置きます。

密には 2 種類あります。出来事の記事 (イベント、体験) では、その場にカメラを置いたように、見えたもの・言われた言葉・順番を描く「場面の密」です。考えや決めたことの記事 (設計の判断、やめた話、目標の立て方) では、頭の中にカメラを置いたように、何を試し、どの事実を見て違和感を覚え、何と何を比べて決めたかを描く「判断の密」です。判断の記事で「議論の経緯だから」と全部を粗にすると、山の無い記事になります。

粗にするとは、論点を落とすことです。粗のブロックは 150 字までを目安にし、論点は 1 つだけ運びます。登壇資料や長いメモが素材のときは注意してください。素材が全論点を均等に語っているので、写すと均等な記事になります。何を書かないかを、ここで決めます。

ここを決めずに書くと、全ブロックを均等に丁寧に書くことになります。それが Claude の既定の書き方で、記事がつまらなくなる原因です。決め方と実例は `references/somitsu.md` にあります。

密の場所が決まったら、そこについてだけ材料を聞きます。場面の密なら、何が見えていたか、誰が何と言ったか、数字、順番、そのときの感情です。判断の密なら、何と何を選択肢として比べたか、退けた案のどこに限界を感じたか、決め手になった事実は何かです。密の節にも、論点は 1 つだけ置きます。密は材料がないと書けません。想像で補うと、誰の体験でもない文章になります。粗の場所については聞きません。

ユーザーに骨組みと粗密の割り振りを提示し、承認を取ってください。ここで構成を固めておかないと、Phase 5 で削るときに骨ごと崩れます。

骨組みと粗密は、studio の中でもターミナルでも、原稿の置き場の `outline.yaml` に書きます (lint が節ごとの字数を予算と比べるのに使います)。見出しごとに `title`・`point` (伝えること。冒頭はフック)・`grain` (密 / 粗)・`budget` (字数の予算) を並べます。ユーザーは studio の構成の画面で、同じものを見て直します (画面では密を「厚く書く」、粗を「短く通る」、予算を「目安の字数」と呼びます)。ユーザーが直した内容が正です。フックの案は `proposals.yaml` の `hook` に書きます。「この構成で書く」が押されたあとは、`outline.yaml` は書けません。直したいときは `outlineRevision` に案を書きます。

## Phase 4 — 書く

骨組みを渡されて Phase 4 から入るときも、書く前に Phase 3「骨組みを組む」の手順 4 の 5 つの確かめを骨組みに当てます。落ちる所があれば、直した骨組みで書き、`check.md` の「話者に見せる変更」に書きます (studio では `outlineRevision` に案を書きます)。`point` に書かれた事実で素材と話者の答えに無いものは、落とさずに聞くことにします。

`references/voice.md` と `references/interest.md` を開き、公開済みの記事を 3 本通して読んでから書きます (「実物を読む」)。出力先は `~/Hobby/hokuchi-private/notes/<名前>/index.md` です (公開リポジトリの外)。studio の中では、原稿のフォルダは作品を始めたときに作品の id の名前で用意されています。場所は作品の文脈にあります。英語の名前は公開の準備で `proposals.yaml` の `slug` に案を出し、ユーザーが選ぶと studio がフォルダの名前を変えます。front matter は公開済み記事と同じ形にします。

```yaml
---
title: サクッと作れる楽しさに、飽きた
hashtags:
  - エンジニア
  - 個人開発
---
```

### 書き方: 話者の言葉を、書き言葉に直して並べる

Claude の初稿が AI っぽくなるのは、骨組みを見て文章を新しく作るからです。話者の言葉から組み立てると、話者の声が残ります。次の順で書きます。

1. 骨組みの節ごとに、その節で使う話者の言葉を素材から抜き出して並べます。抜き出しは、素材の箇所 (何番目の発言か) と対応づけた作業メモにし、Phase 6 の文脈なしの検査に一緒に渡します (原稿の置き場の `extract.md`。原稿には書きません)。`extract.md` の先頭には、Phase 2 で合意した芯の 1 文を写します (studio では作品の文脈にあります)。抜き出すのは、話者が決めたこと・気づいたこと・その理由・見たものです。節ごとに、最終稿まで残す具体 (固有名詞・製品やモデルの名前・数字・画像・話者の言い回し) に「残す」と印を付けます。話者が書き手に頼んだこと (「ここは突っ込みたい」) には印を付けず、頼まれた中身 (突っ込みそのもの) を書きます。話している最中の相づちや、資料を読みながらの反応は抜き出しません。節に使える言葉が無いなら、その節は話者に聞くか、骨組みから外す候補です
2. 抜き出した言葉から、使う 1 回を選びます。話者は音声入力で同じことを何度も言い直します。同じ中身が 2 回以上出てきたら、いちばん具体的な 1 回だけを使い、残りは捨てます。節をまたいで同じ比較 (「6 月はこうだった、11 月はこうだ」) を 2 回書いていないかも確かめます。言い直すたびに中身が進んでいる (「いや、なんならぼくは、コードを避けているのだ」のように一段深まる) なら、それは重複ではないので残します
3. 節ごとに、選んだ言葉が言っていることを 1 文にまとめ、`outline.yaml` の `point` と照らします。その主張を支える順 (場面や前提 → 起きたこと・数字・比べたこと → 話者の受け止め) に並べ直します。話者が話した順のまま書き言葉に直すと、発言の引き写しになります
4. 選んだ言葉を、伝えたい中身はそのままに、書き言葉に直します。時点も直します。素材は話者がそのとき話したもので、記事は書いた時点から振り返ります。すでにしたことは過去形に揃えます。言いよどみと口癖の程度の語 (`references/voice.md` の「受けと口癖の語の一覧」) を外します。推量と留保の強さ (「〜と思う」「〜かもしれない」) は保ちます。数字で示せない体感は、「数字では示せません」と 1 回断ってから、あとは言い切ります (公開版の形)。受けを段落ごとに重ねると歯切れが悪くなるので、断りは 1 か所にまとめます。具体のある文を削って受けを減らすことはしません (公開版の目安は `references/voice.md` にあります)。話し言葉は 2 つに分けて扱います。曖昧な動作の言い方 (「足したり引いたりした」「いろいろいじった」) は、いつ・何を・どうしたかの事実に置き換えます。対象への評価・比喩・素の反応は、話者の語のまま残します。話者が使った具体の語 (製品やモデルの名前、数字、画面に出た言葉) と言い回しを、一般の言葉の要約に置き換えません。置き換えると、記事が要約に読めます。話者の生活圏の比喩や素の反応は、温度の違う 1 文として記事に 1〜2 か所だけ残します (公開済みの例: 「前って、こんなに変換うまかったっけ」「私は一体何を喋ったんだ」)。方言や崩した口語は、記事の山場の 1 文でなければ書き言葉に寄せます (公開済みの例: 「マインクラフトでもここまでは掘らないだろうと思いました」)
5. 直した文を、骨組みの順に並べます。Claude が足すのは 3 つです。文と文をつなぐ言葉、読者が知らない前提の説明 (1〜2 文)、場面の説明 (いつ・どこで・何をしていたときの話か。素材から分かる範囲) です。この 3 つは惜しまず足します。足さないと、話者の発言を引き写しただけの文章になり、読者は誰が何をしている場面なのか分からなくなります。「出どころの無い文を書かない」は、中身 (描写・数字・気持ち・教訓) を作らないという意味で、読者の道案内を省くという意味ではありません
6. 節ごとの字数を、`outline.yaml` の予算と比べます。粗の節が予算を大きく超えたら、同じことを言い直している文と要約の文を選び直します。「残す」の印の具体は削りません
7. 感想の文の直前に、元になった事実の文があるかを確かめます。無ければ事実を素材から足すか、感想を消します

考えや判断の記事では、書く前に、素材から考えの線を書き出します。最初の問い → 比べたもの・試したこと → 引っかかった事実 → 決めたこと → 数字や次にすること、の順です。本文はこの線に沿って進め、決めたことを並べるだけにはしません。線の途中が素材に無いときは、その所を聞くことにしますが、本文は手元の線で閉じ、抜けが読者に見えない形にします (「〜は、まだ決めていません」と穴を見せない)。結論はこの線の終わりに置き、冒頭で言い切りません。記事は、素材にある具体 (決めた数字、次にすること) で終え、抽象の感想で終えません。

密の場所は長さを気にせず書きます。話者から聞いた材料を全部使います。場面の密は、その場にカメラを置いたように並べます。判断の密は、選択肢 → 退けた理由 (事実や違和感) → 選んだ決め手の順に組みます。粗の場所は最初から 1〜3 行で通過します。

次の 4 つは書きながら守ります。

- 一人称は「私」にします。主語を省いて読める文には足しません
- フック・ファーストで書きます。背景説明から始めません
- 具体を入れます。数字・固有名詞・実際に起きたことです。具体は密の場所に集めます
- 素材に無い描写・数字・発言を作りません。足りなければ、原稿の冒頭に `<!-- 聞く: 〜 -->` を独立した行で残して話者に聞きます。聞くのは、素材と話者の答えに無い事実だけです。素材と答えの外で見つけた事実 (リポジトリの資料、Web のページ、別の発表の演題) を書くときも、出どころを `check.md` に書き、聞くことで確かめます。音声入力の誤変換らしい語は、正しい語が明らかに見えても、推測で直して言い切らず、素材の表記のまま書くか、聞くことにします。合意した芯は変えません。芯の抽象語 (「完成する」) の中身が素材に無いときは、芯を弱めずに中身を聞きます。見出し・フック・骨組みを変えたいときは聞くことにせず、直した案を原稿に入れて `check.md` の「話者に見せる変更」に書きます (キャプションの `*` の中には入れません。消したときに記号だけが残ります)。聞くことは 5 つまでにし、先頭には、芯の抽象語の中身か密を立てる材料 (場面の細部、判断の決め手) を置きます。それ以外 (写真、リンク、表記の確認) は後ろに回します

### 書き終えたら、AI っぽさを点検する

`references/ai-tells.md` の 3 つの層を、上から順に当てます。1 の層 (素材に無いことを書いている) がいちばん重く、文を整えても取り返せません。

### 別のモデルにも書かせる (ターミナルのとき)

話者が頼んだときは、consulting-gemini スキル (agy) で同じ材料から Gemini にも 1 本書かせます。渡すのは、話者の言葉そのまま・芯と骨組み・公開済みの記事 2 本 (文体見本) と、`references/voice.md` の「文の書き方」です。2026-11 に `gemini-3.8-flash-high` で 2 本の題材を書かせて書き手を伏せて比べたところ、どちらでも最下位か下から 2 番目でした。素材に無い描写 (「会場を沸かせていました」) と飾った語が多かったためです。そのため、頼まれなければ書かせません。書かせたときは、2 本を並べ、節ごとに話者の声に近いほうを採り、Gemini の版にも `ai-tells.md` の 1 の層を同じように当てます。studio の中では agy を呼べないので、この手順は飛ばし、返事にそう書きます。

## Phase 5 — 削る

`references/density.md` を開き、そこに書かれた順に実行します。最初に削るのは、出どころの無い文です。次に、前置き・段落末の要約・言い換えの重複・芯の外の節です。

量の目安は 1〜2 割です。残っているのが話者の言葉と密の細部と道しるべ (接続語・文末の受け) だけになったら、目安に届かなくても止めます。削る量は粗から取り、密の場所には手を付けません。密の場所に抽象語が残っていたら、削るのではなく事実に置き換えます。

削り終えたら、見出しごとの字数を並べて波を見ます (`references/somitsu.md` の手順 5)。どのブロックも同じ重さなら、まだ平らです。粗の節が長いときは、要約・言い換え・前置きの文から削ります。「残す」の印の具体と、合意した節そのものは削りません。節が芯を支えていないと見たら、節は残して、落とす案を `check.md` の「話者に見せる変更」に書きます。

本文の字数を、骨組みの予算の合計と比べます。1 割以上超えていたら、言い直し・総評・説明の重なりから削ります (具体は残します)。素材を知らない読者は、短い文と短い記事を最後まで読みます。

削る前と後を並べて、ユーザーに見せます。何をなぜ削ったかを短く添え、見出しごとの字数も一緒に出します。

### 往復

書き上げたら、ユーザーに原稿を読んでもらいます。studio の中では、ユーザーは原稿の画面で段落をその場で直すか、段落を指して話します。指した場所は「指している場所: 段落 3「…」」の形で届き、ユーザーが直した段落は「前の返事のあとに変わったもの」に並びます。ユーザーの直しは上書きしません。

`hokuchi-note` が見つからないときは、リポジトリのルートから `node tools/notes/cli.mjs <サブコマンド> ...` で同じように動きます。このスキルの `hokuchi-note` コマンドは、すべてこの形に読み替えられます。

聴衆役の感想は `~/Hobby/hokuchi-private/notes/<名前>/feedback.yaml` のスレッドに入ります (`para` が段落の番号、`head` が段落の書き出し、記事全体は `"*"`)。`ball: Claude` のスレッドを 1 件ずつ判断します。

1. 直すなら原稿 (`index.md`) を直し、`replies` に `thinking` (考えたこと) と `change` (変えたこと) を足して `ball: none`・`closed: 直した` にします
2. 直さないなら `closed: そのままにした` にして、理由を `thinking` に書きます
3. 返事に「直した n 件・見送った n 件」と、見送った理由を書きます。ユーザーは見送りを戻せます

コメントが構成そのものに及ぶなら、Phase 2〜3 に戻って合意し直します。

## Phase 6 — 検査

検査は 3 つで、lint → 素材との照合 → 直し → 読者役の読み → 直し、の順に通します。照合と読者役を並べて起動すると、読者役が直す前の版を読むので、並べません。どれも、欠点を見つけて直すためのものです。数を合わせるために文を削る道具ではありません。

### 機械で検査する

```
hokuchi-note lint <slug>
```

lint が見るのは、文の長さ、段落の長さ、受けとぼかしの多さ、「〜と思いました」の連続、短文の連打、読点の多さ、話し言葉の程度の語、型どおりの言い回し、共感を求める表現、常体の混ざり方、結びの重さ、漢字率です。原稿の隣に `outline.yaml` があれば、節ごとの字数と予算、粗と密の合計も出します。閾値は公開済みの記事の実測から決めているので、警告は「自分の水準から外れている」という意味です。studio の原稿の画面では、同じ指摘が段落の横に出ます。

warn は、読み直す場所の印です。直し方は中身で決めます。数値を合わせるためだけに、文を切る・つなぐ・削ることはしません。受け・ぼかし・読点・粗密の比率・節の予算は info で、公開版との違いを知らせるだけです。info を消すために、体感を言い切りにしたり、「残す」の印の具体や合意した節を削ったりはしません。info には理由を書く必要もありません。直さない warn は、理由を記録に書きます。ただし、文の中央値 (`sentence-median`) と本文の総量 (`over-total`) の warn は、理由では残さずに直します。素材を知らない読者は、長い文と長い記事で読むのをやめます。検査の直しで説明を足すと長くなるので、Phase 6 の最後の lint でもう一度確かめます。

### 素材と照らして検査する (1 回)

Claude は自分の書いた文の型に気づきにくいです。Agent ツールで、会話の文脈を引き継がない新しいサブエージェントを起動し (fork は使いません)、`references/ai-tells.md`・原稿・素材 (話者の言葉)・`extract.md` (先頭に芯) を渡します。合意した芯・見出し・`point` は、何をどの順で言うかの出どころに数えるよう伝えます。事実・数字・原因の出どころは、素材と話者の答えだけです。頼むのは次の 7 つです。

1. 素材に出どころの無い文 (描写・数字・気持ち・原因・教訓) を、行を引用して挙げる。素材のままではない確定 (誤変換を推測で直した語、素材に無い換算) も挙げる
2. `ai-tells.md` の型に当たる箇所を、型の名前と一緒に挙げる
3. 素材にあったのに原稿から落ちた、温度のある言葉 (素の反応、生活圏の比喩、一段深まる言い直し) と、`extract.md` で「残す」と印を付けたのに原稿に無い具体を挙げる
4. 受けやぼかしが段落をまたいで続いている所と、数字で示せない断りを 2 回以上している所を挙げる
5. 見出しやフックと、その下の本文が食い違っていないか (フックが逆説なら、本編が打ち消していないか)。結論を言うタイトルなら、その結論が冒頭か最初の節で出てくるか (逆説や問いのタイトルは、本編の順で答えればよい)。同じ時期の話を節をまたいで語り直していないか
6. `references/voice.md` の「炎上を避ける」に当たる所が無いか。挙げるのは、所属先とその利用者、特定の個人、属性への否定や揶揄だけです。話者が物や場所や歴史に向けた素の感想 (「マインクラフトでもここまでは掘らない」) は、炎上に数えません
7. 日本語として読みにくい文 (直しのつぎはぎ、主語の入れすぎ、解説調の「〜のです」の重なり、話者が書き手に向けた言葉の写し) を引用して挙げる

指摘は 1 件ずつ判断して直します。直すときは、型を別の型に置き換えず、話者の言葉に戻します。落ちた言葉と具体は戻します。直すときに守るのは「素材に無い中身を足さない」だけです。接続語・前提の説明・場面の説明は、足して直してかまいません。

見出しやフックと本文が食い違ったら、直さずに残すことはしません。先に本文の順を直します。逆説や問いのフックは、読者が先を読む理由なので、結論を言うタイトルに替えるのは最後の手段です。結論を言うタイトルにすると、読者は先を読む理由を失います。フックをタイトルに回し、冒頭を事実で始め、フックへの答えを体験のあとに置くと、両方が立ちます。間につなぎの 1 文 (「振り返ってみると」) を足すのは、直したことになりません。直したことは `check.md` の「話者に見せる変更」に書きます (聞くことにはしません)。

### 読者の目で読んでもらう (1 回)

素材も芯も渡さない読者役のサブエージェントを、studio の中でもターミナルでも必ず 1 回起動します (Agent ツール、fork は使わない)。渡すのは、`readers.yaml` か `personas/` から選んだ読み手のプロフィールと、原稿の本文だけです。聞くのは次の 5 つです。

1. この記事がいちばん伝えたいことは何だと思ったか (1 文)
2. 読みにくかった文を、引用して 3 つまで。どこで読むのをやめたくなったか
3. 誰がどこで何をしている場面か分からなかった段落、知らない言葉
4. 読み終えて覚えている場面、または判断の分かれ目
5. 人に勧めるなら、どう紹介するか。勧めないなら、なぜか

2 と 3 は、その文と段落を直します (説明を足してかまいません)。話者が「書かない」と決めた中身の所でも、言い直しの重なりと読みにくさは直します。1 が芯とずれたときは、原因を 1 つ決めます。密の材料が `<!-- 聞く -->` の答え待ちなら、その聞くことを先頭に置きます。そうでなければ、芯を言う文の位置か節の順を直し、`check.md` の「話者に見せる変更」に書きます。4 が密の節でなくても、1 が芯と合っていれば、記録に書くだけで止めません。

### 直したら

素材との照合と読者役の読みは、1 回ずつです。直したあとに全体を読み直させると、新しい読み手は毎回別の指摘を見つけるので、往復が終わりません。直し終えたら、指摘の一覧を閉じて、冒頭から話者の声で読み上げるつもりで 1 回通して読みます。直したところの継ぎ目、言い直しの重なり、硬い文を整えます (中身は足しません)。そのあと lint をもう一度通し、直した文に素材の出どころがあるかを自分で `extract.md` と照らします。構成を組み直したときだけ、素材との照合と読者役をもう 1 回ずつ通します。

### 検査が通ったと言える条件

次の 4 つがそろったら、Phase 6 は通りです。返事には、どれが通ったかを書きます。

1. lint の error が 0。warn は直したか、直さない理由を記録した
2. 素材との照合の指摘を 1 件ずつ判断し、直したか、直さない理由を記録した。素材に出どころの無い文が残っていない。「残す」の印の具体が原稿にある
3. 読者役の 2 と 3 を直した。1 が芯とずれたときは、原因を直したか、答え待ちの聞くことにした
4. `<!-- 聞く -->` が残っていない (聞くことは素材と答えに無い事実だけで、構成の変更は「話者に見せる変更」に書く)

聞くことが残っているなら、1〜3 がそろった時点で「聞くことの答え待ち」として話者に渡します。答えが来たら、密を書き直し、lint と読者役をもう一度通します。`<!-- 聞く -->` が残っている原稿は、Phase 7 に進めません。Claude が直せる指摘は、直してから渡します。見出し・フック・骨組みを直したときは、直した版を渡して「話者に見せる変更」で戻せるようにします。

記録は、原稿の置き場の `check.md` に次の形で書きます (原稿には書きません)。数は、最終稿にかけた lint の値を写します。読者役の答えは要約せず、そのまま写します。

```
検査の記録:
- 芯: <合意した 1 文>
- lint: error 0、warn 1 (uke-heavy → 残した。受けはどれも体感)
- 節: 冒頭 粗 79/100 字、<見出し> 密 572/予算なし、… 粗の合計 556 字 / 密の合計 572 字
- 素材との照合: 指摘 9 件 (直した 7、直さない 2: 理由)
- 読者役: 芯「〜」、覚えている所「〜」、直した段落 2
- 話者に見せる変更: フックを「〜」から「〜」に (本編が理由を並べるため)
- 通る条件: 1 ○ 2 ○ 3 ○ 4 答え待ち (聞くこと 2)
```

Phase 7 でタイトルを選び直したときも、冒頭と最初の節がタイトルの約束を回収しているかを確かめ直します。

### 聴衆役に読んでもらう (studio)

studio の中では、ユーザーが原稿の画面の「聴衆役の読み」で読み手を選んで頼みます。読み手は `personas/` のプリセットから選び、`notes/<名前>/readers.yaml` に入ります。結果は `reads/` にアンケート 8 項目として残り、段落への感想は `feedback.yaml` のスレッドに Claude 宛てで入ります。読み終わると、studio が感想の判断を頼んできます。

感想は 1 件ずつ判断します。直したら `closed: 直した`、直さないなら `closed: そのままにした` にして、理由を `thinking` に書きます。ユーザーの材料や判断が要るものだけ、`ball: 話者` にして何を決めてほしいかを書きます。「いちばん伝えたいことは何だと思ったか」の答えが芯の 1 文とずれていたら、段落の直しではなく構成 (Phase 3) を疑います。

## Phase 7 — 出す

Phase 6 の通る条件が 4 つともそろっていない原稿 (`<!-- 聞く -->` が残る) は、ここに進めません。

`references/structure.md` を開きます。

1. タイトルを 3 案出します。先頭 25 字に核を置き、内容を隠しません。案は質の違うものにします (`references/structure.md` と `references/interest.md` の 9)
2. タグの案を出します。数と選び方は `references/structure.md` の「タグ」にあります。決めるのは話者です
3. 見出し画像を用意します。1280×670px です。有無で PV とスキ数が変わります。下地は `references/eyecatch.md` に沿って、芯の 1 文からモチーフを 3 案出し、選ばれたものを `bun run eyecatch` で作ります
4. 本文の画像は密の場所に寄せます。枚数の目安は 800 字に 1 枚です。ただし均等には撒きません。スクリーンショットや当時のポストは密の核になります

studio の中では、タイトル 3 案 (`title`)・タグ (`tags`)・名前 3 案 (`slug`)・見出し画像のモチーフ 3 案 (`motif`) を `proposals.yaml` に書きます。ユーザーが公開の画面で選び、モチーフを選ぶと下地を作るよう頼まれます。タイトルの正は原稿の front matter です。本文は公開の画面の「本文をコピー」か、`paste` でクリップボードに入れて、note のエディタに貼ります。見出し・強調・埋め込みの URL 行はそのまま入ります。画像行は `（画像 n/N: ファイル名 ｜ キャプション: …）` に置き換わります。note 側でその行を消して、公開の画面で 1 枚ずつコピーした画像を貼ります。

```
hokuchi-note paste <slug>
```

studio の中では、ユーザーが公開した記事の URL を貼ると、studio が `slugs.json` への追記・取り込み・作品との結びつけ・原稿のフォルダの片付けを行い、公開版と原稿の差から学びの案を頼んできます。学びの案は `proposals.yaml` の `learnings` に書きます (`voice.md` は書けません。ユーザーが採ったものだけを studio が足します)。

ターミナルで進めるときは、公開したら次を回してアーカイブに凍結します。

```
hokuchi-note sync
```

公開日と note key が入った `articles/note/<公開日>-<slug>/` ができます。

公開済みの記事を直すときは、studio で作品を開き、「改稿する」を押します。アーカイブの本文と画像が原稿の置き場に写ります。直したら note の記事を更新し、「note を更新した」を押すと取り込み直します。ターミナルでは `sync` で取り込み直します。アーカイブの `index.md` は生成物なので、直接は直しません。`articles/note/slugs.json` に slug を足しておくと、ディレクトリ名が読める形になります。凍結を確認したら、`~/Hobby/hokuchi-private/notes/<slug>/` は消さずに `~/Hobby/hokuchi-private/trash/<日時>-notes-<slug>/` に移します。

## 振り返り

公開して反応が見えたら、`references/voice.md` の末尾に学びを 1 行足します。いちばん効く材料は、Claude の原稿と公開版の差です。話者が直した箇所を読み、`ai-tells.md` の型に当たるものはそこへ、文体の規範に当たるものは `voice.md` の本文へ、記事の種類の約束は `structure.md` へ畳みます。学びの行が 10 を超えたら、畳む時期です。

数値を測り直すときは、`articles/note/` 全体に lint を回します。

```
hokuchi-note lint
```

公開済み記事が error を出さず、warn が改善余地として出る状態を保ちます。error が出るようになったら、閾値か規範のどちらかがずれています。
