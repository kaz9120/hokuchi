# note を研ぎ澄まして書く

このスキルは、題材から公開までを一本で通す。完成の姿は、`articles/note/drafts/<slug>/index.md` に置かれた原稿と、そこから note に貼って公開された記事。

書き手は Claude、決めるのは人間。Claude が担うのは、芯を1文に絞る手伝い、フックの発見、密にする場所を選ぶこと、そして**削ること**である。

## この 4 つを外さない

1. **読後感は「カフェで聞いた話」。書く姿勢は徹底的にロジカル。** 出てくる文章はカジュアルに見えるが、何を伝えるか・誰に届けるか・どう構成するかは戦略的に設計されている。この二層構造が核
2. **濃度がすべて。** 濃度とは、読者が受け取る発見の量 ÷ 文字数。長い記事は読まれない。短くて薄い記事も読まれない。削って濃くする
3. **密は徹底的に密、粗は思いきり粗。** Claude の初稿は、どの段落にも同じだけ手をかけた、強弱のない文章になる。1 文ずつは欠点がないのに、通して読むと目が滑る。丁寧すぎるのは敵である。密にする場所を 1 つ選んで描き切り、残りは通過する (ADR-0023)
4. **文章は一方向的なもの。** 「私はこう思う」「私はこうした」を書く。共感は求めない。自己開示の結果として生まれるならそれでいい

## 着手前に開くファイル

- `references/voice.md` — 人格と文体の規範。実測値つき。Phase 4 の前に必ず開く
- `references/somitsu.md` — 粗密の付け方。どこを密にし、どこを通過するか。Phase 3 で開き、Phase 4・5 でも手元に置く
- `references/density.md` — 削る技術。Phase 5 の手順書。**このスキルの中心**
- `references/structure.md` — 構成・タイトル・タグ・画像。Phase 3 と Phase 7 で開く
- `references/review.md` — 評価の観点。Phase 6 で開く
- `references/examples.md` — 公開済み 44 本から抜いた実例。Phase 3〜5 で開く

### 実物を読む

`articles/note/` に公開済みの記事 44 本がある。**抽象的なルールより、実物のほうが雄弁である。** 書く前に、題材が近い記事を 2〜3 本読む。

- エッセイ・考えたこと系 → `2026-08-16-tired-of-quick-builds`、`2026-07-26-meeting-ideas-i-lack`
- 技術・やってみた系 → `2026-08-23-rewrite-docs-for-ai`、`2026-08-09-ai-builds-shogi-ai`
- イベントレポート系 → `2026-05-24-tskaigi-2026`、`2026-03-08-emconf-jp-2026`
- 月次振り返り → `2026-08-30-monthly-review`

新しい記事ほど研ぎ澄まされている。2025 年 12 月前後の記事は「本記事では〜ご紹介します」「共感していただけると思うのですが」のような、いま避けたい書き方が残っている。**古い記事は反面教師として読む。**

## 全体の流れ

Phase 0 から 7 まで順に進む。Phase 2 と Phase 3 はユーザーの承認を取る関門で、飛ばすと合意していない芯の上に本文を積むことになる。

Phase 5 (削る) は独立した工程である。書きながら削るのではなく、書き切ってから削る。この順序を崩さない。

**原稿を持ち込まれたときは Phase 5 から入る。** 「見てほしい」「レビューして」は削る作業の依頼だと解釈する。最初に見出しごとの字数を並べ、どこが密でどこが粗かを言い当ててから削り始める。密が見当たらない原稿は、削る前に密の場所を決め直す (Phase 3 の後半)。

## Phase 0 — 題材を受け取る

音声入力の書き起こし、箇条書きのメモ、「これについて書きたい」の一言。どの形で来ても、まず材料を揃える。

- 題材について書いた過去の note があれば読む (`articles/note/`)
- 登壇資料が元になるなら `talks/<slug>/deck.yaml` を読む
- イベントレポートなら connpass ページを WebFetch で読む
- スクリーンショットや図があれば Read で開いて、何が写っているか自分の目で確かめる

ネタ出しの質問はしない。書きたいことはすでにある前提で、整理に集中する。

---

## Phase 1 — 読者と持ち帰り

2 つだけ決める。長く聞かない。文脈から埋まるなら埋めて確認だけ取る。

1. **誰に向けて書くか。** 「エンジニア全般」では広すぎる。「AI でツールを作り始めたが、作って満足して使わなくなっている人」まで絞る
2. **読者に何を持ち帰ってほしいか。** 知識か、視点か、行動か

**候補を出す前に、材料の中を読む。** 書き手はたいてい、材料のどこかで読者に向けた言葉をすでに書いている。とくに**最後の段落**に出やすい。そこを読まずにこちらで読者の候補を作ると、書き手はこちらが用意した枠の中でしか選べなくなる。

2026-09-06「飲食目的での勉強会参加について」では、材料の末尾に「会を面白くて良いものにするのは主催者・運営の責任」と書いてあったのに、読者を「タダ飯扱いされないか不安な参加者」に置いた候補を出した。結果、本題が最後の章に唐突に現れる構造になり、Phase 2 からやり直している。

読者が決まると、説明の量が決まる。読者が知っていることは書かない。知らないことだけ書く。ここが濃度の第一歩である。

---

## Phase 2 — 芯を1文に (関門)

**この記事で言いたいことは何か。1文で書く。**

書けないなら、まだ書く段階ではない。題材が 2 つ以上あるなら記事を分ける。1 記事 1 メッセージ。

芯の 1 文は、次を満たす。

- 主張になっている (「〜について書く」は題目であって主張ではない)
- 自分の体験から出ている (借り物の一般論ではない)
- 読者にとって新しい (自明なことを言っていない)

悪い例: 「AI 開発ツールについて書く」「個人開発の学びをまとめる」
良い例: 「なんでも作れることに価値はない。価値があるのは、作ったものを使い続けられるかどうかだった」

ユーザーに芯の 1 文を提示し、**これでいいか確認を取る。** 承認されるまで Phase 3 に進まない。

---

## Phase 3 — フックと骨組み (関門)

`references/structure.md`、`references/somitsu.md`、`references/examples.md` を開く。

### フックを見つける

冒頭は記事の生死を分ける。時系列で始めない。**一番面白かったこと、自分が引っかかった瞬間を冒頭に置く。**

公開済み記事の冒頭は中央値 41 字。短い。

> 自分が欲しいツールがその日のうちに動く。 最初はそれだけで楽しかった。
> 7月25日の大吉祥寺.pmで、wabiさんがこんな話をしていました。

フック候補を 2〜3 案出して選んでもらう。

### 骨組みを組む

見出しレベルの構成案を出す。分量は `references/structure.md` の 3 つの型から選ぶ。迷ったらショート (800字前後) に寄せる。**短いほうが読まれる。**

骨組みと一緒に、画像の入る位置も置く。X のポストや外部記事の埋め込みは、URL だけの行を 1 行置く。note のエディタに貼るとカードになり、公開後に `sync` が取り込む `index.md` も同じ形になる (ADR-0021)。

### 密にする場所を決める

骨組みの各ブロックに「密」か「粗」と、字数の予算を書き添える。「中」は作らない。**密は見出し 1 つ分。長い記事でも 2 つまで。** 選ぶのは、芯の 1 文を読者が信じる根拠になる場面である。用語の定義、議論の経緯、一般論は密にしない。

**粗にするとは、論点を落とすことである。** 粗のブロックは 150 字までを目安にし、論点は 1 つだけ運ぶ。登壇資料や長いメモが素材のときは、素材が全論点を均等に語っているので、写すと均等な記事になる。何を書かないかをここで決める。

ここを決めずに書くと、全ブロックを均等に丁寧に書くことになる。それが Claude の既定の書き方で、つまらなさの原因である。決め方と実例は `references/somitsu.md`。

密の場所が決まったら、**そこについてだけ**材料を聞く。何が見えていたか、誰が何と言ったか、数字、順番、そのときの感情。密は材料がないと書けず、想像で補うと誰の体験でもない文章になる。粗の場所については聞かない。

ユーザーに骨組みと粗密の割り振りを提示し、**承認を取る。** ここで構成を固めておかないと、Phase 5 で削るときに骨ごと崩れる。

---

## Phase 4 — 書く

`references/voice.md` を開いてから書く。出力先は `articles/note/drafts/<slug>/index.md`。front matter は公開済み記事と同じ形にする。

```yaml
---
title: サクッと作れる楽しさに、飽きた
hashtags:
  - エンジニア
  - 個人開発
---
```

**密の場所は長さを気にしない。** 聞いた材料を全部使い、その場にカメラを置いたように書く。削るのは次の Phase の仕事で、書きながら削ると、削るべきでないものまで削れる。

**粗の場所は最初から短く書く。** 1〜3 行で通過する。あとで削ればいいと丁寧に書くと、削るときに惜しくなり、結局どの段落も同じ重さで残る。

次の 4 つは書きながら守る。守らないと後から直せない。

- **一人称は「私」**
- **フック・ファースト** (背景説明から始めない。冒頭で世界観を丁寧に描くと眠い導入になる)
- **具体を入れる。** 数字・固有名詞・実際に起きたこと。「さまざまな工夫をした」ではなく「レイアウト案を 100 個作らせて 12 個選んだ」
- **具体は密の場所に集める。** 全段落に均等に撒くと、どこも少しずつ具体的で、どこも山にならない

---

## Phase 5 — 削る

**このスキルの中心。** `references/density.md` を開いて、そこに書かれた順に実行する。

目標は明確に置く。**書き上げた原稿から 2 割削る。** 削れないと思ったところから、たいてい 2 割出る。

**2 割は粗から取る。** 密の場所には手を付けない。均等に 2 割ずつ削ると、均等に薄い文章が短くなるだけである。密の場所に抽象語が残っていたら、削るのではなく事実に置き換える。

削り終えたら、見出しごとの字数を並べて波を見る (`references/somitsu.md` の手順 5)。どのブロックも同じ重さなら、まだ平らである。粗と付けたブロックが 150 字を超えていたら、ラベルを付けただけで書き方が変わっていない。論点を 1 つに絞って畳むか、ブロックごと落とす。

削る前と後を並べてユーザーに見せる。何をなぜ削ったかを短く添え、見出しごとの字数も一緒に出す。

### 往復はブラウザで受ける

ここから先の往復は、ターミナルではなく `serve` で受ける (ADR-0022)。書き上げたら立てて、URL を伝える。

```
hokuchi-note serve articles/note/drafts/<slug>/
```

ユーザーはブラウザで文を選び、その場の入力欄に一言書いて Enter で送る。コメントは `drafts/<slug>/feedback.md` に節ごと追記される。ユーザーが「ターミナルに貼る」でまとめて貼ってくるか、「フィードバック見て」と言ってきたら次を回す。

1. `feedback.md` を読む (貼られた本文と同じ内容)。節ごとに、段落番号・見出し・引用した本文・コメントが入っている
2. 原稿を直す。画面は原稿の変更に追従するので、直したら報告するだけでよい
3. **反映した節を `feedback.md` から消す。** ファイルは往復の受け渡し口で記録ではない。残った節が「未反映」として画面に出る

コメントが構成そのものに及ぶなら、Phase 2〜3 に戻って合意し直す。

## Phase 6 — 検査

### 機械で検査する

```
hokuchi-note lint articles/note/drafts/<slug>/index.md
```

文の長さ、段落の長さ、ぼかし表現の密度、型どおりの言い回し、共感を求める表現、結びの重さ、漢字率を見る。閾値は公開済み 44 本の実測から決めてあるので、**警告は「自分の水準から外れている」という意味**になる。`serve` を立てていれば、同じ指摘がサイドバーに出て、クリックで該当段落に飛べる。

warn はすべて潰す努力をする。潰せない理由があるなら、その理由を言えるようにしておく。lint が見ているのは数えられるものだけで、濃いかどうかは見ていない。

### 人が読んで検査する

`references/review.md` の観点で読み返す。特に次の 4 つは lint では拾えない。

- **芯の 1 文が伝わるか。** 読者が読み終えて言い換えられるか
- **フックが効いているか。** 冒頭 3 行で読む気になるか
- **具体があるか。** 抽象語で済ませた箇所はないか
- **どこが密か指させるか。** 読み終えて覚えている場面が 1 つあるか。全段落が同じ重さなら、平らなまま残っている

声に出して読む。カフェで話して違和感があるなら直す。

## Phase 7 — 出す

`references/structure.md` を開く。

1. **タイトルを 3 案出す。** 先頭 25 字に核を置く。内容を隠さない
2. **タグを 3〜5 個。** 主題タグ 2〜3 + ジャンルタグ 1〜2 + note 公式のお題があれば 1
3. **見出し画像を用意する。** 1280×670px。有無で PV とスキ数が変わる
4. **本文の画像は密の場所に寄せる。** 枚数の目安は 800 字に 1 枚だが、均等には撒かない。スクリーンショットや当時のポストは密の核になる

本文は `serve` の画面の「note に貼る本文をコピー」か、`paste` でクリップボードに入れて note のエディタに貼る。見出し・強調・埋め込みの URL 行はそのまま入る。画像行は `（画像 n/N: ファイル名 ｜ キャプション: …）` に置き換わるので、note 側でその行を消して画像を入れる (「assets を開く」で Finder が開く)。

```
hokuchi-note paste articles/note/drafts/<slug>/index.md
```

公開したら、次を回してアーカイブに凍結する。

```
hokuchi-note sync
```

公開日と note key が入った `articles/note/<公開日>-<slug>/` ができる。`articles/note/slugs.json` に slug を足しておくと、ディレクトリ名が読める形になる。凍結を確認したら `drafts/<slug>/` は消してよい。

---

## 振り返り

公開して反応が見えたら、`references/voice.md` の末尾に学びを 1 行足す。うまくいった言い回し、滑った構成、読まれた記事の傾向。**このスキルは 44 本の実測の上に立っているので、記事が増えるほど規範を更新できる。**

数値を測り直すときは `articles/note/` 全体に lint を回す。

```
hokuchi-note lint
```

公開済み記事が error を出さず、warn が改善余地として出る状態を保つ。error が出るようになったら、閾値か規範のどちらかがずれている。
