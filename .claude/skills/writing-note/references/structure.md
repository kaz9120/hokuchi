# 構成・タイトル・タグ・画像

## 分量の型

公開済み 44 本の中央値は 1,365 字。最短 246 字、最長 4,995 字。**迷ったら短いほうに寄せる。**

下の型に書いた行数は総量の目安で、各ブロックに均等に配る数字ではない。密にする 1 ブロックに寄せ、残りは 1〜3 行で通過する (`somitsu.md`)。「本題① 10〜15 行、本題② 10〜15 行」をそのまま埋めると、平らな記事になる。

### ショート (500〜800 字 / 30 分)

書きたいことが 1 つだけあるとき。「とにかく出す」ための型。

```
[見出し画像]
フック（体験・エピソード・問い）   3〜5 行
本題（言いたいこと）              10〜15 行
結び（次のアクション or 一言）     1〜3 行
```

### スタンダード (1,500〜2,500 字 / 1〜2 時間)

テーマを掘り下げたいとき。note の標準。

```
[見出し画像]
フック                            3〜5 行
背景・前提                        5〜10 行
[画像 or 区切り線]
本題① 具体的なエピソード・事実     10〜15 行
[画像]
本題② 考察・学び                  10〜15 行
結び                              1〜3 行
```

### ロング (3,000 字以上 / 3 時間以上)

ノウハウ系・振り返り系。情報量が多いとき。セクションごとに画像を挟む。

```
[見出し画像]
フック                            3〜5 行
この記事で伝えること（1〜2 文）
[画像 or 区切り線]
セクション 1〜3                   各 10〜20 行 + 画像
結び                              1〜3 行
```

## 構成の原則

### フック・ファースト

時系列順 (背景 → 経緯 → 結果) で書かない。一番面白かったこと、自分が引っかかったエピソードを冒頭に置く。そこから本題へ繋げる。

公開済み記事の冒頭は中央値 41 字。

> 自分が欲しいツールがその日のうちに動く。 最初はそれだけで楽しかった。
> 7月25日の大吉祥寺.pmで、wabiさんがこんな話をしていました。
> 3週間前、コンピュータ将棋の開発を Claude Code と再開した話を書きました。

避けたい冒頭 (初期記事に多い):

> 本記事は 〇〇 Advent Calendar 2025 の1日目の記事です。
> MOSHにジョインして、気づけば半年が経ちました。

### 結論 → 背景 → 補足

「背景 → 経緯 → 気づき → 結論 → 余韻」の順で書かない。読者に「で、何が言いたいの？」と思わせたら負け。

### 見出しは言い切る

見出しは平均 18 字。**説明ではなく主張にする。** 見出しだけ拾い読みしても記事が追える状態が理想。

> 「プロジェクトごと」に分けるのをやめた
> 打率は67%から27%に落ちた
> 覚えているのは技術のほうではありません
> 大雨の日に限って、足が向きます

「おわりに」「作ったもの」「〇〇とは」は情報がゼロで、この下に何が書いてあるか分からない。中身を見出しに出す。

### リニアに展開する

大見出し → 中見出しの入れ子を避ける。読者の「なぜ？」を一つずつ消していく。

### 密は 1 つ、残りは通過

骨組みの各ブロックに「密」か「粗」を書く。密は 1 つ、長い記事でも 2 つまで。芯の 1 文の根拠になる場面を密にし、背景・経緯・一般論は粗にする。決め方は `somitsu.md`。

背景を丁寧に積んでから本題に入る構成は、読者が本題に着く前に眠くなる。背景は密を読むのに足りる分だけ、密の直前か途中に置く。

### 結びは短く

3 文以内。まとめ直し・振り返り・抱負は不要。公開済み記事の結びは中央値 44 字。

## タイトル

note は SNS 経由の流入が多い。タイムラインで目に留まるかが勝負。

- **何が書いてあるか 1 秒で分かること。** 内容を隠さない。結論を入れてよい
- **先頭 25 字に核を置く。** SNS や検索結果で省略される
- 固有名詞・数字・具体的なエピソードを含める
- 煽りや釣りは使わない。等身大のトーンを保つ

| パターン | 例 |
|---|---|
| 具体的な体験 + テーマ | Slackの通知を全部切った。フルリモート半年の結論 |
| 言い切り | サクッと作れる楽しさに、飽きた |
| 問い + 主観 | 「仕事」と「好き」の境界線で。今年、コミュニティについて考えたこと |
| 対象 + 意外性 | ドキュメントは、AI に渡す前に作り直す |
| 数字 + スコープ | AIが将棋AIを作る3週間、見えてきた壁 |

避けるもの:

| パターン | 例 | 理由 |
|---|---|---|
| まとめ記事風 | 【完全保存版】エンジニアのためのSlack活用術10選 | 個人 note の温度感と合わない |
| 煽り・釣り | 知らないと損！SNSアカウント名の最強戦略 | ハイカロリー。ブランド毀損 |
| 内容が分からない | 最近思ったこと | クリックされない |

**3 案出して選んでもらう。** 記事の芯の 1 文 (Phase 2) から作ると外れにくい。

## タグ

1 記事あたり 3〜5 個。多すぎると逆効果。3 つの層で構成する。

| 層 | 説明 | 例 |
|---|---|---|
| 主題タグ | 記事のテーマそのもの | エンジニア、個人開発、AI駆動開発 |
| ジャンルタグ | 記事の形式・カテゴリ | エッセイ、イベントレポート、振り返りnote |
| お題タグ | note 公式の募集中のお題に該当する場合 | (公式お題) |

公開済み 44 本のうち 19 本はタグが 2 個以下。**ここは伸びしろがある。** 3 個を下回らないようにする。

note 公式のお題は https://note.com/contests で確認する。

## 画像

- **見出し画像は必ず設定する。** 有無で PV とスキ数が変わる。推奨 1280×670px。大きな造形や色面のあるシンプルなデザインが目に留まる
- **本文中の画像は 800 字に 1 枚を目安。** ただし均等には撒かない。密の場所に寄せる。「サクッと作れる楽しさに、飽きた」は、設定項目が増えていく場面に 2 枚、100 案を並べた場面に 2 枚を集めている
- **画像の役割は 3 種類:** ①内容の補足 (スクリーンショット、図解) ②空気感の演出 (写真) ③区切り
- スクリーンショットや図解は、直後の説明文とセットで置く
- キャプションを付けると画像が語り出す。公開済み記事では 37 枚にキャプションがある

## 埋め込み

X のポスト、外部記事、YouTube、Speaker Deck を本文に埋められる。公開済み記事の中央値は 1 記事 1 個。

- 自分のポストを引くと、そのときの熱量がそのまま入る
- イベントレポートでは connpass ページを埋めると、読者がそのまま辿れる
- 埋め込みは説明の代わりにならない。**何を見てほしいのかを地の文で書いてから置く**
