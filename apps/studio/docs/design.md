# studio の設計

studio は、発表資料と note の記事を、AI と一緒に企画から公開・振り返りまで作るローカルの制作アプリです。CMS に近いものですが、作ったものを管理するより、作る過程を支えることを主にします。この文書は生きた設計書で、試しながら書き換えます。根拠は `research/` にあり、決定の経緯は ADR-0036・0039・0040・0041・0043・0044・0045・0046 にあります。

## 1. 考え方

3 つの調査 (slide:ology、note の本、note 公式の記事 10 本) は、媒体が違っても同じことを言っていました。

- 何を言うかが、どう言うかより先で、比重も大きい
- 書く・作る前に、相手と一言を決める。相手は属性ではなく、名前のある 1 人として描く
- 量を出してから捨てる。最初の案を採らない
- 構成ができるまで、本文やスライドに入らない
- 最後に決めるのは人。AI と機械は、量を出す・抜けを指摘する・数えて検査する側に回る

studio は、この順序を画面の並びにします。もう 1 つ、使いながら決めたことがあります。

- 画面は、話者が読む・決める・書くものだけを出す。Claude が実装を合わせるための情報 (絵の作り方・動きの役割・検査) は、話者の画面に出さない
- AI との対話は、画面に置かない。話者は画面に指摘を書き、Claude Code はファイルを読んで直す。接点はファイルにある (ADR-0038・0040)
- 1 つの面でする仕事は 1 つにする。読み方の違う仕事を、同じ面に同居させない

## 2. 扱うもの

| もの | 中身 | 置き場 |
|---|---|---|
| 作品 | 発表 1 本、または記事 1 本。企画・絵コンテ・指摘・聴衆役の読みを持つ | 企画シートは `~/Hobby/hokuchi-private/works/<id>/brief.yaml`。`talk` に紐づくトークの slug を、`note` に紐づく記事の slug を書く。完成にした作品は `finishedAt` (押した日時) を持つ |
| トーク | 発表 1 本の絵コンテ・シーン・指摘・読み。公開する発表はリポジトリに、非公開 (社内向け) の発表は外に置く (ADR-0041) | `talks/<トーク>/` か `~/Hobby/hokuchi-private/talks/<トーク>/` |
| 絵コンテ | 章 → シーン → コマ。シーンは「伝えること」と「かける時間」、コマは絵と「話すこと」を持つ | `<トーク>/storyboard.md` |
| 指摘 | 1 件の指摘と、その往復 (スレッド)。話者・聴衆役・Claude のどれが書いたものも同じ形 | `<トーク>/feedback.yaml`、記事は `<原稿>/feedback.yaml` |
| 聴衆役の読み | 読み手が 1 回読んだ結果。アンケート 8 項目・自由記述 2 つ・コマへの感想 | `<トーク>/reads/<番号>.yaml` |
| ペルソナ | 聴衆役の「人」。発表でも記事でも使い回すプリセット | `personas/<id>.yaml` |
| 読み手 | この発表を読んでもらうペルソナと、その「場」(なぜここに来たか) | `<トーク>/readers.yaml` |
| 原稿 | 記事 1 本の本文。段落を単位に、指摘と聴衆役の読みを回す (ADR-0046) | `~/Hobby/hokuchi-private/notes/<slug>/` (`index.md`・`assets/`・`feedback.yaml`・`readers.yaml`・`reads/`) |
| ネタ | 作品になる前の種 | `~/Hobby/hokuchi-private/seeds/` |

話者の頭の中にあるのは「KomeKaigi の発表」1 つです。置き場が 2 か所 (企画は公開リポジトリの外、絵コンテは中) に分かれているのは実装の都合なので、画面では 1 つの作品として見せます。非公開 (社内向け) の発表は、絵コンテも外に置きます。社内向けの資料が公開リポジトリに入る道を、置き場の段階で断つためです。studio は両方の置き場を読むので、画面での扱いは変わりません (ADR-0041)。

### 作品の状態

作品の状態は、進み具合と公開範囲の 2 つの軸で持ちます (ADR-0045)。話者の頭の中にある「できたか」と「出したか」の区分に揃えています。

| 軸 | 値 | 決め方 |
|---|---|---|
| 進み具合 | 下書き・完成 | 話者が決める。作品の画面の「完成にする」で企画シートに `finishedAt` を書き、「下書きに戻す」で消す。完成しても編集はできる。公開した作品は完成として扱う |
| 公開範囲 | 非公開・公開 | 実物から決める。発表はサイトに載るもの (`talks/` の `public: true`)、記事は note のアーカイブ (`articles/note/<公開日>-<slug>/`) にあるもの。それ以外は非公開 |

進み具合は行き来できます。登壇の直前に直す、記事を改稿するといった場面があるためです。公開から非公開には戻せません。一度サイトや note に出たものは、リポジトリの履歴や検索に残るためです (ADR-0043)。非公開の発表は、リポジトリの外に置きます (ADR-0041)。

人が書き込むのは進み具合だけです。公開範囲を企画シートに書かないので、書いた状態と実物がずれません。

## 3. 画面

```
ホーム ──→ 発表 ┬ 企画   場・聴衆・聞き終えたあと・伝えたいこと (段階 1〜4)
               ├ 流れ   発表全体を見渡して、順序と時間を決める
               ├ コマ   絵コンテを読んで、話すことを直し、指摘を書く
               ├ 読み   聴衆役に読んでもらい、指摘に返信する
               └ 公開   通して見る。公開・振り返り (これから)

       └──→ 記事 ┬ 企画   書きたいこと・読者・読み終えたあと・芯 (段階 1〜4)
               ├ (構成) 見出しの並びと字数の予算を決める (2 段目で作る)
               ├ 原稿   段落ごとに読んで直し、指摘を書く
               ├ (読み) 聴衆役に記事として読んでもらう (2 段目で作る)
               └ (公開) タイトル・タグ・見出し画像を決め、note に貼る (2 段目で作る)
```

記事のタブは、発表と同じ骨組み (ADR-0046) で、流れが構成に、コマが原稿に当たります。まだ作っていない構成・読み・公開のタブは出しません。押しても何もできないタブは、話者に「何をすればいいか」を迷わせるだけだからです。

作品の画面の上の帯には、種類の横に、進み具合と公開範囲のバッジを 1 つずつ出します (公開したものは「公開」だけ)。タブの右には、次の操作を置きます。

- 下書き: 「完成にする」と「削除」。「完成にする」は押すとすぐ完成になります (戻せるので、確かめる吹き出しは挟みません)
- 完成・非公開: 「下書きに戻す」と「公開の手順」。「公開の手順」は、押すと公開の頼み方を出します。発表は、トークを `talks/` に移して `public: true` にし、デプロイします。手作業とデプロイの確認が要るので、画面からは公開しません
- 公開: バッジだけです。下書きに戻す操作も出しません

「削除」は下書きのときだけ置きます。危険な操作なので、目立たない見た目にし、押すと確かめる吹き出しを開きます (ADR-0044)。「削除する」を押すと、企画シートと、リポジトリの外に置いた紐づくトークを、ごみ箱 (`<HOKUCHI_PRIVATE>/trash/<日時>-<id>/`) に移します。消さずに移すので、間違えても戻せます。ごみ箱の中は、元の置き場と同じ形 (`works/<id>/`・`talks/<トーク>/`) です。リポジトリの中のファイル (`talks/` のトーク・`articles/note/drafts/` の原稿) は git の操作が要るので触らず、吹き出しの中で「リポジトリのファイルは残ります。消すときは Claude Code に頼んでください」と伝えます。ネタの `workIds` からも外し、削除のあとはホームに戻ります。完成した作品と公開した作品は削除できません。サーバも断ります (ADR-0045)。

その下には、「伝えたいこと」と「聴衆」を出し続けます。slide:ology がメッセージマップを常に表示させ、聴衆のプロフィールを資料の冒頭に置くのと同じ考えです (p.36-37, p.39)。聴衆は名前を押すと、どんな人か・悩み・なぜここにいるかが開きます。右端には「Claude に渡す指摘 n 件」が出ます。

各面で、話者がすることを 1 つに絞ります。

| 面 | 読む | 決める | 書く |
|---|---|---|---|
| ホーム | 発表と記事の一覧と、下書きの次にやること | どれを開くか | ネタ |
| 作品の帯 | 進み具合・公開範囲・伝えたいこと・聴衆・Claude に渡す指摘の数 | 完成にするか・下書きを削除するか | — |
| 企画 | 自分が前に書いたこと | 伝えたいこと (確定する) | 段階ごとの欄 |
| 流れ | 発表全体 (シーンのカードと時間の帯) | 順序と、シーンごとの時間 | シーンの「伝えること」、時間 |
| コマ | 絵と話すこと (上から通して) | このコマはこれでいいか | 話すこと、コマへの指摘 |
| 原稿 | 本文 (上から通して) と、段落の横の検査結果・指摘 | この段落はこれでいいか | 本文、段落への指摘 |
| 読み | アンケートの結果と、あなた宛ての指摘 | 指摘にどう答えるか | 返信 |

### ホーム

上から「ネタ帳」と「発表と記事」の 2 つです。ネタ → 下書き → 完成 と、作品ができていく順に上から並べます。

右上には「サイトを開く」と「作成」を置きます (ADR-0044)。

- サイトを開く: 本番 (`https://slides.y-kaz.com/`。`packages/stage/node/talk.mjs` の `SITE`) を開きます。世の中から見えている姿で、サイトに載っているものだけが見えます。studio の中で立てるローカルの開発サーバは、作品の画面のプレビューで使い、ホームからは開きません
- 作成: 押すと「発表」「記事」を選ぶメニューが開きます。2 つに優劣は無いので、ボタンを並べずに 1 つにまとめました

- ネタ帳: 書き留める欄は 1 行に収めます。Enter で書き留め、Shift+Enter で改行します。一覧は公開した記事で長くなるので、ネタ帳を一覧の下に置くと、書き留めるたびに長くスクロールすることになります。毎日開く画面なので、上に置いて小さくしました。書き留めたネタは、欄の下にカードで並びます
- 発表と記事: 企画シートのある作品と、企画シートの無い公開物 (note の記事・サイトに載る発表) を 1 つにまとめます。企画シートが公開物に紐づいていれば 1 枚にします (発表は `talk`、記事は `note`)。企画シートの無い下書きのトークも入ります

一覧の並びは、下書きが上 (触った順)、そのあとに完成したものを日付の新しい順です。種類 (すべて・発表・記事)・進み具合 (すべて・下書き・完成)・公開範囲 (すべて・非公開・公開) で絞り込み、タイトル・タグ・イベントで探せます。絞り込みの数は、ほかの絞り込みと検索を効かせたうえで、その値を選んだときの数です。

カードには、種類と、進み具合・公開範囲のバッジを出します。公開したものは完成なので、「公開」のバッジだけを出します。下書きは「次にやること」を言うカードです。次にやることは、企画が残っていれば企画、絵コンテがあれば、あなた宛ての指摘 → 読んでもらう → コマを読む、の順で決めます。完成したものは、表紙の絵 (発表は表紙のスライド、記事は見出し画像) のカードです。押すと、発表は作品の画面、公開した記事は読む画面が開きます。

### 企画 (段階 1〜4)

左に段階、右にその段階の欄です。★ は、人が「確定する」を押して進む段階です。

| 段階 | 発表 | 記事 | 根拠 |
|---|---|---|---|
| 1. 場と素材を集める / 書きたいことを書き出す | 素材・場 (イベント・持ち時間・会場・公開するか) | 出来事・素材・種類 | slide:ology p.32, 39 / けんすう |
| 2. 聴衆を描く / 読者を決める | プロフィールシート: 名前のある聴衆と 7 つの問い | 読者 1 人と、その悩み | slide:ology p.35-37 / 本 p.126-132 |
| 3. 聞き終えたあと / 読み終えたあとを決める | 行動への呼びかけ、聴衆との関係 | 読後感 | slide:ology p.34-35 / 本 p.636 |
| 4. 伝えたいことを 1 文にする ★ | 中核メッセージを 1 文 | 芯を 1 文 | 鈴木・佐伯・本 p.161 |

AI に頼めること (1 文の案を出す、反論を挙げる、など) は、欄の下に小さく置きます。案や意見が出るだけで、欄は書き換わりません。

### 流れ

slide:ology の「ポストイットを壁に貼って並べ替える」(p.48) とメッセージマップ (p.39) に当たる面です。

- 上の帯は、シーンごとの時間を 1 本に並べたものです。章ごとに濃さを変え、持ち時間を超える所に線を引きます。どの章が厚いかと、収まるかが分かります
- カード 1 枚がシーン 1 つです。最初のコマの絵・名前・伝えること・コマの数・時間を出します。伝えることと時間は、その場で直せます
- 時間は、話すことの字数から見積もります (1 分 300 字)。話者が時間を書くと、それを使います (絵コンテの `粗密:` に入ります)。決めた時間と話すことの量が 15 秒以上ずれると、カードに出します
- カードは、章の中で前後に動かせます。章をまたぐ移動、削る、骨組みの案を比べる、はまだありません

### コマ

絵コンテ用紙と同じ、縦の並びです。1 行が 1 コマで、左に絵、真ん中に話すこと、右の余白にそのコマへの指摘を置きます。

- 左のレールは目次です。あなた宛ての指摘があるシーンに、数を出します
- 話すことは、その場で直して欄の外を押すと、絵コンテに保存されます
- 絵を押すと、その絵に変わる動きを大きく再生します。← → で前後のコマ、Esc で閉じます
- 絵の作り方 (絵コンテの「画面の説明」) は Claude への指示なので、既定では出しません。絵がまだ無いコマと、レールの下の切り替えを入れたときだけ出します
- 右の余白は、あなた宛ての件・あなたが書いた件・聴衆役の感想 (詰めて表示)・解決済み (畳む) の順です。「コマに指摘を追加」は何度でも押せます。話す内容でも、スライドの見た目でも、同じ所に書きます

studio という道具そのものへの意見は、右下の agentation で書きます (ADR-0032)。

### 原稿 (記事)

記事の「下書き」を読んで磨く面です (ADR-0046)。発表のコマの面と同じく、上から通して読み、気になった所でその場で直すか、指摘を書きます。

誰が・何を・どう使うか:

- 読むのは話者です。読者と同じ順で本文を頭から読み、「この段落はこれでいいか」を決めます。決め方は 3 つで、その場で直す・指摘を書いて Claude に渡す・そのままにする、です
- 書くのは本文と指摘です。本文は段落の欄を直して欄の外を押すと、`index.md` に書き戻します。front matter (タイトル・タグ) には触りません
- 機械の検査 (`hokuchi-note lint`) は、人の指摘と並べますが、混ぜません。検査は直せば消える目印で、返信も閉じる操作もありません

並べ方:

```
┌ 目次 ──┬ 記事全体: タイトル・字数・段落・文の中央値 ─────┬ 記事全体への検査・指摘 ┐
│ 見出し │ ¶1 本文 (その場で直せる)                       │ ¶1 の検査・指摘        │
│ 見出し │ ## 見出し                                     │                       │
│  …    │ ¶2 本文                                        │ ¶2 の検査・指摘        │
└───────┴──────────────────────────────────────────────┴───────────────────────┘
```

- 左は見出し (##・###) の目次です。押すとその見出しへ移り、あなた宛ての指摘がある見出しには数を出します
- 真ん中は本文で、段落 1 つが 1 行です。幅は note の本文に近い読みやすさを優先し、コマの面の「話すこと」と同じ大きさの文字にします。見出し・画像・埋め込み・コードも同じ並びに出し、元の Markdown のまま直せます
- 右は、その段落への検査と指摘です。検査が上で、指摘のスレッドが下です。指摘の並べ方 (あなた宛て → Claude 宛て → 聴衆役の感想 → 解決済み) はコマの面と同じです
- いちばん上の帯は記事全体です。段落に寄せられない検査 (ぼかし表現の率・漢字の率・タグの数など) と、記事全体への指摘をここに出します

コマの面との違い:

| | コマ | 原稿 |
|---|---|---|
| 単位 | シーン → コマ | 見出し → 段落 |
| 左の列 | 絵 | (無い。本文を広く取る) |
| 直すもの | 話すこと | 本文そのもの |
| 右の余白 | 指摘 | 検査と指摘 |
| 位置の持ち方 | シーンの id とコマの番号 | 段落の番号と、段落の書き出しの文字列 |

段落の番号は、本文を直すとずれます。指摘は書き出しの文字列も持っているので、番号がずれても書き出しで付け直します。付け直せない指摘は、記事全体への指摘に寄せます。画面で段落を直したときは、その段落の指摘を新しい書き出しで持ち直します。

原稿がまだ無い記事では、この面に「原稿を作成」を置きます。slug (`notes/<slug>/` と、公開後の `articles/note/<公開日>-<slug>/` の名前) を決めると、企画のタイトルを入れた `index.md` を作り、企画シートの `note` に書きます。

### 読み

slide:ology の「同僚に見せて、要点を押さえているかを評価してもらう」(p.54) に当たる面です。

- 「読んでもらう」を押すと、読み手がいまの絵コンテを読みます。読み手は毎回まっさらで、渡すのはペルソナ・場・絵コンテの画面と話すことだけです。数分かかります。自動では読ませません
- アンケートは 8 項目で、5 段階と理由 1 行です。行を選ぶと、その項目に付けた理由が読めます。最初は、いちばん点の低い項目を開いておきます。2 回目からは、前回との差を出します
- 「いちばん伝えたかったことは何だと思ったか」を、話者の「伝えたいこと」と並べます
- その下に「あなた宛ての指摘」の一覧があります。返信するか、閉じるかを、ここで済ませられます

画面には「聴衆役の読み」と明記します。AI が演じる聴衆で、本物の聴衆ではありません。

## 4. 指摘のスレッド

1 件の指摘と、その往復を 1 本にします。見るのは 2 つだけです。

| 項目 | 値 | 意味 |
|---|---|---|
| `ball` | 話者 / Claude / none | いま誰が動く番か |
| `closed` | 直した / そのままにした / 良かった点 / 読み直した | 済んだ件の終わり方 |

画面の言葉は、`ball: 話者` が「あなた宛て」、`ball: Claude` が「Claude 宛て」です。`closed` は、直した が「解決」、そのままにした が「見送り」、読み直した が「再読済み」と出ます。

- 話者ができるのは 3 つです。書く (Claude の番になる)、返信する (Claude の番になる)、閉じる (「解決する」は直した、「見送る」はそのままにした)。状態は選びません
- Claude ができるのも 3 つです。直して閉じる、直さずに閉じる、話者に確かめる (話者の番にする)。`replies` に、考えたこと (`thinking`) と変えたこと (`change`) を足します
- 聴衆役の感想は、読みを取り込むときにスレッドになり、Claude の番から始まります。良かった点は、済んだ件として残します。次に読んでもらうと、Claude の番のまま残っていた聴衆役の感想は「読み直した」で閉じます。話者の番の件は残ります
- Claude へは、上の帯の「Claude に渡す指摘 n 件」から渡します。依頼文は「feedback.yaml に Claude の番の指摘が n 件ある。読んで直して」という短い文で、ターミナルの Claude Code に貼ります

## 5. 聴衆役のアンケート

項目は、聴衆を知る 7 つの問い (slide:ology p.35) を裏返したものと、うまくいったかの見分け方 (p.269) から作っています。調査は `research/audience-survey.md` にあります。

| 群 | 項目 |
|---|---|
| 届いたか | 得に来たものを得られた / 自分の悩みに触れていた / 新しい見方を得た |
| 分かったか | 話の筋を最後まで追えた / 画面はひと目で分かった |
| 動くか | 主張に納得した / 明日やってみようと思うことがある |
| 総合 | 同じ立場の人に勧めたい |

ペルソナは「人」と「場」に分けます。人 (どんな人か・悩み・知っていること・引っかかりやすい点・話し手を知っているか) は `personas/` のプリセットで、発表でも記事でも使い回します。場 (なぜここに来たか) は `readers.yaml` に、作品ごとに書きます。

## 6. 画面の言葉

画面の言葉は、`ユーザーの問題解決とプロダクトの成功を導く エンジニアのためのドキュメントライティング` に沿って書きます。

- 知識の呪いを避ける。書き手 (Claude) が本や実装で覚えた言葉 (「種」「関門」「中核メッセージ」「状態」「粗密」「未対応」) を、そのまま画面に出さない。本を読んでいない人が、読んですぐ分かる言葉にする
- ボタンは、押すと何が起こるかを動詞で言う (「最初から再生」「読んでもらう」「依頼文をコピー」)。造語を作らず、一般的な Web サービスで同じ操作を呼ぶ言葉を選ぶ (「完成にする」「下書きに戻す」「追加」「送信」「キャンセル」)。用語は「作品・発表・記事」「シーン・コマ」「指摘・感想・返信」「あなた宛て・Claude 宛て・解決済み」に揃える
- 数には、何の数かを付ける (「あなた宛ての指摘 11 件」)。「残り」「未対応」のような、主語の無い言葉を使わない
- 絵コンテの単位は、シーンとコマで呼ぶ。「場面」は使わない。実装の言葉 (状態・トーク) は出さない
- 最初に読まれる所に、いちばん大事なことを置く。段階の冒頭に「やること」、その下に「なぜやるのか」、欄ごとに「何を書くか」と「例」を出す
- 例は、話者の過去の作品から引けるものは引く。作品に無い例は、ただの「例」として書く
- 本の考え方を言い換えたときは、出典を添える
- 文字は、shadcn/ui の既定より一回り大きくする (根の大きさを 112.5%)

## 7. 技術

- UI は shadcn/ui をそのまま使う (Tailwind v4)。studio は管理画面なので、hidoko のデザインシステムには乗らない。画面の系統は 1 つにする
- 絵コンテの読み書きは `packages/stage/node/storyboard.mjs` が持つ。話すこと (`replaceNotes`)、シーンの情報 (`replaceSceneMeta`)、並び (`moveScene`) を、Markdown のまま書き換える
- 指摘は `threads.mjs`、聴衆役の読みは `readers.mjs` が持つ。YAML は、人が読めて AI も直せるように、文書のまま開いてコメントと並びを保って書き戻す
- 聴衆役は `claude -p` の単発の依頼で、答えを JSON で受け取る。リポジトリの文脈 (CLAUDE.md) を拾わないよう、一時ディレクトリで起動する
- 発表の絵と再生は、サイト全体の開発サーバ (`apps/slides/site-server.mjs`) を使う。studio が中で立てる。トークは起動時に拾うので、トークを足したら studio を起動し直す
- studio は `startSite` に `<HOKUCHI_PRIVATE>/talks/` を足して渡し、非公開のトークも読む。そこのトークは非公開として扱い、開発サーバの一覧には非公開の印付きで出る。`bun run dev` とサイトの組み立て (`apps/slides/build.mjs`) は、`talks/` だけを読む (ADR-0041)
- 画面と Claude への依頼文に出すトークの場所は、リポジトリの中なら相対パス、外なら絶対パスにする
- 作品のタブと場所は URL のハッシュに持つ (`/works/<id>#koma/<シーン>`・`/works/<id>#draft/<段落>`)。agentation のメモが場所ごとに分かれる
- 原稿の読み書きは `draft.mjs` が持つ。本文を空行で段落に分け (コードの囲みは 1 つにまとめる)、段落の位置で書き換える。保存のときは、画面が読んだときの段落と今の段落が同じかを確かめ、違えば保存しない (Claude Code が同時に直したときに上書きしないため)
- 原稿の検査は `tools/notes/src/lint.mjs` の `lintDraft` をそのまま使う。検査結果の `at` (本文の抜粋) を含む段落に寄せ、寄せられないものは記事全体に出す
