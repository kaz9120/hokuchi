# studio の設計 (v0)

studio は、発表資料と note の記事を、AI と一緒に企画から公開・振り返りまで作るローカルの制作アプリです。CMS に近いものですが、作ったものを管理するより、作る過程を支えることを主にします。この文書は生きた設計書で、試しながら書き換えます。根拠は `research/` にあります。

## 1. 考え方

3 つの調査 (slide:ology、note の本、note 公式の記事 10 本) は、媒体が違っても同じことを言っていました。

- 何を言うかが、どう言うかより先で、比重も大きい
- 書く・作る前に、相手と一言を決める。相手は属性ではなく、名前のある 1 人として描く
- 量を出してから捨てる。最初の案を採らない
- 構成ができるまで、本文やスライドに入らない
- 最後に決めるのは人。AI と機械は、量を出す・抜けを指摘する・数えて検査する側に回る

そこで studio は、チャットを入口にしません。段階ごとの画面 (欄・カード・チェックリスト) を入口にし、AI は各段階で「頼めること」として横に置きます。人が欄を埋めて関門を通り、AI は候補・講評・検査で支えます。

## 2. 扱うもの

| もの | 中身 |
|---|---|
| 作品 | 発表 1 本、または記事 1 本。企画シートと段階の進み具合を持つ |
| ネタ | 作品になる前の種。出来事・なぜそう感じたか・どんな悩みにつながるか。発表にも記事にもなる |
| 公開済み | 公開した発表と、note の記事 (いまは 52 本)。改稿すると、新しい作品として段階をやり直せる |

## 3. 段階

発表と記事で骨組みを揃え、欄の中身だけを変えます。どの段階にも戻れます (slide:ology p.30-31 の反復)。★ は人が通す関門です。

| 段階 | 発表 | 記事 | 根拠 |
|---|---|---|---|
| 1. 種 | 素材・場 (イベント・持ち時間・会場・公開するか) | 出来事・素材・種類 (情報・日記・主張) | slide:ology p.32, 39 / けんすう |
| 2. 相手 | プロフィールシート: 名前のある聴衆と 7 つの問い (複数可) | 読者 1 人と、その悩み・いま知っていること | slide:ology p.35-37 / 本 p.126-132 / 白水・佐伯 |
| 3. ゴール | 行動への呼びかけ、聴衆との関係 | 読後感・読者にどうなってほしいか | slide:ology p.34-35 / 鈴木・本 p.636 |
| 4. 一言 ★ | 中核メッセージを 1 文 | 芯を 1 文 | 鈴木・佐伯・本 p.161 |
| 5. 発散と取捨 | アイデアカード (5 案以上出してから選ぶ) | 材料 (エピソード・数字) に、使う・捨てるの印 | slide:ology p.46-48, 60 / 佐伯・鈴木 |
| 6. 構成 ★ | メッセージマップ → 絵コンテ | 冒頭 (一番面白い所) を固定 → 箇条書きの流れ。型を選べる | slide:ology p.39, 48 / 村井・本 p.167 |
| 7. 制作 | シーンの実装 (いまの編集画面) | 執筆 | |
| 8. 見直し ★ | 機械の検査 + 人のチェック (3 秒で読めるか、1 場面 1 アイデア) | 機械の検査 + 人のチェック (冒頭は一番面白いか、「よく書けた」と思えるか) | slide:ology p.160, 256 / 村井・本 p.634 |
| 9. 公開 | 公開の可否・OGP・ノートの仕上げ | タイトル案 (複数)・タグ・見出し画像・公開前の仮説 | 本 p.213-218 / 鈴木 |
| 10. 振り返り | リハーサルの記録 (3 つの R)・当日の反応 | 仮説と結果を並べる。シェアの言葉 | slide:ology p.241 / 鈴木 |

一言 (4) と相手 (2) は、決めたあと全段階の画面の上に出し続けます。slide:ology がメッセージマップを常に表示させるのと同じ考えです (p.39)。

## 4. 画面

- ホーム: 進行中の作品 (段階の進み具合つき)・ネタ帳・公開済み (発表と note の記事を一覧し、検索できる)・新規作成 (発表 / 記事 / ネタから始める)
- 作品の画面: 左に段階の一覧 (未着手・進行中・通過)。中央に段階の画面 (欄・カード・チェックリスト)。右に AI の欄 (その段階で頼めることのボタンと、自由なチャット)。上に一言と相手
- 公開済みの記事: note 風に描画して読める。「改稿する」で作品を作り、段階の途中 (たとえば見直し) から始められる

## 5. AI に頼めること (段階ごと)

| 段階 | 頼めること |
|---|---|
| 相手 | 7 つの問いの抜けを指摘する。反発を予測する |
| 一言 | 候補を 2〜3 案出す。主張になっているか、自明でないかを講評する |
| 発散と取捨 | 案を増やす。陳腐な比喩を指摘する。捨てる候補を挙げる |
| 構成 | 冒頭の候補を比べる。読者が抱く疑問を順に挙げる |
| 見直し | 機械の検査を回す。同僚役として講評する |
| 公開 | タイトル案・タグ案を出す |

AI の出したものは候補として欄の横に並び、人が選んで欄に入れます。欄を直接書き換えるのは人だけにします (案。試して決める)。

## 6. 技術

- UI は shadcn/ui をそのまま使う (Tailwind v4)。studio は管理画面なので、hidoko のデザインシステムには乗らない
- 作品の企画シート (`works/<id>/brief.yaml`) とネタ帳 (`seeds/<id>.yaml`) は、公開リポジトリの外の置き場 (既定は `~/Hobby/hokuchi-private`) に置く。人が読めて、AI も直せるように YAML にする (ADR-0036)
- AI に頼めることは `claude -p` の単発の依頼で、候補を JSON で受け取って企画シートに残す (`ai.mjs`)
- 発表のプレビューと撮影は、サイト全体の開発サーバ (`apps/slides/site-server.mjs`) を使う

## 7. 決めたこと (ADR-0036)

- 置き場はリポジトリの外に分ける。公開するときに、リポジトリの中へ移す
- 関門は、通る前でも次の段階を開ける。代わりに、一言が決まっていなければ警告を出し続ける

## 8. 試作の進み具合と、決まっていないこと

v0 で作ったのは、ホーム (進行中・ネタ帳・公開済み) と、作品の画面の段階 1〜4、公開済みの記事の閲覧まで。

- 段階 5〜10 の画面
- 公開済みの記事の改稿の手順。調査した資料には、体系的な手順がなかった。いまの案は、記事を作品として写し、見直しの段階から始める形
- 作品を公開するときに、置き場からリポジトリ (`talks/`・`articles/note/drafts/`) へ移す手順
- いまある発表 (Dev's Garden) を、作品の段階にどう載せるか。いまは公開済みとして並べ、前からの編集画面で開く
