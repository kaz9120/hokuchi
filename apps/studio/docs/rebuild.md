# studio の作り直し

- ステータス: 合意 (2026-10-20。ADR-0049。作り直しの作業の計画書として使い、終わったら design.md に畳む)
- 日付: 2026-10-20
- 根拠: `research/2026-10-19-rebuild-architecture-audit.md` (作りの棚卸し)・`research/2026-10-19-rebuild-ux-audit.md` (使い心地の棚卸し。画面 53 枚)

## 1. なぜ作り直すか

話者の評価は「つぎはぎ感があって、微妙に使いづらい。この使いづらいシステムだと実装もやばそう」だった (2026-10-19)。機能は良いので、いまの機能を正として、骨組みから作り直す。

2 つの棚卸しは、同じ原因に行き着いた。作品を表す骨組みが無いことである。

- 作りの側: 作品の中身が 4 か所 (企画シート・トーク・原稿・アーカイブ) に分かれ、slug の文字列で紐づいている。状態の判定はサーバ 3 か所と画面 3 か所に散り、発表と記事の処理は 2 本ずつ書かれ、`kind` の分岐が 37 か所ある。`server.mjs` は 702 行で、リクエストの処理は 250 行の if の連なりである
- 使い心地の側: 作品の画面の帯 2 段に 15 種類の要素が詰まり、1280 幅ではタイトルが 3 文字しか見えない。ナビが 3 つあり、指摘の件数は 2 か所に別の数字で出る。状態ごとに帯の右の中身が 5 通りある

## 2. 守るもの

作り直しても、次の 3 つは変えない。

- 機能。作りの棚卸しの 1 章の一覧が仕様の正である。作り直しで機能を落とすときは、話者に確かめる
- ファイルの形。`brief.yaml`・`storyboard.md`・`feedback.yaml`・`readers.yaml`・`reads/`・`outline.yaml`・原稿の `index.md`・`personas/`・アーカイブ。skill と Claude Code が同じファイルを直接読み書きするので、形を変えると skill が壊れる (作りの棚卸しの 6.2)
- 振る舞いの規則。段落の数え方・指摘の付け直し・読みの取り込み・削除と改稿の規則など (同 6.3)

これらを先にテストで固定してから、作り直す。

## 3. 言葉

画面の言葉とコードの名前を、1 対 1 で決める。コードの中でも、同じものを違う名前で呼ばない。

| 画面 | コード | 意味 |
|---|---|---|
| 作品 | `Work` | 発表 1 本、または記事 1 本 |
| 発表・記事 | `kind: talk / note` | 作品の種類 |
| 企画 | `Brief` | 企画シート (`brief.yaml`) |
| 下書きの全体 (流れ・構成) | `Outline` | 発表の流れ、記事の構成 |
| 下書きの単位 (コマ・段落) | `Unit` | 発表のコマ (シーン + 状態)、記事の段落 |
| 中身 | `Body` | 発表の絵コンテとシーン、記事の原稿 |
| 指摘 | `Thread` | `feedback.yaml` の 1 件 |
| 聴衆役・読み | `Reader`・`Read` | AI が演じる聴衆と、その読みの結果 |
| 状態 | `WorkState` | 進み具合・公開範囲・改稿中から導く、画面の 1 語と押せる操作 |

コマの番号は、画面もコードも 1 始まりにそろえる。ごみ箱の名前は `<日時>-<何を>-<id か slug>` の 1 通りにする。

## 4. 作品のモデル

作品を、サーバの中で 1 つの実体にする。読み込むと、企画シート・中身・アーカイブ・指摘・読みが 1 つにまとまる。

```
Work
  id, kind
  brief        企画シート (無い作品もある。企画の無い公開済みの発表・記事)
  body         中身。発表は TalkBody (絵コンテ・シーン)、記事は NoteBody (原稿・構成)
  archive      公開済みの記事のアーカイブ (記事だけ)
  threads      指摘
  reads        読みの結果
  state        導いた状態 (下の表)
```

### 4.1 状態は 1 か所で導く

進み具合・公開範囲・改稿中の判定と、その状態で押せる操作を、サーバの 1 つの関数 (状態の表) にまとめる。画面は結果を表示するだけにし、判定を持たない。

| 状態 (画面の 1 語) | 条件 | 押せる操作 |
|---|---|---|
| 下書き | 公開でない・`finishedAt` が無い | 完成にする・削除 |
| 完成 | 公開でない・`finishedAt` がある | 下書きに戻す・公開の手順 |
| 公開 | サイトに載る・アーカイブにある | 改稿する (記事) |
| 改稿中 | 公開で、改稿の原稿がある | 改稿をやめる |

データは ADR-0045 の 2 つの軸のままにし、画面では 1 語に畳む (話者が決めた。9 章)。社内向けの完成は「完成（社内）」のように添える。

### 4.2 正を 1 つに決める

同じ意味の値に正が複数あるところを、決め直す。

| 意味 | 正 | 写すもの |
|---|---|---|
| タイトル | 中身があれば中身 (発表は talk.tsx、記事は原稿の front matter)。無ければ企画シート | 企画シートの `title` に写す |
| 伝えたいこと | 企画シートの段階 4 | 絵コンテの `中核メッセージ:` は Claude が写す |
| 聴衆 | 企画シートの段階 2 で描いた人 | 読み手 (`readers.yaml`) は、その人とプリセットから選ぶ |
| 公開範囲 | 実物 (ADR-0043) | 企画の「公開しますか」は意図として残し、実物と食い違ったら知らせる |

### 4.3 発表と記事の違いは、媒体の部品 1 つに寄せる

発表と記事で同じ流れを通し、違うところだけを媒体の部品 (`media/talk`・`media/note`) に寄せる。部品が持つのは、次のものだけである。

- 中身の読み書き (絵コンテとシーン / 原稿と構成)
- 下書きの単位と位置 (コマ: シーン + 状態 / 段落: 番号 + 書き出し)
- 聴衆役に渡す文とアンケートの項目
- 公開の確かめる項目と依頼文
- 縮小画像 (発表だけ)

`kind` の分岐は、この部品の選び分けの 1 か所だけにする。

## 5. サーバの構造

```
apps/studio/
  server/
    main.ts        起動
    http/          ルーティングと、薄いハンドラ (入力の検査・ドメインを呼ぶ・返す)
    domain/        作品・状態・指摘・読み・ネタ・ごみ箱。ファイル形式の読み書きはここだけ
    media/         talk.ts・note.ts (4.3 の部品)
    infra/         ファイルの読み書き (版つき)・監視・購読 (SSE)・claude の呼び出し・撮影
  shared/          画面とサーバで共有する型 (API の契約)
  ui/
```

- TypeScript にする。Node 22 の型の取り除き (`--experimental-strip-types`) で動かし、ビルドは要らない。画面とサーバで `shared/` の型を共有し、型検査に studio も入れる
- 書き込みは、全部のファイルで「読んだ版と違えば保存しない」にそろえる。Claude Code と画面が同じファイルを直すので、どちらの書き込みも消えないようにする。いまは原稿の段落だけがこうなっている
- 購読は作品ごとにする。作品を開いているあいだだけ監視と撮影の作業場を動かし、閉じたら止める。ホームにも変更を知らせる。トークのサイトのサーバは、開いたときに立てる (いまは起動時に全部立てるので、トークを足すと再起動が要る)
- 依頼文 (Claude に渡す指摘) は短くし、作法は skill の側に書く

## 6. 画面の構造

使い心地の棚卸しの 3 章の提案を骨組みにする。

```
┌──────────────────────────────────────────────────────────────────┐
│ ← 作品一覧   AIに任せられるのは、磨いてきたものだけ          下書き  ⋯ │  帯 1 行
├─────────────┬────────────────────────────────────────────────────┤
│ 伝えたいこと  │                                                    │
│ 聴衆         │                                                    │
│             │                                                    │
│ ✓ 企画       │                 面 (企画 / 流れ・構成 / コマ・原稿 /     │
│ ● 流れ 29:40 │                     読み / 公開)                     │
│ ○ コマ       │                                                    │
│ ○ 読み       │                                                    │
│ ○ 公開       │                                                    │
│             │                                                    │
│ あなた宛て 11 │                                                    │
│ Claude へ 45 │                                                    │
│             │                                                    │
│ KomeKaigi    │                                                    │
│ あと 12 日   │                                                    │
└─────────────┴────────────────────────────────────────────────────┘
```

- 帯は 1 行にする。戻る・タイトル・状態・「⋯」。状態ごとの操作は「⋯」の中に、押せるものだけを出す
- 左のレールに、芯 (伝えたいこと・聴衆)・工程 (面の並びと、面ごとの数字)・受け渡し (あなた宛て・Claude へ)・場 (イベント・日付) を置く。ナビはこの 1 つにする。企画の段階 1〜4 は、工程の企画の子として畳む
- 公開済みの記事の読む画面と、作品に紐づかない発表の画面は、作品の画面に吸収する。公開済みの記事は「原稿」の面で読むだけの状態として出し、「改稿する」で同じ面が直せる状態になる
- 指摘は「余白で書く・受信箱で裁く・レールから 1 手で渡す」の 1 本にする。指摘のカードは行の高さを変えない (Google ドキュメントのコメントの置き方)。「指摘を書く」は、行にカーソルを乗せたときだけ出す
- 聴衆役の感想は、読んでもらった直後に話者がざっと見て、まとめて Claude に渡す
- 「まだ」と「間違い」の色を分ける。未設定は灰色にし、赤や橙は話者が決めた値と食い違ったときだけにする
- 実装の言葉 (slug・ball・絶対パス) を画面に出さない。原稿の slug は、企画のタイトルから決める
- 画面の土台に、ルータと、作品ごとのデータの層 (取得・購読・楽観的な更新) を最初に置く

ホームは、上を「いま」(下書き・完成・改稿中)、下を「積み上げ」(公開。月で区切る) にする。ネタは帯の 1 行で書き留める。

## 7. 見た目の系統

中立のまま (shadcn の既定の系統) にする。使い心地の棚卸しは、左のレールを夜の闇にし ember で灯す案を出したが、話者は中立を選んだ (9 章)。design.md 7 章の「hidoko のデザインシステムには乗らない。画面の系統は 1 つにする」はそのまま残す。手触りは、色ではなく骨組み・余白・字の大きさ・動きで出す。

## 8. 進め方

ブランチ `studio-rebuild` で作る。main の studio は、作り直しのあいだも使える。

| 段 | すること | 確かめ方 |
|---|---|---|
| 0 | ファイル形式と振る舞いの規則を、テストで固定する | いまの実装で通ることを確かめる |
| 1 | サーバを作り直す (作品のモデル・状態の表・媒体の部品・版つきの書き込み・作品ごとの購読) | 段 0 のテストが通る。いまの画面が新しい API で動く範囲は動かす |
| 2 | 画面の骨組み (帯・レール・面・「⋯」・ルータ・データの層) と見た目の系統 | 写しの studio で全画面を操作して撮る |
| 3 | 指摘の導線 (受信箱・余白・1 手の受け渡し・聴衆役の感想の扱い) | 同上 |
| 4 | 発表と記事の作法をそろえる (読み手の選び方・公開の面の型・slug を出さない) | 同上 |
| 5 | ホーム (いま・積み上げ) | 同上 |
| 6 | 言葉と空の状態の総点検 (Gemini も通す)・設計書・ADR・skill の追従 | 文言の対応表 |

各段の終わりに、写しの studio で撮った画面を話者に見せる。確かめは、いつも `HOKUCHI_PRIVATE` を写しに向けた studio で行い、本物の hokuchi-private とアーカイブには触らない。段 6 のあとに main へ取り込む。

## 9. 話者が決めたこと

話者が決めたこと (2026-10-20)。

1. 見た目の系統: 中立のまま。ブランドの色は持ち込まない
2. 状態の見せ方: 画面で 1 語 (下書き・完成・公開・改稿中) に畳む
3. ホーム: 「いま・積み上げ」に分ける
