# ADR-0001: スライドは意図宣言型 YAML スキーマで記述する

- ステータス: 承認
- 日付: 2026-07-04
- スコープ: presentation

## 文脈

Marp や Slidev のような Code to Slide ツールは、テキスト中心のスライドでは有効だが、図の挿入やレイアウトの工夫で表現力の限界に達しやすい。根本原因は、Markdown が文書の記法であり、スライドというメディアのセマンティクス（配置・関係・強調）を持たないことにある。表現力と「スライドとしての正しさ」（slide:ology の原則への準拠）を両立する記述形式を決める必要があった。

書き手は Claude を想定する。スキルが人間との対話で聴衆・メッセージを深掘りし、YAML を生成する。人間の仕事は `idea` と `notes` のレビュー。

## 選択肢

1. **Markdown 拡張 (Marp 路線の強化)** — front-matter とディレクティブで意図を注釈する。既存資産と手書きの書き味は最良。しかし本文が Markdown フローである限り、レイアウトと図は「本文の外の注釈」になり二重管理が発生する。根本原因に触れない対症療法
2. **YAML 宣言スキーマ** — 書き手が意図（何を伝えたいか・要素同士の関係）を宣言し、レンダラが配置を導出する。JSON Schema による検証・lint・LLM 生成との相性が良い。弱点は人間が手書きする際の書き味
3. **コンポーネント DSL (Slidev/JSX 路線の徹底)** — 表現力の上限は最も高いが、自由度が高すぎて正しさを静的に保証しにくく、規律が書き手のスキルに依存する
4. **2 のスキーマ + 既存ツールへのコンパイル** — スキーマは 2 で定義し、レンダラは HTML/SVG への直接レンダリングから始めて差し替え可能にする。2 と排他ではなく実装戦略

## 決定

2 + 4 を採用する。書き手はピクセルではなく意図を書き、見た目はテーマとレンダラが導出する。3 層構造（Foundation = テーマトークン / Slide = 1 枚 1 アイデア / Element = 表現の語彙）とし、最初の実装は HTML/SVG への直接レンダリングとする。

## 根拠

書き手が Claude と確定したため、YAML の書き味の悪さは問題にならず、検証可能性（スキーマ検証・lint・structured output）の価値が最大化する。spike（presentation/spike/、2026-07-04）で 9 枚のサンプルデッキを検証し、意図のみの宣言から視覚的に成立するスライドが導出できることを確認済み。確信度は高。

## 見直しの条件

実デッキ 3 本を運用し、(1) raw 要素（スキーマ外の SVG/HTML 埋め込み）が全要素の 1 割を超える、または (2) グリッド直接指定が名前付きパターンの利用を上回る場合、語彙の粒度設計が現実に負けている。語彙を増やすのではなく、導出モデル自体を見直す。

## 影響

- SPEC.md と JSON Schema が唯一の真実になる。linter・レンダラ・skill はすべてこれを参照する
- レンダラは差し替え可能な実装として扱い、既存ツールへの依存には抽象化レイヤーを挟む
- 詳細な設計は presentation/docs/design.md（生きた設計書）が持つ
