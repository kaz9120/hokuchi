# ADR-0004: スライド id を必須にし、再生成と手編集のマージ設計は運用後に行う

- ステータス: 承認
- 日付: 2026-07-04
- スコープ: presentation

## 文脈

書き手は Claude で、スキルが対話から YAML を生成する（ADR-0001）。ここで避けられない問題がある。生成された YAML を人間が手で編集した後、対話で再生成すると、手編集が失われうる。この「再生成と手編集の共存（マージ戦略）」をいつ設計するかを決める必要があった。マージは実際の編集パターンが分かって初めて要件が固まる領域で、机上で先に精緻な戦略を組んでも外しやすい。

## 選択肢

1. **最初からマージ戦略を設計** — 3-way マージや差分適用の仕組みを初版スキーマと同時に決める。運用開始時点で手編集が守られる。しかし実際にどの部分がどう編集されるかを観測する前の設計になり、複雑領域で精緻な計画を先に立てる典型的な失敗リスクを負う。使われないマージ機構を作り込む恐れがある
2. **完全に先送り（id も無し）** — マージに関わるものを一切入れない。初版は最小で済む。しかし後からマージを設計するとき、スライドを再生成をまたいで同定する安定キーが無く、後付けが難しくなる。安定キーの欠如は、後で最も戻しにくい種類の負債になる
3. **id のみ先行して先送り** — マージ戦略そのものは運用後に設計する。ただし将来のマージに備え、スライド id の必須化（安定キー）だけは最初のスキーマから入れる

## 決定

3 を採用する。マージ戦略の設計は、実デッキを運用して手編集の実態を見てから行う。その一方で、スライドの `id` は初版スキーマから必須にする。id は再生成・差分レビューをまたいでスライドを同定する安定キーであり、後からマージを設計するときの土台になる。

## 根拠

再生成と手編集の共存は、正解が分析からは出ない複雑領域の問題です。どの部分が手編集されるかを観測してから設計するのが、先に精緻な戦略を組むより確実です（design.md §8、2026-07-04 決定）。一方で id の必須化は、コストが小さく、後からでは足しにくい。安定キーは「今は使わないが、将来のマージが成立するかを左右する」性質を持つため、先行して入れます。先送りという判断自体の確信度は高、id だけで将来のマージに足りるかの確信度は中です。

## 見直しの条件

手編集と再生成の衝突（再生成で手編集が失われる、design.md §8）が実際に発生し、運用の痛点として観測されたときに、マージ戦略の設計を開始します。逆に、実運用で「生成後は手編集しない／手編集後は再生成しない」という使い分けが定着し、衝突が起きないなら、マージ機構は作らない。どちらに転ぶかを運用で見極めてから動きます。

## 影響

- スライド `id` は必須フィールド。この決定は ADR-0007 の「要素は常に slot / id を持つ」への一貫化とつながり、同定キーをスライド・要素の両層で揃える方向に効く
- マージ戦略・SPEC.md 側のマージ仕様は、運用データが集まるまで未定のまま残す
