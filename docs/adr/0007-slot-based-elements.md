# ADR-0007: 要素はスロット制にし、emphasis を要素別語彙に分け、タイプスケールをテーマに昇格する

- ステータス: 承認
- 日付: 2026-07-04
- スコープ: presentation

## 文脈

spike（presentation/spike/、2026-07-04）で 9 枚のサンプルデッキをレンダリングし、実装者としてスキーマの痛点を記録した（spike/NOTES.md §2）。中心仮説「意図を書けば配置は導出できる」はこの範囲で成立したものの、レンダラが暗黙に持つ導出テーブルが厚く、いくつかの構造的な曖昧さが表面化した。重要度の高い痛点（NOTES.md §2.1・§2.2・§2.3・§2.7）に、SPEC.md へ進む前にスキーマ側で答えを出す必要があった。3 つの決定を 1 本にまとめる。

## 選択肢

1. **現状維持（順序依存のまま）** — 名前付きパターンの要素を配列順で解釈し、emphasis は kind ごとに型を割り、フォントサイズはレンダラの暗黙テーブルに残す。初版のまま動く。しかし spike で観測した壊れやすさが残る。title-stage に並ぶ 2 つの statement は、どちらが主タイトルでどちらが副題かを「配列の 1 個目＝タイトル」という順序でしか判別できない（NOTES.md §2.1）。要素の入れ替えや追加で黙って壊れる
2. **スロット制へ寄せる（採用）** — 名前付きパターンがスロットを宣言し、要素は slot で入る。emphasis を要素種別ごとの語彙に分ける。フォントサイズの階層をテーマのトークンへ昇格する。壊れやすさの根を断つが、スキーマの語彙は増える
3. **grid-direct に一本化** — 名前付きパターンを廃し、常にグリッド直接指定（element 名参照）で書かせる。順序依存も id の不整合も消える。しかし「9 割は名前付きパターンで足りる」（design.md §レイアウト）という書き味を捨て、毎回グリッドを書かせる負担が全スライドに乗る。ADR-0001 の導出の思想に逆行する

## 決定

2 を採用する。3 つを決める。

第一に、名前付きレイアウトパターンはスロット（headline / hero / subhead など）を宣言し、要素は `slot:` でそのスロットに入る。要素は名前付きパターンでも grid-direct でも常に slot ないし id を持ち、配列順や kind の暗黙ルールに依存しない。これで NOTES.md §2.1（無名スロットの順序依存）と §2.7（id が必須になったり無かったりする不整合）を同時に解消する。

第二に、emphasis を要素種別ごとに別の語彙へ分ける。statement は強調する語（強調語）、diagram はノード参照、chart は annotations（`{at, annotate, style}` の注釈）とする。同じ `emphasis` キーが 3 種の別物を指す状態（NOTES.md §2.2）をやめる。

第三に、フォントサイズの階層（タイプスケール）を、レンダラの暗黙テーブルからテーマのトークンへ昇格する。role × layout × slot の組ごとのサイズ（NOTES.md §2.3 の階層表）を、レンダラ内の発明ではなくテーマが持つ一級の定義にする。

## 根拠

いずれも spike で実際に観察された具体的な問題への回答です。title-stage の 2 つの statement は配列順でしか主タイトルと副題を判別できず、スロット名が無い（NOTES.md §2.1）。emphasis は statement で強調語配列・diagram でノード id 配列・chart で注釈オブジェクト配列という 3 つの型に割れ、実装では kind による分岐が必須でスキーマ検証も型が割れていました（NOTES.md §2.2）。フォントサイズの対応表はレンダラ内に隠れ、テーマを差し替えても制御できませんでした（NOTES.md §2.3）。id は grid-direct で必須・名前付きパターンで不在という不整合を抱えていました（NOTES.md §2.7）。これらは書き味の好みではなく、静的検証が効かず黙って壊れるという構造の欠陥です。スロット制・語彙分割・トークン昇格は、いずれも「意図を宣言し配置を導出する」（ADR-0001）を壊さずに検証可能性を回復します。確信度は高。スロット語彙（headline / hero / subhead …）の具体的な粒度は、パターンを増やしながら調整する前提のため、そこは確信度中です。

## 見直しの条件

次のいずれかで再訪します。(1) 実デッキでスロット語彙が足りず、新しい名前付きパターンやスロットの追加が頻発するとき。粒度設計が現実に負けているので、ADR-0001 の撤退ライン（グリッド直接指定が名前付きパターンの利用を上回る）と合わせて導出モデルを見直す。(2) emphasis を要素別に分けた結果、要素をまたぐ共通の「強調」抽象がやはり必要だと判明したとき。分割ではなく共通抽象の再設計へ振り直す。(3) タイプスケールをテーマに持たせても、role × layout × slot の組み合わせ爆発でテーブルが管理不能になるとき。サイズ導出の規則そのものを簡素化する。

## 影響

- SPEC.md の要素モデルは、要素が常に slot / id を持つ形を前提にする。ADR-0001 の Element 層を精緻化し、ADR-0004 の「スライド id 必須」と同じ同定キーの思想を要素層まで広げる
- emphasis は要素種別ごとに別フィールドとして JSON Schema に定義する。kind による型分岐が検証時に不要になる
- タイプスケールはテーマトークンの一部になる。サイズはレンダラの実装詳細ではなく、テーマの差し替えで制御できる対象になる
- 残る痛点（NOTES.md §2.4〜§2.6・§2.8・§2.9：グリッド行数と stage_margin の相互作用、chart のデータ形の食い違い、axis-lock の宣言場所、role と layout の視覚属性の二重支配、diagram edges の文字列検証）は、この ADR の対象外。SPEC.md で個別に扱う
