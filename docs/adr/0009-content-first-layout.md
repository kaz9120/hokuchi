# ADR-0009: リポジトリはコンテンツを主役に置き、発表済み資料は凍結する

- ステータス: 承認
- 日付: 2026-07-05
- スコープ: リポジトリ全体

## 文脈

hokuchi は発信に関するツールとドキュメントをすべて置くリポジトリであり、これから発表に使用する資料が実際に蓄積されていく。初版実装の時点では、ツールが `presentation/` として root に立ち、資料はその中の `decks/` に置く規約だった。つまりコンテンツがツールの下に住む主従逆転の構成であり、これから増えるのはコンテンツの側である。構成を今のうちに決める必要があった。

判断の軸は 3 つ。(1) 主従 — hokuchi の存在理由は発信そのもので、ツールは脇役。(2) ライフサイクル — ツールはバージョン管理されテストされ更新され続けるが、資料は時系列に蓄積し発表後は凍結される。(3) 再現性 — レンダラは進化するため、deck.yaml だけを残すと当時の見た目を再現できなくなる。

## 選択肢

1. **talks/ + tools/ に分離** — 資料を root 直下の `talks/`（将来は `articles/` などの発信形態が並ぶ）に、ツールを `tools/slides/` に移す。root を見れば「発信が主役、ツールは脇役」が読める。移動コストは初版直後の今なら小さい
2. **presentation/ 維持 + talks/ 追加** — ツールは `presentation/` のまま、資料だけ root の `talks/` に出す。変更は最小だが、「presentation」という名前がツールなのか資料なのか曖昧なまま残る
3. **現状維持（decks/ 内包）** — 変更ゼロだが、資料がツールの下に住み続け、ライフサイクルの違うものが同じ木に混ざる。資料が増えるほど後から動かしにくくなる

発表済み資料の扱いは、(a) 最終レンダリングを凍結コミットする、(b) deck.yaml のみ保存する、の 2 択。

## 決定

1 を採用する。root は発信形態ごとのコンテンツディレクトリ（`talks/`、将来 `articles/` など）と `tools/` で構成し、スライドツールは `tools/slides/` に移す。発表資料は `talks/<YYYY-MM-slug>/` に置き、`deck.yaml` + `assets/` + `out/`（git 管理外）+ `final/` の構成とする。

発表済み資料は (a) を採用する。発表が終わったら最終レンダリング（PNG 一式 + PDF）を `final/` にコミットして凍結する。作業中の `out/` は git 管理外のまま。

## 根拠

これから増えていくのは資料であり、リポジトリの構成はその意思（発信が主役）を反映すべきです。ツールと資料はライフサイクルが異なるため、同じ木に混ぜるとどちらの管理も濁ります。凍結コミットを選ぶのは、アーカイブとしての再現性を deck.yaml とレンダラの組に依存させないためです。deck.yaml は schema_version を持ちますが、レンダラのバージョンは資料に紐づかないので、当時の見た目の保存は出力の凍結でしか担保できません。確信度は高。

## 見直しの条件

(1) 発信形態が増えて root のコンテンツディレクトリが乱立し、一覧性が落ちたとき（グルーピングを再検討する）。(2) final/ のコミットでリポジトリサイズが問題になったとき（Git LFS か外部アーカイブを検討する）。(3) ツールが tools/ 配下で相互依存を持ち始めたとき（パッケージ構成を再設計する）。

## 影響

- `presentation/` は `tools/slides/` へ移動（git mv 済み。npm test 通過を確認）。パッケージ名は `@hokuchi/slides` に変更
- crafting-presentation skill の既定出力先は `talks/<YYYY-MM-slug>/`。Phase 6 に「発表後は final/ へ凍結」を追加
- root の `.gitignore` に `talks/*/out/` を追加
- ADR-0001〜0008 の本文中の `presentation/` パスは決定当時の記述として残す（ADR は不変）
