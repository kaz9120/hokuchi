# ADR-0012: render の出力を単一ファイル SPA (index.html) に統合する

- ステータス: 承認
- 日付: 2026-07-06
- スコープ: tools/slides

## 文脈

render はスライドごとの `slide-NN.html` と一覧の `index.html` を出力してきた。ai-survival (2026-07) の運用で 2 つの痛みが出た。

1. ページ送りが `location.href` の全再読み込みで、1 枚 = 1 ドキュメントのためレビューの体験が細切れになる
2. serve + agentation (ADR-0011) のアノテーションがページ単位に分断される。デッキ全体を通してレビューしても、フィードバックは 26 ページ分の断片として届く

またファイル数がスライド数に比例して増え、out/ の管理も煩雑だった。

## 選択肢

1. **現状維持** — ページごとの HTML。痛みが残り続ける
2. **ビルド時に単一ファイル SPA を出力する** — render が全スライドを 1 つの `index.html` に含めて出力する。表示スライドの切り替えは CSS `:target` + URL hash (`#pNN`) で行い、JS はキーボードナビと縮尺調整の薄い層だけ。`g` キーで全スライドを縦に並べる一覧モード (旧 index 相当) に切り替える。shot は `index.html#pNN` を 1 枚ずつ撮る
3. **serve のみ SPA 合成** — render 出力は現状のまま、配信時に 1 ページへ合成する。ディスク上の HTML と配信物が乖離し、「本番と同一物を配信する」という ADR-0011 の原則を壊す
4. **React 等によるランタイム SPA** — ビルドパイプラインと実行時依存が増える。静的スライドに対して過剰

## 決定

2 を採用する。出力は `index.html` (+ assets) の 1 ドキュメントに統合する。スライド切り替えの基本機構を CSS `:target` に置くのが要点で、JS が死んでいても `#p03` を開けば 3 枚目が正しく表示される。これにより shot (headless Chrome のスクリーンショット) は JS の実行タイミングに依存しない。`slide-NN.html` は出力しなくなり、render は古い残骸を掃除する。PNG の命名 (`slide-NN.png`) は Google Slides への手貼りフローが依存しているので変えない。

## 根拠

アノテーションの集約 (一覧モードでデッキ全体に注釈して 1 回で Send できる) とレビュー体験の連続性が主目的で、これは 1 ドキュメント化でしか達成できない。選択肢 3 は ADR-0011 の原則と衝突し、4 は脇役のツールに本体より厚い基盤が生える。確信度は高。確信度を下げる前提は「headless Chrome が fragment 付き file:// URL で :target を初期適用すること」だが、これは CSS 仕様の標準挙動である。

## 見直しの条件

- デッキが大きくなり単一ファイルが実用に耐えなくなったとき (目安: スライド 100 枚超、または index.html が数十 MB)
- プレゼンテーションランタイム (presenter view・スピーカーノート表示・タイマー) を本格的に載せる判断をしたとき。その時点で構成ごと再設計する (これが実れば Google Slides への出力自体が不要になる)

## 影響

- shot はスライド数を出力 HTML の `data-slides` 属性から読み、`#pNN` 付き URL で撮る
- serve は変更が最小 (ルートを index.html に向け、アノテーションの記録にページ内 hash を含める)。agentation のセレクタはスライドのセクション id (`#pNN`) を含むため、1 ドキュメントでもスライドの特定性は保たれる
- test / docs/design.md / skill (crafting-presentation) の出力説明を更新する
- 発表済みの talks/*/final/ は凍結物なので触らない (ADR-0009)
