# ADR-0014: 構図の知識はレンダラが専有し、レイアウトを measure/compose の 2 パスに再設計する

- ステータス: 承認
- 日付: 2026-07-08
- スコープ: tools/slides

## 文脈

coverage デッキの目視検証 (2026-07-08) で、flow.cycle が離心率 5:1 の楕円に潰れ、trend チャートのプロットが 944×198px (4.8:1) の帯になっていることが分かった。人間は正多角形や黄金比・白銀比に近い形を美しいと感じるが、現行レンダラの出力はそこから大きく外れる。

原因を掘ると 2 つに絞れる。

1. 縦予算の欠乏。外周マージン 64px とレターボックス 98.7px が上下に重なり、キャンバス 720px のうち 45% (上下各 162.7px) が舞台の外にある。headline 帯と 92% スケールを引くと、主役に渡る箱は 1088×288px (3.78:1) の帯になる。この箱の中では正円の環も 2:1 のプロットも作れない。
2. 一方向レイアウト。現行の導出は「箱を先に切り、中身を箱いっぱいに引き伸ばす」の一択で、中身の望む形 (循環はほぼ正円、推移は 2:1 前後) を container に伝える経路が存在しない。楕円の扁平はこの構造の症状である。

さらに、構図パラメータ `theme.grid.stage_margin` がテーマに露出している。「書き手は意図を書き、配置はレンダラが導出する」(ADR-0001) の分界からすると、構図の知識が宣言側に漏れている。slide:ology の 5 条件 (design.md §2) のうち C4 (配置の 6 原則) をどの層が担うか、境界を確定する必要がある。

## 選択肢

**A 案 — 現行構造のまま逐次修正。** パターン関数ごとにマジックナンバーを調整する。安価だが「箱いっぱいに引き伸ばす」一方向の構造が残るため、form を増やすたびに同じ病気が再発する。構図の知識がレンダラ中に定数として散在し続ける。

**B 案 — measure/compose の 2 パスに自作で再設計。** 各描画要素が measure パスで「最小サイズ・理想アスペクト・伸縮の許容範囲」を申告し、compose パスがステージ上の兄弟要素と余白をまとめて配分して光学中心に載せる。余白は「残り」ではなく配分対象になる。Flutter / WPF のレイアウトプロトコルと同型で、キャンバス 1280×720 固定・ビルド時一発描画・要素 7 種という条件なら数百行の規模。

**C 案 — 外部レイアウトライブラリへの委譲。** yoga (flexbox) は箱の分配はできるが「中身が理想アスペクトを申告して交渉する」「光学中心」の語彙がなく、むしろ戦うことになる。ELK / dagre はグラフ自動レイアウトで、効くのは network / tree のノード配置だけ。スライドの図解はノード 3〜7 個で、アルゴリズムの強さより美的統制が支配的。チャートを vega-lite 等に渡すと「チャートジャンクがそもそも書けない」担保 (ADR-0002) が依存先の設定項目に化ける。

## 決定

B 案を採る。あわせて境界を次のとおり確定する。

- スキーマ (deck / theme) が担うのは意味と関係 — C1 (語数)・C2 (1 スライド 1 アイデア)・C5 (データの意味)、および C3 のうちブランドのアイデンティティ (色・書体・アイコン様式のスロット)。
- レンダラが専有するのは空間の実現 — C4 (コントラスト・フロー・階層・統一感・関係性・余白) の全部。比率・正多角形・光学中心・余白配分は仕様ではなくレンダラ内部の実装詳細であり、スキーマ・テーマ・SPEC のいずれにも露出させない。
- SPEC §8 は「正しさの床」(チャートジャンク禁止・改行規則・3 レイヤー規律など) に縮め、美しさの規則は床の上でレンダラが自由に進化する。美の改善のたびに SPEC が版を上げる状態を作らない。
- `theme.grid.stage_margin` はレンダラ内部ポリシーに引き取り、テーマから撤去する方向とする (スキーマ改版は本実装時に行う)。

## 根拠

確信度は中。要素種が固定・キャンバスが固定という条件で 2 パスレイアウトは自作可能な規模であり、外部ライブラリは欲しい語彙と合わない (選択肢 C の評価)。確信度を高にしないのは、理想比率の具体値 (循環の離心率上限、推移の 2:1 など) が机上の仮説だからで、spike (`spike/layout-engine/`) で cycle / trend の 2 枚を新エンジンで貫通させ、before/after を目視してから本実装に入る。

## 見直しの条件

1. network / tree でノード 10 個超の実デッキが現れ、エッジ交差最小化が必要になったら、ELK を diagram レイアウト戦略の 1 実装として抽象化レイヤー越しに導入する (自前の幾何で書くべき領域ではないため)。
2. 規範ベースの導出にしても serve 注釈 (ADR-0011) で構図への指摘が減らないなら、比率の値いじりではなく導出モデル自体を再訪する (design.md §8 と同じ撤退基準)。

## 影響

- render.mjs のレイアウト部を measure/compose に再実装する。描画の見た目はデッキ全体で変わる
- SPEC §8 を「正しさの床」に改訂する
- theme スキーマの次版で `grid.stage_margin` を廃止する
- coverage デッキが before/after の検証台になる
- 書き手の語彙 (deck.yaml) と crafting-presentation skill には影響しない
