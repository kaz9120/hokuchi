# ADR-0018: レンダラを React コンポーネントで再実装し、ページ内の配置を CSS レイアウトに委ねる

- ステータス: 承認
- 日付: 2026-08-03
- スコープ: tools/slides

## 文脈

coverage デッキ 39 枚の目視検証 (2026-08-03) で、通しで見たときに見出しが上下に跳ねることが分かった。見出しの Y 座標を実測すると次のとおり散っている。

| スライド | 内容 | 見出しの Y |
|---|---|---|
| slide-20 | chart trend | 85px |
| slide-13 | diagram tree | 115px |
| slide-22 | bullets | 142px |
| slide-32 | table | 214px |
| slide-19 | flow.timeline | 267px |

原因は `leadStage` (`src/render.mjs:1976`) に絞れる。この関数は見出しと本体の合計高さを求め、その塊を stage 内の光学中心 (0.45) に置く。本体が薄いスライドほど塊が短くなり、見出しが下へ落ちる。

同じ関数が本体を `stage.x + (stage.w - m.w) / 2` で中央に寄せている。見出しは常に x=96 の左寄せなので、本文の左端も要素ごとに散る。実測では table が 313px、code が 254px、timeline が 110px だった。

ADR-0014 で導入した measure/compose は、1 枚の中で「中身が望む形」を実現する目的を果たしている。欠けていたのは枚をまたぐ一貫性で、design.md §2 の C3 が求める「グリッドがデッキ全体で揃う」を担う機構が存在しなかった。1 枚ずつ最適に組んだ結果、デッキとしてのリズムが崩れている。

第二の文脈として、`render.mjs` が 2664 行に達している。描画は文字列連結で、SVG のパス生成はテンプレートリテラルの中にある。タグの閉じ忘れとエスケープ漏れを型が防がず、要素を 15 種まで増やした今、読み書きの負荷が上限に近い。

## 選択肢

**A 案 — `leadStage` だけを直す。** 見出しの Y を固定し、本体の左端を揃える。最小の変更で今回の症状は消える。しかし絶対座標を JS で計算する構造は残るため、stage を追加するたびに同じ規律を手で守る必要がある。文字列連結の保守負荷にも触れない。

**B 案 — Marp をバックエンドにし、hokuchi をインタプリタにする。** deck.yaml から Marp Markdown を生成し、レンダリングと出力を Marp CLI に委ねる。組版を CSS に委ねる規律が手に入り、エコシステムに乗れる。ただし diagram 6 類型と chart 3 レイヤーには Markdown の対応物がないため、`--html` で div と SVG を吐くことになる。Marp が担うのはページ分割と CSS 適用と CLI 出力の 3 つだけで、SVG 生成も measure も残る。PDF と PNG は現状 Chromium 経由で既に出せている。PPTX は各スライドを画像として貼るだけで、editable モードは実験的機能であり LibreOffice を要求し、複雑なスタイルで壊れ、スピーカーノートに対応しない。得るものに対して、`build` の段階的開示と `serve` のアノテーション (ADR-0011) を失う。

**C 案 — React コンポーネントで再実装し、ページ内の配置を CSS に委ねる。** 描画層を JSX に移し、`renderToStaticMarkup` で静的 HTML を吐く。stage 内の縦積みは flex に任せ、見出しの位置は CSS が決める。`react` `react-dom` `esbuild` は agentation 用に既に devDependencies にあり、追加の依存はない。移行対象が 2664 行あることが弱点。

**D 案 — C に加えて shadcn/ui を採用する。** カードやパネルの見た目を既製のコンポーネントで賄う。Tailwind と Radix が前提になる。

## 決定

C 案を採る。内訳は次のとおり。

描画層を React コンポーネントに移し、`renderToStaticMarkup` で静的 HTML を生成する。ランタイムに React は乗せない。出力は ADR-0012 の単一ファイル SPA のまま変えない。

ページ内の配置は CSS の flex に委ねる。stage を flex コンテナとし、見出しは上端に固定、本体は残り領域を占める。本体の縦方向だけを中央に寄せ、左端は動かさない。`leadStage` を経由する 12 種の stage (diagram / chart / list / image / code / post / link / stat / table / versus / agenda / video) がこの変更を共有する。

measure は純関数のまま残し、役割を自動縮小の判定に限定する。`while (fs > minFs && ...) fs -= 1` に相当する処理は CSS に代替機能がないため JS が担い続ける。一方、配置のために幅を申告して呼び出し側が中央寄せする経路は廃止する。

SVG 内部の座標計算は自前を続ける。ADR-0014 の選択肢 C で ELK / dagre / vega-lite を却下した理由は現在も有効で、ノード 3〜7 個の図解では美的統制がアルゴリズムの強さを上回る。`renderDag` が持つ「流入エッジを合流点で 1 本に束ねる」「同列・逆行は描かない」といった判断は、この語彙に固有のものである。

外部ライブラリの導入は d3-scale と d3-array に限る。用途は chart の目盛り算出とスケール変換で、`src/render.mjs:1066` の自前実装 (`Math.pow(10, Math.floor(Math.log10(v)))`) を置き換える。描画は自前のままとする。

shadcn/ui と Tailwind は採用しない。

## 根拠

診断部分の確信度は高い。見出しの Y のばらつきは実測値であり、`leadStage` の 1 行がその発生源であることはコードから直接読み取れる。

React 化の投資対効果については確信度が中。2664 行の移行はコストであり、出力の見た目が向上するわけではない。それでも採るのは、3 つの理由による。1 つ目は依存が増えないこと。2 つ目は CSS レイアウトへの移行と同時に行えば、同じ場所を 2 度書かずに済むこと。3 つ目は SVG の可読性で、テンプレートリテラルの中のパス文字列が `<Edge from={a} to={b} merged={merged} />` になる差は、要素を今後も増やす前提では大きい。

D 案を退ける理由は 3 つある。Tailwind のトークン体系は、BRAND.md と hidoko `tokens.css` から色と書体を導出する ADR-0003 と二重管理になる。shadcn/ui の余白・角丸・影は本文 14〜16px のアプリ UI 向けに設計されており、本文 24px・見出し 60px 以上のスライドではスケールが合わない。Radix が提供する Dialog / Popover / Select は静的なスライドで使わない。ただし見た目の設計を参照し、値を BRAND.md 側に取り込むことは妨げない。

B 案を退ける確信度は中。Marp が担う層が薄いという判断は上記のとおりだが、「自分以外の人間が Markdown で直接スライドを書く」という前提が将来立ち上がれば、評価は変わる。その場合は diagram と chart を捨てる判断とセットになるため、ADR-0001 の中心仮説そのものを置き換える別の決定になる。

## 見直しの条件

1. React 化を stage 3 種まで進めた時点で、コード量が減らず可読性の向上も実感できないなら、残りの移行を止めて A 案 (CSS レイアウト化のみ) に切り替える。
2. 人間が deck.yaml ではなく Markdown で直接スライドを書く運用が必要になったら、B 案を ADR-0001 の見直しとして再訪する。
3. diagram でノード 10 個超の実デッキが現れ、エッジ交差の最小化が要るようになったら、ADR-0014 の見直し条件 1 に従って ELK を抽象化レイヤー越しに導入する。

## 影響

- `src/render.mjs` を React コンポーネント群へ分割する。stage 単位で段階的に移行し、各段階で coverage デッキ 39 枚をレンダリングして差分を確認する
- ビルドに esbuild の JSX 変換を挟む。出力の HTML は静的なままで、ランタイム依存は増やさない
- 見出しの位置と本文の左端が全デッキで変わる。`talks/*/final/` は凍結済みのため影響しない。`out/` は再生成する
- `d3-scale` と `d3-array` を dependencies に追加する
- SPEC には影響しない。構図はレンダラ専有 (ADR-0014) の範囲内で完結する
- 書き手の語彙 (deck.yaml) と crafting-presentation skill には影響しない
- `serve` のアノテーション (ADR-0011) は、注入対象が静的 HTML である前提を保つため、そのまま動く
