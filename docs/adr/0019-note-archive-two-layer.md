# ADR-0019: note の記事は原本 JSON と Markdown の 2 層でアーカイブする

- ステータス: 承認 (埋め込みの表現は → ADR-0021 で置き換え)
- 日付: 2026-08-31
- スコープ: リポジトリ全体 / tools/notes

## 文脈

note に週 1 で書き続けた記事が 44 本たまった。これを hokuchi で管理したいという要求は前からあり、何度か試みては消している。失敗はいつも同じ形で起きた。

1. 記事に埋め込んだ X のポストや外部記事カードが、Markdown に取り込むと素の URL か空行になる。note の画面では「カード」に見えていたものが、種別ごと消える
2. 画像の置き場所が定まらない。note の URL を参照したままだと記事を消した時点で壊れるが、落とすとファイル名と参照の対応が崩れる
3. 何より、落ちたことに気づけない。取り込んだ直後は読めるので問題なく見え、後から埋め込みが消えているのを見つけて、やり直す気力を失って消す

つまり本当の問題は変換の精度ではなく、「落ちたことに気づく手段がない」ことだった。ADR-0009 が発表資料に与えた答え (出力を凍結してアーカイブの再現性をレンダラから切り離す) を、記事にも与える必要がある。

## 選択肢

**取得元。** A 案: 公開ページの HTML をスクレイプする — 埋め込みは描画後の姿でしか取れず、元 URL が失われる。過去の失敗はここに根がある。B 案: note の公開 API (`/api/v3/notes/<key>`) を使う — `body` に完全な HTML が入り、`figure` の `data-src` と `embedded_contents` が埋め込みの元 URL とメタを保つ。B 案を採る。

**保存形式。** A 案: Markdown だけを置く — 埋め込みカードもキャプションも Markdown に対応物がなく、変換した時点で情報が減る。減った分は二度と戻らない。B 案: 原本 HTML だけを置く — 情報は完全だが、読めないし差分も追えない。C 案: 原本と Markdown の 2 層を置く。C 案を採る。

**埋め込みの表現。** A 案: 素の URL 行 — 読めるが種別が消え、これまでの失敗の再来になる。B 案: 生の HTML を埋める — Markdown が読めなくなる。C 案: `:::embed{service="..." url="..."}` ディレクティブに、ポスト本文や記事タイトルをテキストで添える。C 案を採る。

**画像。** A 案: note の URL を参照する — 記事を消せば壊れる。B 案: `assets/` に実体を落とし、元のファイル名のまま相対参照する。B 案を採る。

## 決定

note の記事は `articles/note/<公開日>-<slug>/` に、次の 3 つで置く。

1. **`source.json`** — 原本。note API のレスポンスから、記事として不変なフィールドだけを取り出して凍結する。本文 HTML・埋め込みメタ (`embedded_contents`、埋め込み先のスナップショット HTML を含む)・見出し画像・ハッシュタグは丸ごと保つ。スキ数やコメント数のような閲覧のたびに変わる値は、記事の同一性に関わらないので落とす
2. **`index.md`** — `source.json` から決定的に導く読む用の派生形。手で直す場所ではない。埋め込みは `:::embed{service url}` で種別と URL を残し、ブロックの中に X のポスト本文や外部記事のタイトルをテキストで置く。埋め込み先が消えても中身が残る
3. **`assets/`** — 見出し画像と本文画像の実体。note のファイル名のまま置く。見出し画像の URL は note が配信用に縮小・再圧縮した版 (`?fit=bounds&quality=85&width=1280`) を指すので、クエリを外したオリジナルを取る

埋め込み先のタイトルを OGP から補うようなことはしない。`index.md` に出てよいのは `source.json` にあるものだけとする。note がタイトルを持たない埋め込み (docswell や speakerdeck など 12 件) は URL だけになるが、外から足した情報が混ざると「原本に忠実」の意味が曖昧になる。

取り込みと再生成と検査は `tools/notes` の `hokuchi-note` が行う (`sync` / `build` / `verify` / `index`)。ディレクトリ名の slug は `articles/note/slugs.json` を唯一の真実とし、記事の同一性は常に note key で追う。slug を書き換えれば `sync` がディレクトリを引っ越す。

そして `verify` を置く。原本と生成物を突き合わせ、本文の断片・埋め込みの種別と URL・本文リンク・画像の実体・見出しやリストの数が合わなければ error にする。検査は `parse.mjs` とは別経路で書き、原本 HTML を正規表現で直接数える。パーサのバグと検査のバグが同じ方向へ倒れないようにするためである。

## 根拠

確信度は高。2 層にすれば、Markdown 側の判断 (キャプションをイタリック行にする、`&nbsp;` を半角に寄せる、といった読みやすさのための割り切り) が情報の欠落にならない。原本が別にあるので、変換規則を後から変えても記事は失われず、`build` を回し直すだけで済む。

`verify` の効き目は実地で確かめた。取り込みの過程で 6 本の記事から欠落を検出しており、どれも目視では気づけない類のものだった。`<figure><a href><img></a></figure>` というリンク付き画像の href を捨てていたもの、`<figcaption>` の中のリンクをテキストに潰して URL を消していたもの、コードブロック内に ``` を含む記事のフェンス崩れ、埋め込みカードの説明文が見出しに化ける事故である。

検査は「原本の要素が生成物にあるか」だけでは足りない。段落の入れ替えも、2 回書いた文が 1 回に減ることも、リンクのラベルが別の URL に付け替わることも、それでは通ってしまう。だから本文はカーソルを前へ進めながら照合して順序と出現回数まで見る。同じ理由で、リンクは href とラベルの組で、画像は並び順で、見出し画像は実解像度が原本の宣言以上かで検査する。

確信度を下げている前提が 1 つある。note の公開 API は非公式で、仕様が変わりうる。ただし原本を手元に持つ以上、API が変わって困るのは新しい記事の取り込みだけで、既存のアーカイブは影響を受けない。

## 見直しの条件

- note の公開 API が使えなくなったとき (取得経路だけを差し替える。保存形式は変えない)
- `assets/` の合計が大きくなり、リポジトリの取り回しに響いたとき (現状は 44 本 137 枚で 66MB。ADR-0009 の見直し条件と同じ扱いで、Git LFS か外部アーカイブを検討する)
- note 以外の発信先が増え、`articles/<媒体>/` の構成が窮屈になったとき

## 影響

- `articles/note/` を新設し、公開済みの 44 本を取り込む。ADR-0009 が「将来」としていた `articles/` がこれで埋まる
- `tools/notes` (`@hokuchi/notes`) を追加する。依存はゼロで、HTML パーサも自前に持つ
- CLAUDE.md のディレクトリ節を、`articles/` を実在するものとして書き直す
- 記事を書き足したら `hokuchi-note sync` を回す。slug 未設定の記事は key のままディレクトリが作られ、`slugs.json` に足して再実行すれば引っ越す
