# ADR-0020: note の執筆はスキルで進め、文体の規範は実測から引いて lint に落とす

- ステータス: 承認
- 日付: 2026-09-06
- スコープ: リポジトリ全体 / tools/notes

## 文脈

これまで note は、note のエディタで書き、執筆の支援は 1 枚の長いプロンプト (Persona / Style Guide / 評価基準を全部入れたもの) で受けていた。ADR-0019 で過去記事 44 本がリポジトリに入り、執筆の順序も「hokuchi で書いてから note に貼る」に変わる。支援の形をリポジトリ側に持ち直す時期になった。

書き手の課題は本人の言葉で 2 つある。AI っぽい文章になりがちなこと、長くて読みづらくなることである。

ところが 44 本を実測すると、そのままには受け取れない。1 文の長さは中央値 29 字で、60 字を超える文は 7.4% しかない。段落も中央値 60 字。記事の長さも時期を追って短くなっている (前半 1,620 字 → 後半 1,134 字)。プロンプトが掲げていた「1 文 60 字以内」は、すでに達成された規範だった。

一方で、ぼかし表現 (かもしれません / と思います / 気がします) は 93 回、千字あたり 1.5 回出ている。冒頭が「本記事では〜ご紹介します」で始まる記事が 8 本、結びが読者へのお願いで終わる記事も残っている。タグが 2 個以下の記事が 19 本ある。

つまり伸びしろは文の長さではなく、**濃度** (読者が受け取る発見の量 ÷ 文字数) の側にあった。

## 選択肢

**規範の作り方。** A 案: 既存プロンプトをそのままスキルに移す — 移すだけなら価値が増えない。実測すると数値が実態と合っていないことも分かった。B 案: 44 本の実測で校正し、数値を実データに置き換える。B 案を採る。

**規範の置き場所。** A 案: すべて散文で書く — 「1 文 60 字」のような数えられる規範まで人が目視することになり、毎回は続かない。B 案: 数えられるものは lint に落とし、散文は数えられないものだけを扱う。B 案を採る (ADR-0002 の 2 段構えと同じ考え方)。

**手本の与え方。** A 案: 抽象ルールだけ — 「低カロリー」「フック・ファースト」と書いても、書き上がりは書き手の癖に引っ張られる。B 案: 公開済み 44 本を一次資料として読ませる。B 案を採る。実物のほうが規範より雄弁で、しかも新しい記事ほど研ぎ澄まされているので、時系列そのものが良し悪しの教材になる。

**削る作業の扱い。** A 案: 執筆の最後のチェック項目にする (既存プロンプトはこの形で、「書き終えたら削れる文はないか確認する」の 1 行だった) — 書きながら削ると、削るべきでないものまで削れる。B 案: 独立した工程にし、目標値を置く。B 案を採る。

## 決定

`.claude/skills/writing-note/` を置き、Phase 0〜7 の一気通貫フローにする (crafting-presentation と同じ形)。

1. **Phase 5「削る」を独立した工程にする。** 書き切ってから削る。目標は「2 割削る」と先に置く。手順は `references/density.md` に、上から順に機械的に判断できる形で並べる。原稿を持ち込まれたレビュー依頼は、この Phase から入る
2. **文体の規範は 44 本の実測から引く。** 1 文 29 字、段落 60 字、冒頭 41 字、結び 44 字、ひらがな 67%、です・ます 65%。理想ではなく「自分が実際に書けている水準」を基準にする
3. **数えられるものは `hokuchi-note lint` に落とす。** 文の長さ、段落の長さ、ぼかしの密度、型どおりの言い回し、共感を求める表現、結びの重さ、漢字率、見出しの中身、タグの数。閾値は公開済み記事が error を出さず warn が改善余地として出る位置に合わせる
4. **公開済み 44 本を一次資料として読ませる。** 題材別に読む記事を指定し、2025 年 12 月前後の記事は反面教師として扱う
5. 原稿は `articles/note/drafts/<slug>/` に置く。公開したら `hokuchi-note sync` が `<公開日>-<slug>/` に凍結する

## 根拠

確信度は高。規範を実測に接地させたことで、「守れているルール」と「伸びしろ」を取り違えなくなった。文の長さを詰める指導を続けても記事は良くならず、削る工程を立てるほうが効く、という判断がデータから出せている。

lint の閾値は公開済み 44 本で校正した。最初は 80 字超の文を error にしていたが、それだと自分が良しとして公開した記事から error が 23 件出る。公開済みが error を出す基準は、基準のほうが間違っている。個別の文を挙げるのは 80 字超だけにして、あとは記事全体の率で見る形に変えた結果、error 0 / warn 66 に落ち着いた。warn の中身は、冒頭の定型 8 件、タグ不足 16 件、80 字超の文 21 件など、実際の改善余地である。

確信度を下げている前提が 1 つある。「濃度」は lint では測れない。削れたかどうかは人が読んで決めるしかなく、スキルが与えられるのは手順と目標値と実例までである。

## 見直しの条件

- 記事が 20 本ほど増えたら実測を取り直し、`references/voice.md` の数値と lint の閾値を更新する。公開済み記事が error を出すようになったら、閾値か規範のどちらかがずれている
- 「2 割削る」が機械的な削りすぎを生んでいると分かったとき (density.md の「削ってはいけないもの」を厚くする)
- note 以外の媒体で書き始めたとき (スキルを媒体ごとに分けるか、共通部分を括り出すかを判断する)

## 影響

- `.claude/skills/writing-note/` を追加 (SKILL.md + references 5 本)
- `tools/notes` に `hokuchi-note lint` を追加。`src/lint.mjs` は文体だけを見る。取り込みの忠実さを見る `verify` とは別物として分ける
- `articles/note/drafts/` が原稿の置き場所になる。`source.json` がないので `sync` / `verify` / `build` の対象には入らない
- CLAUDE.md に執筆の入口を書く。note を書く依頼は writing-note に従う
