# ADR-0026: 発表資料はシーン×状態の React コードで書き、再生と部品のフレームワーク tools/stage を自作する

- ステータス: 承認
- 日付: 2026-10-07
- スコープ: リポジトリ全体 / tools/stage / tools/slides

## 文脈

ADR-0001 以来、スライドは意図宣言型 YAML で書き、配置・色・サイズはレンダラが導出してきた (ADR-0014, ADR-0018)。2026-10-07 に話者が出した評価は「自前レンダラの品質は低い。これなら毎回 HTML を書いた方がよっぽど良い」だった。求めているのは、紙芝居ではなく、モーションと状態遷移のある体験と、質の高い図解である。年 100 本の発表でもスケールすることも条件に加わった。

品質が上がらない原因は、磨き込みの不足ではなく役割分担にある。

- 表現の上限が、スキーマの語彙とレンダラの実装量で決まる。yamanote-west では 29 枚中 18 枚が statement-stage だった
- 動きの語彙がない。段階表示 (reveal / build) はあるが、要素が画面に残ったまま移動・変形・強調される表現は書けない
- 図解はノードとエッジからの自動配置で、汎用の箱と矢印になる。その話のための図にならない

slide:ology 第 9 章は、プレゼンを「1 枚ずつバラバラなスナップショットの連続」ではなく「1 つのシーンから次のシーンへ移り変わる映画」と考えるよう勧めている (p.212)。アニメーションは装飾ではなくコミュニケーション手段であり (p.200)、関係性の変化・画面の演出・オブジェクトの変化・連続性・強調の 5 役割のどれかを果たすときだけ使う (p.205)。

`tools/slides/spike/motion-scenes/` で、ai-team-culture の 5 シーンを React + Motion で作り直した。layout アニメーションによるモーフ、線の描画、線上を流れる粒、数の数え上げ、シーン間のパンが、5 シーン約 400 行で書けた。話者の評価は「めちゃんこ良い」だった。同時に、状態遷移に固有の崩れも見つかった。見出しの差し替えで新旧の文言が重なる、縮むカードの中で文字が引き伸ばされる、幅が変わったカードで折り返しが先に飛ぶ、の 3 つである。

## 選択肢

**A 案: 毎回素の HTML を書く。** 再生の仕組みもトークごとにコピーする。自由度は最大だが、上の崩れの対処と、発表者ビューなどの周辺機能を毎回やり直すことになる。年 100 本では、直した知見が次のトークに残らない。

**B 案: Slidev や reveal.js に乗る。** 発表者ビュー・書き出し・ステップ送りが手に入る。ただし Slidev は Vue 前提で、hidoko と既存資産は React である。どちらも「スライド単位の Markdown + 段階表示」が基本の単位で、要素が状態をまたいで生き続けるシーンの書き方は、拡張として後付けすることになる。

**C 案: React のフレームワークを自作し、各トークは Claude が TSX で書く。** シーンは素の React コードなので、表現力は A 案と変わらない。フレームワークは「再生」と「部品」だけを持つ。状態遷移の崩れは部品で一度だけ吸収し、トークをまたいで使い回せる。自作の保守コストを負う。

## 決定

C 案を採る。`tools/stage/` に再生機・部品・テーマ・CLI を置き、各トークは `talks/<slug>/` に TSX のシーンとして書く。

フレームワークが持つものと、持たないものの境界は次のとおり。

- 持つ: ステップ送りとシーン間の遷移、発表者ビュー・一覧・ノートを読むモード、スマホでの操作、状態遷移の部品 (文言の差し替え・登場・モーフするカード・要素同士をつなぐ線・流れ・数の変化)、テーマ (トークン・ブランド枠・OGP カード)、検証 (全状態の静止画・遷移のコマ撮り・はみ出しと重なりの検出)
- 持たない: 配置の決定。どこに何を置くか、どんな図にするかは、シーンを書く側 (Claude) が毎回決める

部品はスキーマではなく出発点である。シーンは素の要素や SVG を自由に使ってよい。ADR-0014 の「構図はレンダラが専有する」とは逆向きの決定になる。

## 根拠

- 表現の上限を語彙で決めないことが、話者の要求の中心にある。コードで書けば上限は Web の表現力そのものになる (確信度: 高)
- スパイクで見つかった崩れは、どれもシーンの内容ではなく遷移の仕組みに由来する。部品に吸収すれば、2 本目以降のトークは同じ崩れを踏まない (確信度: 高)
- 状態遷移を Motion の layout アニメーションで書けることは、スパイクで確かめた。B 案の基本単位に後付けするより素直である (確信度: 中。複雑なシーンでの性能は未検証)
- Claude はトークごとに素の React を書くので、フレームワークの API を覚える量は小さくて済む。部品が足りないときは、シーンの中で書いてから部品に昇格させればよい (確信度: 中)

## 見直しの条件

- 部品が肥大化し、シーンを書くよりフレームワークの制約を回避するコードの方が増えたとき
- 1 本あたりの制作時間が、旧方式より長いまま 5 本続いたとき
- 発表会場の環境 (投影機・会場 PC) でブラウザ再生が安定しない事例が出たとき

## 影響

- 次の ADR を廃止にする。YAML スキーマ・レンダラ・lint に結びついた決定である: 0001, 0002, 0004, 0006, 0007, 0008, 0010, 0012, 0013, 0014, 0015, 0016, 0017, 0018, 0025
- ADR-0003 (テーマはブランドトークンから導出する) は引き続き有効で、テーマの CSS トークンに適用する。ADR-0011 (アノテーションで人のレビューを受ける) も有効で、tools/stage に移植する
- `tools/slides/` は新規の利用を止める。既存の発表済み資料の `final/` はそのまま残す
- 絵コンテの形式と crafting-presentation の書き換えは、別の ADR で決める
- 配信 (PDF・docswell・凍結) の扱いは ADR-0027 で決める
