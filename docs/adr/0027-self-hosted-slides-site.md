# ADR-0027: 発表資料は slides.y-kaz.com に自前でホスティングし、PDF と docswell をやめる

- ステータス: 承認
- 日付: 2026-10-07
- スコープ: リポジトリ全体 / tools/stage

## 文脈

これまで公開資料は、レンダリングした画像から PDF を作り、docswell にアップロードして公開してきた。ADR-0026 で資料が動きと状態遷移を持つようになると、PDF では動きが消える。スパイクでは状態を選んで PDF のページにする方式を試し、ベクターで文字も選べる PDF を出せた。ただ、動きを落とした版を別に作り込むことになる。

話者からは、自前でホスティングする提案があった。`slides.y-kaz.com` にスライド置き場を作り、これからの資料はすべてそこに置く。PDF にできなくてよい代わりに、SNS でシェアしたときの OGP をきちんと設定したい。

もう 1 つの前提として、ADR-0009 は発表済みの資料を `final/` に凍結すると決めている。レンダラが進化すると、ソースだけでは当時の見た目を再現できないからだ。フレームワークを自作する ADR-0026 でも、この事情は変わらない。

## 選択肢

**A 案: docswell を続け、PDF を作り込む。** 既存の導線と閲覧数の集計がそのまま使える。動きは失われ、PDF 専用の補足や状態選びを毎回作ることになる。

**B 案: 自前でホスティングし、Web をそのまま公開する。** 動きと状態遷移を、閲覧者もそのまま体験できる。OGP・URL・一覧ページは自分で作る。docswell のようなプラットフォーム上の発見性は失う。

**C 案: 自前ホスティングと docswell の両方に出す。** 発見性と体験の両方を取れるが、PDF の作り込みが残る。

## 決定

B 案を採る。発表資料は `slides.y-kaz.com` に静的サイトとして置き、PDF の書き出しと docswell への投稿はやめる。

- 各トークは `https://slides.y-kaz.com/<slug>/` で公開する。`<slug>` は `talks/` のディレクトリ名である
- 各トークの HTML に、タイトル・説明・OGP 画像 (1200×630)・Twitter カードのメタタグを入れる。OGP 画像はテーマが持つ OGP カードから生成する
- 話者なしで読む閲覧者のために、ノートを読むモードを用意する。PDF にだけ載せていた補足は、このモードが引き受ける
- 発表後は、トークをビルドした静的ファイル一式を `talks/<slug>/final/` にコミットして凍結する (ADR-0009 の凍結を、ビルド成果物に読み替える)。サイトは各トークの `final/` と一覧ページを組み立てて作る。フレームワークを変えても、公開済みのトークは変わらない
- 配信先は、hidoko のアプリと同じく Cloudflare Workers の静的アセット配信を第一候補にする。デプロイとドメインの設定は、話者の確認を取ってから行う

## 根拠

- 動きを持つ資料の価値は、閲覧者が動きを体験できて初めて届く。PDF に落とすと、作り込んだ部分がいちばん失われる (確信度: 高)
- 凍結をビルド成果物で行えば、フレームワークを自由に変えられる。過去のトークをすべて最新の API に追従させる必要がない。年 100 本では、この差が大きい (確信度: 高)
- 静的ファイルの配信なので、ホスティング先を後から変えても資料は変わらない (確信度: 高)
- 発見性の低下は、OGP を整えて SNS で共有することで補えると見ている (確信度: 低。実績がない)

## 見直しの条件

- SNS からの流入が docswell 時代より明らかに少ない状態が続いたとき
- イベント側から PDF の提出を求められることが多いとき。その場合は、状態を選んで PDF にする書き出し (スパイクで実証済み) を復活させる

## 影響

- ADR-0009 の「final/ に最終レンダリングを凍結する」は、凍結物をビルド成果物に変えて引き継ぐ。ADR-0009 自体は廃止しない
- 旧方式で発表した資料のうち、`final/index.html` を持つものは、そのままサイトに載せられる
- tools/stage の CLI に、build (凍結)・site (サイトの組み立て)・OGP 画像の生成を入れる
