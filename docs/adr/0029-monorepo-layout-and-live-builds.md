# ADR-0029: 発表資料の構造を packages / apps / parts に組み直し、凍結をやめて公開のたびに全トークをビルドする

- ステータス: 承認
- 日付: 2026-10-07
- スコープ: リポジトリ全体

## 文脈

ADR-0026〜0028 で、発表資料は `tools/stage` のフレームワークで書き、slides.y-kaz.com に公開し、発表後は `final/` にビルドを凍結することになった。数本を作ってみて、話者から次の声があった。

- `final/` の運用は旧方式のころから面倒だった。凍結はやめたい
- フレームワークを `tools/` に置くのが合っているのか気になる。ディレクトリ構造は大きく見直したい
- 使い回す素材を共通部品としてどう管理するかも、決めておきたい
- 過去資料は `YYYY_MM_DD_<ハッシュタグ>_<演題>` で命名していて (Google ドライブに 106 件)、この一覧性が好き
- 旧方式の資料はサイトに載せない。いつか新方式で作り直したい

あわせて、hokuchi リポジトリは GitHub で公開されていることが分かった。`public: false` はサイトに載せないだけで、`talks/` に置いたものは誰でも読める。

## 選択肢

構造について。

**A 案: `tools/stage` のまま、凍結だけをやめる。** 変更は小さい。フレームワークは「道具」より製品に近く、サイトや制作アプリのようなアプリも増えていくので、`tools/` に詰め込むと見通しが悪くなる。

**B 案: hidoko と同じく `packages/` と `apps/` に分け、bun のワークスペースにする。** フレームワークは `packages/stage`、サイトは `apps/slides`、制作アプリは `apps/studio` に置く。コンテンツ (`talks/`・`articles/`) は root に残す (ADR-0009 のコンテンツ主役は保つ)。

**C 案: フレームワークを hidoko に移す。** デザインシステムと同じ場所に置ける。トークとフレームワークを別リポジトリで直すことになり、作り込みの段階では遅い。

凍結について。

**D 案: 凍結を続ける。** 公開済みのトークは変わらない。`final/` のコミットと、ビルド成果物の蓄積が続く。

**E 案: 凍結をやめ、公開のたびに全トークを最新のフレームワークでビルドする。** フレームワークの改善が過去のトークにも届く。フレームワークを変えたときに、過去のトークの見た目が意図せず変わるおそれがある。

## 決定

B 案と E 案を採る。

```
talks/<YYYY_MM_DD_タグ_演題>/   公開する発表 (storyboard.md / talk.tsx / scenes/ / assets/)
parts/                          トークをまたいで使い回す中身 (自己紹介・会社紹介・写真)
packages/stage/                 フレームワーク (再生機・部品・テーマ・トーク単位の CLI)
apps/slides/                    slides.y-kaz.com (全トークのビルド・トップページ・配信)
apps/studio/                    ローカルの制作アプリ
archive/talks/                  旧方式の deck.yaml と写真 (作り直すときの素材。ビルドしない)
```

- ディレクトリ名は過去資料と同じ `YYYY_MM_DD_<タグ>_<演題>` にする。URL は日付とタグから作る (`/2026-09-29-devsgarden/`)。タグに英数字が無いときや、同じ日に同じタグが重なるときは、`talk.tsx` の `slug` で指定する
- 凍結をやめる。`apps/slides/build.mjs` が公開のたびに全トークをビルドする。そのとき全トークの全状態を撮り、前回の静止画と比べる。見た目が変わった状態があれば、前後の画像を並べて止める。意図した変化なら `--accept` で受け入れる
- 使い回しは 2 つに分ける。中身を持たない汎用の部品 (線・カード・数の変化) はフレームワークの kit に置く。中身を持つもの (自己紹介・会社紹介) は `parts/` に置く。凍結しないので、時期によって変わる中身 (自己紹介の肩書きなど) は日付つきの履歴で持ち、トークの日付の時点の内容を出す
- 社内向けの発表は、このリポジトリの外に置く。CLI はリポジトリ外のトークも扱える
- 旧方式のトークは `archive/talks/` に移し、凍結出力は外した。`tools/slides` は削除した (Git の履歴に残る)

## 根拠

- フレームワークとサイトと制作アプリを分けると、それぞれの責務が名前で分かる。hidoko と同じ形なので、話者にとっても読みやすい (確信度: 高)
- 全トークが同じリポジトリにあり、全状態の静止画を比べられるので、凍結しなくても意図しない変化は止められる。フレームワークを大きく変えるときは、Claude が全トークをまとめて追従させられる (確信度: 中。トークが 100 本を超えたときのビルド時間は未計測)
- 過去資料の命名を引き継ぐと、Google ドライブの 106 件を作り直すときに対応が取りやすい (確信度: 高)

## 見直しの条件

- 全トークのビルドが長くなり、公開の待ち時間が負担になったとき。差分のあるトークだけをビルドする仕組みを検討する
- 静止画の差分が頻繁に出て、確認が形骸化したとき
- 社内向けの発表を、公開の発表と同じ場所で扱いたい需要が強くなったとき (非公開のリポジトリを分けるなど)

## 影響

- ADR-0027 のうち「発表後に final/ へ凍結する」を置き換える。ADR-0009 のうち「発表済み資料を final/ に凍結する」も置き換える。コンテンツを root に置く方針は引き継ぐ
- CLI の `freeze` と `site` を廃止し、サイトの組み立ては `apps/slides/build.mjs` に移した
- 依存はルートの bun ワークスペース (hoisted) で管理する。`talks/` のシーンからも react や motion がそのまま解決できる
- crafting-presentation と CLAUDE.md を新しい構造に追従させる
