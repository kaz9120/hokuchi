# ADR-0036: studio は段階の画面を入口にし、AI は各段階で頼めることとして横に置く

- ステータス: 承認 (試作 v0: ホームと段階 1〜4)
- 日付: 2026-10-09
- スコープ: リポジトリ全体 / apps/studio

## 文脈

ADR-0035 で、studio を発信準備の入口にした。話者からは次の要望があった。

- note は過去に書いた記事も全部 studio で見られるようにしたい。過去の記事も改善したい
- この画面から新規作成したい。新規作成のときに最初に考えるべきことは決まっている。いきなりチャットで始めるのではなく、そこもシステム化したい
- 既存のスキルにとらわれず、全く新しく作る気持ちで進めてよい。大前提は slide:ology を踏襲する。note は、note の本と note 公式が紹介する書き方の記事を読み直す
- UI は shadcn/ui をそのまま使う。studio は管理画面なので、hidoko のデザインシステムには乗らない
- 枯れた分野 (CMS) ではあるが、AI と共作する環境として新しい形を模索する。情報設計も含めて、何度も試しながら整える

調査の記録は `apps/studio/docs/research/` にある。3 つの資料は、媒体が違っても同じことを言っていた。何を言うかがどう言うかより先、相手を名前のある 1 人として描いてから一言に絞る、量を出してから捨てる、構成ができるまで本文に入らない、最後に決めるのは人、の 5 つである。

## 選択肢

**A 案: チャットを入口にし、AI が問いを順に投げる。** 作りは小さい。何を決めたか・どこまで進んだかが会話に埋もれ、あとから見返しにくい。

**B 案: 段階の画面 (欄・カード・チェックリスト) を入口にし、AI は各段階で「頼めること」として横に置く。** 決めたことが欄に残り、進み具合が見える。AI は候補・講評・検査を出し、人が選んで欄に入れる。

**C 案: 全段階をフォームにし、AI を使わない。** 人の判断は守れるが、量を出す・抜けを指摘するという AI の強みを捨てる。

置き場について。このリポジトリは GitHub で公開されている。ネタ帳や未公開の企画は、置くと誰でも読める。リポジトリに置く、リポジトリの外に分ける、git の管理外にする、の 3 つを比べた。

関門について。関門を通るまで次の段階を開けない作りと、開けるが警告を出す作りを比べた。

## 決定

B 案を採る。置き場はリポジトリの外に分け、関門は開けるが警告を出す (話者の選択)。

- 発表と記事で、骨組みの揃った 10 段階 (種・相手・ゴール・一言★・発散と取捨・構成★・制作・見直し★・公開・振り返り) を持つ。欄の中身だけを媒体ごとに変える。★ は人が「これで決める」を押して通る関門で、通したあとに中身を変えると未決定に戻る
- 一言と相手は、決めたあと全段階の画面の上に出し続ける
- AI に頼めることは、段階ごとの単発の依頼にする (候補を出す・抜けを指摘する・反発を予測する・講評する)。ローカルの Claude Code を `claude -p` で 1 回呼び、候補を JSON で受け取る。候補は企画シートに残す。欄を書き換えるのは人で、候補の「欄に入れる」を押したときだけ入る
- 作品の企画シート (`works/<id>/brief.yaml`) とネタ帳 (`seeds/<id>.yaml`) は、リポジトリの外の置き場 (既定は `~/Hobby/hokuchi-private`、環境変数 `HOKUCHI_PRIVATE` で変えられる) に置く
- ホームに、進行中の作品・ネタ帳・公開済み (発表と note の記事) を並べる。公開済みの記事は note 風に描画して読める
- 新しい画面は shadcn/ui (Tailwind v4、neutral) で作る。発表資料の編集画面 (ADR-0030) は、いまの見た目のまま残す。全体の指定がぶつからないよう、画面ごとに片方の CSS だけを読む

試作 v0 で作ったのは、ホームと、作品の画面の段階 1〜4 まで。段階 5〜10 と、公開済みの記事の改稿は次の段で作る。

## 根拠

- 決めたことが欄に残るので、途中でやめても続きから再開でき、何が決まっていないかが見える (確信度: 高。ネタ → 記事 → 相手 → 一言 → 関門まで通して、企画シートに残ることを確かめた)
- 人が決め、AI は候補と講評を出すという分担は、3 つの資料の「最後に決めるのは人」に沿う (確信度: 高)。一言の講評を 1 回頼み、企画シートに沿った指摘が 15 秒ほどで返ることを確かめた
- 段階を一方通行にしないのは、slide:ology が検証から作り直しに戻る反復を描いているため (p.30-31) (確信度: 中)

## 見直しの条件

- 段階を行き来するうちに、10 段階が細かすぎる・粗すぎると分かったとき。情報設計は試しながら直す前提である
- 単発の依頼では足りず、段階の中でも会話が要ると分かったとき (右の欄にチャットを足す)
- 置き場をリポジトリの外に分けたことで、公開するときの移し替えが重いと分かったとき

## 影響

- `apps/studio` に Tailwind v4 と shadcn/ui の部品 (`ui/components/ui/`) を入れた。設定は `components.json` と `tsconfig.json`
- サーバに `store.mjs` (置き場)・`notes.mjs` (公開済みの記事)・`ai.mjs` (頼めること) を足した
- studio とサイトのポートは、環境変数 `HOKUCHI_STUDIO_PORT`・`HOKUCHI_SITE_PORT` で変えられる
- crafting-presentation と writing-note のスキルは、まだ studio の段階と結びついていない。段階 5 以降を作るときに、どう引き継ぐかを決める
