# ADR-0046: 記事も発表と同じ流れで studio で作る。原稿はリポジトリの外に置き、段落を単位に指摘と読みを回す

- ステータス: 承認
- 日付: 2026-10-19
- スコープ: apps/studio / tools/notes / .claude/skills/writing-note

## 文脈

`docs/vision.md` で、発表と記事を同じ流れ (ネタ → 芯を決める → 下書き → 読んでもらう → 磨く → 出す → 積み上げる) で作ると決めた。発表の側は、studio の作品の画面で企画から公開までを進められる (ADR-0040)。記事の側で studio にあるのは、企画 (段階 1〜4) と公開済み記事を読む画面だけだった。構成・執筆・削る・検査・公開は、writing-note skill と `tools/notes` の CLI と会話の中にあった。

原稿の往復は、`hokuchi-note serve` の別画面で選んだ文にコメントを付け、`feedback.md` に追記する形だった (ADR-0022)。発表の指摘のスレッド (`feedback.yaml`、ADR-0040) とは別の仕組みで、聴衆役の読み (ADR-0039) は記事に無かった。

原稿の置き場は `articles/note/drafts/` で、公開リポジトリの中にある。git では追跡していなかったが、誤って追跡すれば公開前の原稿が GitHub に出る。

話者と次の 3 つを決めた (2026-10-19)。

- 原稿はリポジトリの外に置く
- 指摘と聴衆役の感想は、段落を単位にする
- `serve` と `feedback.md` は studio に統合し、役目を終える

## 選択肢

**記事の作品の画面**

- A 案: 記事専用の画面を新しく設計する
- B 案: 発表のタブの骨組みを使い、記事の中身に置き換える。企画・構成 (発表の流れ)・原稿 (発表のコマ)・読み・公開

**原稿の置き場**

- A 案: `articles/note/drafts/` のまま、`.gitignore` に入れる
- B 案: `<HOKUCHI_PRIVATE>/notes/<slug>/` に置く。公開したら、今までどおり `sync` でアーカイブ (`articles/note/`) に取り込む

**指摘の単位**

- A 案: 見出しのまとまり
- B 案: 段落

## 決定

画面は B 案、置き場は B 案、単位は B 案を採る。

- 記事の作品の画面は、企画・構成・原稿・読み・公開のタブにする。発表と同じ骨組みで、言葉と中身を記事に合わせる
  - 構成: 見出しの並び・フック・密にする場所・段ごとの字数の予算 (writing-note の Phase 3)
  - 原稿: 段落ごとに本文を直す。段落の横に、lint の結果と、その段落への指摘を出す。左に見出しの目次を置く
  - 読み: 聴衆役に記事として読んでもらう。アンケートと段落への感想を返す。ペルソナは発表と共通 (`personas/`)
  - 公開: タイトルの案・タグ・見出し画像を決め、note に貼る形でコピーする。公開後は取り込み (`sync`) を Claude Code に頼む
- 原稿は `<HOKUCHI_PRIVATE>/notes/<slug>/` に置く。中身は `index.md` (frontmatter と本文)・`assets/`・`feedback.yaml` (指摘のスレッド)・`readers.yaml`・`reads/`。企画シートの `note` に slug を書いて紐づける
- 指摘のスレッドは、発表と同じ形 (`ball` と `closed`) にする。位置は、段落の番号と段落の書き出しの文字列の両方で持つ。本文を直して番号がずれても、書き出しの文字列で付け直す
- `hokuchi-note serve` と `feedback.md` は、studio の原稿タブで置き換えたあとに外す。`lint` と `paste` は CLI にも残し、studio からも呼ぶ
- writing-note skill は、studio の作品の画面を前提に書き直す。会話でしか進められなかった段階 (構成・執筆・削る・検査) は、studio の画面とファイルを介して往復する

## 根拠

- 発表と記事で骨組みを揃えると、話者は 1 つの使い方を覚えれば両方を進められる。片方で育てた仕組み (読み・指摘) が、もう片方にもそのまま効く (確信度: 高)
- 公開前の原稿を公開リポジトリの外に置けば、誤って公開する道を断てる。公開後のアーカイブは原本 (`source.json`) から作るので、原稿がリポジトリに無くても困らない (確信度: 高)
- 記事の読み手が引っかかるのは、文と段落の単位である。見出しのまとまりでは、どこへの指摘かがぼやける。`serve` も段落の番号で位置を表していた (確信度: 中)
- 段落の番号は本文を直すとずれる。書き出しの文字列を併せて持てば、ほとんどの場合に付け直せる。付け直せない指摘は、記事全体への指摘に寄せる (確信度: 中)

## 見直しの条件

- 段落の付け直しが外れることが多いとき。段落に安定した id を振る方式を考える
- 記事の構成の画面が、発表の流れの画面と違いすぎて骨組みを共有できないとき

## 影響

- ADR-0022 (`serve` のフィードバックループ) を、この ADR で置き換える
- `articles/note/drafts/` を使わなくなる。CLAUDE.md・`tools/notes/docs/design.md`・writing-note skill の置き場の記述を直す
- 段階に分けて作る。1 段目は、置き場の引っ越しと原稿タブ (段落の編集・lint・指摘)。2 段目は、構成・読み・公開
