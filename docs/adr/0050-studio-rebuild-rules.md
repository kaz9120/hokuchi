# ADR-0050: studio の作り直しで、値の正・名前・状態の見せ方の規則を決め直す

- ステータス: 承認
- 日付: 2026-10-20
- スコープ: apps/studio

## 文脈

ADR-0049 で、作品を 1 つの実体にした骨組みで studio を作り直すと決めた。作り直しの段 1〜6 で、ADR-0049 と `rebuild.md` には書いていない規則を、いくつか決め直した。どれも、skill と Claude Code が同じファイルを読み書きするときに効く。設計書 (`apps/studio/docs/design.md`) は現在の姿だけを描くので、なぜそう決めたかをここに残す。

## 選択肢

- A 案: 決め直したことを design.md にだけ書く。経緯が残らず、あとで戻すときに理由が分からない
- B 案: 決め直したことを 1 本の ADR にまとめ、design.md からリンクする

## 決定

B 案を採る。決め直したのは次の 8 つである。

1. 同じ意味の値の正を 1 つにする。タイトルは中身 (発表は talk.tsx、記事は原稿の front matter) が正で、中身が無ければ企画シート。企画シートの `title` には写す。伝えたいことは企画の段階 4、聴衆は企画の段階 2 が正。公開範囲は実物が正で、企画の「資料を公開しますか」は意図として並べ、食い違えば知らせる
2. 状態は、サーバの状態の表 1 か所で導き、画面では 1 語 (下書き・完成・完成（社内）・公開・改稿中) で出す。押せる操作も同じ表が決め、画面の「⋯」にはその操作だけを出す。データは ADR-0045 の 2 つの軸のまま
3. ごみ箱の名前は `<HOKUCHI_PRIVATE>/trash/<日時>-<種別>-<id か slug>/` の 1 通りにする (種別: `work`・`revision`・`notes`)
4. 読み手 (`readers.yaml`) は、プリセットの id のほか、企画の段階 2 で描いた人を `persona: brief:<名前>` の形で指定できる。その人の中身は企画シートから読む。readers.yaml の形は変えない。同じ名前のプリセットがあれば、そのプリセットが演じる
5. 記事の原稿の置き場の名前 (slug) は、話者に聞かない。企画のタイトルと伝えたいことから Claude に短い英語の名前を 1 つ付けてもらい、失敗したときはタイトルのかなをローマ字にした名前に落とす (話者の決定: 「個別に直すのは面倒なので、claude に良い感じにつけてもらいましょう」)。直したいときは「⋯」の「原稿の名前を変更」で変える (公開前の原稿だけ)
6. 書き込みは、どのファイルも「読んだ版や中身と違えば保存しない」(409) にそろえる。画面は 409 を受けたら読み直して知らせ、書いた文は欄に残す
7. Claude へ渡す依頼文は 2 行 (場所と件数、従う skill の Phase) にし、直し方と feedback.yaml の書き方は skill の側に書く。聴衆役の感想を話者が「目を通した」印は、feedback.yaml に書かずブラウザの手元にだけ持つ (ファイルの形と `ball`・`closed` の値を変えないため)
8. 画面の言葉は、「まだ」と「間違い」を分ける。決めていないもの・無いものは灰色で「未定」「未設定」、橙と赤は話者が決めた値と食い違ったときだけ。公開済み・改稿中の作品で何も書いていない企画シートは、企画シートの無い作品と同じに見せる

## 根拠

- 1・2: 同じ値の正が複数あると、Claude Code が片方だけを直したときに画面とファイルが食い違う。作りの棚卸し (`apps/studio/docs/research/2026-10-19-rebuild-architecture-audit.md`) で、状態の判定が 6 か所に散っていたのが、つぎはぎの原因の 1 つだった (確信度: 高)
- 3: ごみ箱の名前が 3 通りあり、手で戻すときに探しにくかった (確信度: 中)
- 4: 段階 2 で描いた聴衆と読み手が別物で、芯の聴衆と読みの聴衆役の数が合わなかった。readers.yaml の形を変えずにつなぐには、id で企画を指すのが変更がいちばん小さい (確信度: 中)
- 5: slug を聞く画面は、実装の都合を話者に説明していた。ローマ字だけだと漢字が落ちて読めない名前になり、話者が個別に直す手間になる (確信度: 中)
- 6・7: Claude Code と画面が同じファイルを直すので、どちらの書き込みも消えないことが前提になる。依頼文に作法を書くと、skill と画面の 2 か所を直すことになる (確信度: 高)
- 8: 使い心地の棚卸しで、書き始める前から赤い警告が出る画面が「間違い」に見えていた (確信度: 中)

## 見直しの条件

- Claude が付ける原稿の名前が、続けて話者の意図と外れるとき。名前の付け方を企画の欄から選べるようにする
- `brief:<名前>` の読み手を、skill (Claude Code) から直接読む必要が出たとき。readers.yaml に中身を書き出す形を考える
- 「目を通した」印を、別のブラウザや別の機械でも共有したくなったとき

## 影響

- `apps/studio/docs/design.md` の 2・3・4・6 章が、この規則で書かれている
- crafting-presentation・writing-note skill の、studio・依頼文・ごみ箱・readers.yaml・原稿の作り方の記述を、この規則に合わせた
