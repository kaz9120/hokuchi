# hokuchi の思想

- ステータス: 合意 (2026-10-19。話者が自分の言葉で書き直していく)
- 更新: 2026-10-19

hokuchi は、山本一将のブランディングプラットフォームです。考えを整理し、整え、磨き上げて、発表や記事として世に出す場所です。ブランドの中身 (何を約束し、どう見せるか) は `BRAND.md` が定義します。この文書は、それを支える場としての hokuchi が何を目指し、迷ったときに何を基準に判断するかをまとめたものです。

機能や画面を足すときは、まずこの文書に照らしてください。照らして判断できないときは、この文書の記述が足りていません。話者と相談して、この文書を更新します。

## 1. 何のためにあるか

話者の言葉では、次のとおりです (2026-10-19)。

> アウトプットプラットフォームというと、手段が先行してしまう印象すらあります。ブランディングプラットフォームなのです。私を形作る全てがここにあり、その質を高め、私自身の考えも整理し、整え、磨き上げることができる場所にしたいです。

> 思考を整理して、私一人ではできないレベルの量・質を作り上げるのがツールの役目だと思っています。

> かっこよくありたい。

発表や記事を「出す」ことは、目的ではなく結果です。目的は、山本一将の考えを磨き上げることにあります。磨いた考えが、発表や記事という形になります。出したものはここに積み上がり、次の考えの土台になります。

## 2. 目指す状態

次の 4 つを、どれも欠かさずに満たします。1 つを取るためにほかを捨てる設計はしません。

| 何が | どうなっている | 確かめ方 |
|---|---|---|
| 速さ | 思いついてから出すまでが短い。手を動かすのは、決めることと話すことだけになっている | ネタを書き留めてから公開するまでの日数。話者の手作業の回数 |
| 質 | 1 本ごとの質が、話者 1 人で作るより高い。芯がぶれず、読み手に届く | 聴衆役の読み (ADR-0039) で、芯が伝わったか。公開後の反応 |
| 蓄積 | 出したものがここに残り、次の 1 本に効く。過去の言葉・図・学びを引ける | 次の作品で、過去の作品から引いたものの数 |
| 体験 | 使っていて気持ちがいい。触るたびに、自分の考えが整っていく感覚がある | 話者が「使いづらい」と言わないこと。迷わずに次の操作が分かること |

これら 4 つの土台となるのが、かっこよさです。発表・記事・サイトのように外に出るものも、studio のように話者自身が使う道具も、手触りのあるものにします。`BRAND.md` 2.2 の「不便を愛する遊び心」と同じで、合理性の先にある体験の豊かさを大切にします。

## 3. 人とツールの役割

決めるのは話者で、量と質を引き上げるのはツール (Claude と studio) です。

- 話者が担うこと: 何を伝えるかを決める。自分の言葉で話す・書く。出すかどうかを決める
- ツールが担うこと: 考えを引き出し、整理して見せる。1 人では作れない量の下書きや図を作り、検査を回す。文脈を持たない読み手の目で読み直す。公開と蓄積の手間を引き受ける

ツールは、話者の代わりに考えません。候補や反論は出しますが、芯の 1 文は話者の言葉で決めます (memory「芯は素材より先に決める」、ADR-0024)。

## 4. 作品の流れ

発表も記事も、同じ流れで作ります。媒体の違いは、各段階の中身の違いとして扱います。

```
ネタ → 芯を決める → 下書き → 読んでもらう → 磨く → 出す → 積み上げる
```

| 段階 | すること | 発表 (いま) | 記事 (いま) |
|---|---|---|---|
| ネタ | 思いついたことを、なぜそう感じたかと一緒に書き留める | ネタ帳 | ネタ帳 |
| 芯を決める | 誰に何を届けるかを決め、伝えたいことを 1 文にする | 企画シート (段階 1〜4) | 企画シート (段階 1〜4) |
| 下書き | 芯から全体を組み、1 本の形にする | 絵コンテとシーン (流れ・コマ) | 構成と原稿 (リポジトリの外の `notes/<slug>/`)。studio の構成・原稿タブ (ADR-0046) |
| 読んでもらう | 文脈を持たない読み手に読んでもらい、意図が伝わっているかを確かめる | 聴衆役の読み (読み) | 聴衆役の読み (読み)。段落への感想 |
| 磨く | 指摘を 1 件ずつ往復して直す | 指摘のスレッド (`feedback.yaml`) | 段落への指摘のスレッド (`feedback.yaml`) と lint |
| 出す | 公開する。共有用の形 (テキスト・PDF など) も作る | サイト・単一 HTML・テキスト・PDF | 公開タブで note に貼る形をコピー。公開済みの記事は「改稿する」で直す (ADR-0047) |
| 積み上げる | 出したものを残し、次に引ける形にする | `talks/` と公開サイト | アーカイブ (`articles/note/`) |

いまは、発表の仕組みが先に整っています。記事は、下書きから磨くまでの工程が studio の外 (skill と CLI) にあります。次は、発表で培った「読んでもらう」「磨く」を記事にも当てはめます。

## 5. 迷ったときの決め方

1. 話者の考えを整え、磨くことに効くか。効かない機能は、便利でも作りません
2. 4 つ (速さ・質・蓄積・体験) のどれかを、ほかを損なわずに上げるか
3. 外に出るものと話者が触る画面の両方で、かっこよさを保てているか。造語や説明だらけの画面、平板な成果物は、かっこいいとは言えません
4. 発表と記事で、同じ流れに乗っているか。片方だけの仕組みを作るときは、もう片方にどう当てはめるかを先に考えます
5. 話者が決めることを、ツールが勝手に決めていないか

## 6. まだ決めていないこと

- 「積み上げる」の具体的な形。過去の作品の言葉・図・学びを、次の作品でどう引くか (検索・引用・部品の収穫など)
- 発表と記事以外の発信 (X の投稿・プロフィール・イベント運営など) を、ここで扱うか
- 記事の「下書き」の画面を studio でどう見せるか。発表のコマに当たるものを、段落にするか見出しの単位にするか
- 体験とかっこよさを、どう確かめるか。いまは話者の感想だけが頼りです
