# スライドスキーマ設計 — 意図を宣言し、配置を導出する

- 作成: 2026-07-04
- 参考文献: ナンシー・デュアルテ『slide:ology』BNN、2014年（以下ページ番号は同書）
- ステータス: 承認済み。書き手は Claude（スキル経由の対話で情報を集め、YAML を生成。人間は `idea` と `notes` をレビュー）と決定し、§7 の B+D 案で確定
- 決定の記録: 経緯は [ADR](../../../docs/adr/README.md) を参照。本書は常に現在の設計を描く

## 問いと結論

問い: Marp や Slidev のような Code to Slide ツールが図とレイアウトで表現力の限界に達するのはなぜか。そして slide:ology の原則を土台に、表現力とスライドとしての正しさを両立するスキーマをどう設計するか。

結論: Markdown という「文書メタファー」を捨て、書き手が **意図** (何を伝えたいか・要素同士がどう関係するか) を宣言し、レンダラが **配置** を導出する 3 層の宣言スキーマにする。表現力はダイアグラム 6 類型・グリッド配置・データ 3 レイヤー・段階的開示を第一級の語彙にすることで確保し、正しさは「スキーマ上そもそも書けない制約 (correct by construction)」と「書けるが警告される制約 (linter)」の 2 段構えで担保する。

## 1. なぜ既存ツールは限界に達するのか

「なぜ」を 3 回掘ります。

1. **なぜ図とレイアウトで表現力が尽きるのか。** Marp/Slidev のスライドは「Markdown の流し込み + CSS ハック」だから。図は画像貼り付けか Mermaid 外注、レイアウトは HTML/CSS への脱出になり、スライドの記述言語そのものには空間の語彙がない。
2. **なぜ語彙がないのか。** Markdown は文書 (ドキュメント) の記法であり、見出し・段落・箇条書きという「読む」ためのセマンティクスしか持たないから。デュアルテの分類 (p.26-27) で言えば、Markdown はスライドをドキュメント/テロップ側に引き寄せる記法であり、そのまま書くと「スライデュメント」を量産する。箇条書きが第一級市民である記法は、箇条書きスライドを第一級市民にする。
3. **なぜスライドには空間の語彙が要るのか。** スライドの意味の大半を配置が担うから。「オブジェクトのサイズや接近度で、ストーリーは変わる」(p.119)。同じ要素でも配置次第で「対等」「支配」「衰退」と読みが変わる (p.124)。配置を表現できない記法は、スライドの意味の半分を表現できない。

つまり課題の根本は「テーマ機能が弱い」ことではなく、**記述言語がスライドというメディアのセマンティクスを持っていない**ことです。CSS を足すのは対症療法で、語彙を足すのが根治になります。

## 2. 「スライドとしての正しさ」の定義

スキーマで守るべき「正しさ」を、slide:ology から 5 条件に絞って定義します。ここが検証可能になっていることが、このスキーマの存在意義です。

| # | 条件 | 出典 |
|---|------|------|
| C1 | グランス・メディアである — 3 秒で読み取れる。可視テキストは 50 語程度まで、75 語以上はもはや文書 | p.26-27, p.160, p.164 |
| C2 | 1 スライド 1 アイデア — 主役となるメッセージが 1 枚に 1 つ | p.109 (レッシグ), p.254 (カワサキ) |
| C3 | 一貫性 — 色・書体・アイコン様式・グリッドがデッキ全体で揃い、逸脱は意図的な例外に限る | p.135, p.120-122 |
| C4 | 配置が原則に従う — コントラスト/フロー/階層/統一感/関係性/余白の 6 原則。余白は削ってよいものではなく 1 つの要素 | p.112-127 |
| C5 | データは意味を語る — 「データスライドが伝えるべきは、データそのものではなく、データの意味です」 | p.84 |

## 3. 設計方針 — 何を宣言させ、何を導出するか

方針は 1 行に集約できます。**書き手はピクセルではなく意図を書く。見た目はテーマとレンダラが導出する。**

| 書き手が宣言するもの | スキーマ/レンダラが導出するもの |
|---|---|
| スライドのアイデア (1 文) | — (検証の基準になる) |
| 要素間の関係 (ダイアグラムの型・ノード・エッジ) | 図形の描画・線種・間隔 |
| グリッド上の占有領域と要素の階層 | 実座標・サイズ・余白 |
| データの意味 (intent と強調点) | 軸・グリッド線・配色・脱チャートジャンク |
| 開示の順序 (build) と場面のつながり | アニメーション効果の実体 |
| テーマトークンへの参照 | 実際の色値・書体・サイズ |

これは第 10 章のテンプレート論と同じ構造です。「テンプレートは言葉や画像を収めるための単なる骨組み」(p.226) であり、めったに変化しないもの (色・グリッド・書体) をテーマに固定し、頻繁に変化するもの (コンテンツ) だけをスライドに書かせます。

## 4. スキーマの 3 層構造

### 層 1: Foundation — テーマトークン (第 7・10 章)

デッキから参照する共有基盤。ここがスロット制になっていることが correct by construction の核です。

```yaml
theme:
  grid:
    pattern: col-4          # col-3 | col-4 | col-5 | fibonacci  (p.121)
    stage_margin: 1         # 上下 1 行を空ける「映画スクリーン」効果 (p.122)
  palette:                  # 色は名前付きスロットのみ。任意の色値は書けない
    core: ["#0B3D91", "#2E86AB", "#F2A104"]   # 3〜5 色 (p.156)
    neutral: ["#F5F5F2", "#8A8A85", "#2B2B28"]
    highlight: "#E4572E"    # 強調専用 1 色
    background: dark        # dark=フォーマル/大会場, light=配布・小会議室 (p.152)
  type:                     # 書体はスロットが 2 つしかない (p.163)
    display: { family: "Noto Sans JP", weight: 700 }
    body:    { family: "Noto Sans JP", weight: 400, min_size_pt: 24 }  # p.172-173
  iconography: isometric    # isometric | flat | hand-drawn — 混在不可 (p.188, p.192)
  space: 2d                 # 2d | 3d — 必ずどちらか一方 (p.140)。3d なら光源・消失点もここで固定 (p.140-143)
```

デフォルトテーマは hokuchi の `BRAND.md` §6 と hidoko デザインシステム (`hidoko/packages/ui/src/tokens.css`) から導出する。ember-400 (`#f47d3a`、ブランド指紋色) を highlight スロットに置くと、slide:ology のハイライトカラー (強調専用 1 色、p.156) と BRAND.md の「基準色はブランドを象徴する接点に使う」がそのまま一致する。core には補助色 (moon/moss/smoke)、neutral には ink 段階色を割り当て、書体は LINE Seed JP + Inter、ダーク標準。BRAND.md §6.5 の「冒頭スライドにキャッチコピー」「自己紹介スライドは毎回更新」は opener テンプレートの仕様に落とす。デザインシステムを複数リポジトリからどう共有するかは別途検討 (hokuchi のスコープ外)。

テーマは複数運用する (ADR-0010)。個人登壇は `themes/hokuchi.yaml`、MOSH としての登壇は `themes/mosh.yaml`。組織テーマのために theme は `brand` ブランド枠 (ロゴ・フッタ・背景アート・反転前景) と `type.webfonts` を持つ (theme スキーマ 0.2.0)。ブランド枠は舞台の外側のレイヤーとして描かれ、role とレイアウトの分担 (ADR-0008-6) に触れない。レンダラを変更したときの検証台は `examples/coverage/` — 全 role・全パターン・全要素・ブランド枠を 1 デッキで踏む。

### 層 2: Slide — 1 枚 = 1 アイデア (第 10・11 章)

```yaml
deck:
  title: "..."
  audience:                 # 聴衆プロファイル (p.34-37)。レンダリングされない設計メタデータ
    who: "..."
    action: "プレゼン後に取ってほしい行動"
  theme: ./theme.yaml

slides:
  - id: why-now             # 必須。再生成・差分レビューの安定キー
    role: content           # opener | title | transition | content | closer  (p.232 の「つなぎ/コンテンツ」)
    idea: "研修プログラムの開始が売上反転の起点だった"   # 必須。1 文。C2 の検証基準
    notes: |
      スライドから削ったテキストの行き先。話者ノート (p.243)
    layout: split-golden    # 名前付きパターン or グリッド直接指定 (後述)
    connect: push-left      # cut | push-left | push-up | ... — パノラマ接続 (p.210-212)
    elements: [...]
    build: [...]            # 段階的開示 (後述)
```

`idea` を必須にするのは、ZS アソシエイツの事例 (p.40-43) の教訓です。詰め込みは「メッセージが複数ある」ことの症状であり、1 文で言えないスライドは分割対象です。linter は「idea が書けない・elements が idea と無関係に多い」を検出の起点にします。

削ったテキストは消すのではなく `notes` に落とします。3 つの R (Reduce/Record/Repeat、p.240-241) の Reduce をスキーマ操作として実行できるようにする、つまり「本文→ノート」への移動を一級操作にするのが狙いです。

### 層 3: Element — 表現力の核

要素は 7 種。それぞれが slide:ology の章に対応します。

#### statement / bullets — テキスト (第 7 章)

```yaml
- kind: statement           # 1 文を大きく見せる。フォントサイズは階層から導出
  text: "76% が犬を選ぶ"
  emphasis: ["76%"]         # highlight スロットの色が当たる

- kind: bullets             # ネスト構造が存在しない = サブ項目が書けない (p.171)
  items: ["聴衆を犠牲にしない", "控えめに使う", "見出しのつもりで作成する"]
  reveal: one-by-one        # 1 項目ずつ表示、済んだ項目は dim (p.165)
```

#### image — 写真 (第 8 章)

```yaml
- kind: image
  src: assets/classroom.jpg # 省略可。無い場合は prompt がプレースホルダを生成する
  prompt: "夕方の教室で、窓からの自然光の中で笑う小学生。望遠、浅い被写界深度"
                            # 画像生成 AI 向けプロンプト。運用では人間が任意の生成 AI で
                            # 出力した画像を src に置いて差し替える。プロンプト自体が
                            # 「どんな画像であるべきか」の仕様として YAML に残る
  treatment: full-bleed     # full-bleed | framed | cutout  (p.43 フルブリード)
  subject: third-right      # 被写体を三分割交点に置く (p.181)。空いた側がテキスト領域になる
  gaze: toward-content      # 人物の視線はコンテンツ側へ (p.117)。逆向きなら lint 警告
```

#### diagram — ダイアグラム 6 類型 (第 3 章)

ここが Marp との最大の差分です。図を「絵」として持ち込むのではなく、**関係の型**として宣言します。デュアルテの分類体系 (p.64-77) をそのまま form の語彙にします。

```yaml
- kind: diagram
  form: flow.cycle          # 型の語彙は下表
  nodes:
    - { id: plan,  label: "計画" }
    - { id: do,    label: "実行" }
    - { id: check, label: "検証" }
  edges: [plan -> do, do -> check, check -> plan]
  emphasis: [check]         # 強調ノード。サイズ/色は階層原則から導出 (p.119)
  reveal: sequential        # 複雑な図は段階的に示す (p.78)
```

| form | 下位分類 | 表すもの |
|------|---------|---------|
| flow | linear / cycle / branch / converge / network | プロセス・手順 (p.66-67) |
| structure | matrix / tree / layer | 階層・並置 (p.68-69) |
| cluster | overlap / closure / enclosed / linked | まとまり・共有 (p.70-71) |
| radial | semi / core / coreless | 中心と広がり (p.72-73) |
| pictogram | process / cutaway / route / location / influence | 具体物の図解 (p.74-76) |

複合図 (「マーキテクチャー」p.78) は diagram の入れ子 (`nodes` の中に別の diagram を置く) で表現します。「これらのサンプルはけっして網羅的なものではありません」(p.73) とある通り、form は描画テンプレートの ID ではなく**レイアウト戦略の指定**であり、同じ form でもテーマ次第で見た目は変わります。

#### chart — データ (第 4 章)

チャートは「グラフ種類」ではなく **intent** (何を言いたいか) で宣言し、3 レイヤーモデル (背景/データ/強調、p.92-93) をスキーマの形にそのまま写します。

```yaml
- kind: chart
  intent: trend             # comparison | trend | distribution  (p.77)
  message: "3 月の研修開始が売上反転の起点"   # 必須 (C5)。message のない chart は書けない
  data: { source: sales.csv, x: month, y: revenue }
  emphasis:                 # 第 3 レイヤー。ここが「意味」を語る
    - { at: "2024-03", annotate: "研修プログラム開始", style: highlight }
  detail: appendix          # 完全版データは配布資料へ (p.84, p.86)
```

背景レイヤー (目盛・グリッド線) は書き手が触れません。無彩色・最小限 (p.92) をレンダラが保証し、3D・グラデーション・枠線などのチャートジャンク (p.94) はそもそも指定する場所がありません。intent が comparison で項目が少数なら円/棒の選択もレンダラが規則 (p.90-91) で決めます。

#### quote / raw

```yaml
- kind: quote
  text: "..."
  attribution: "..."

- kind: raw                 # 脱出口。SVG/HTML を直接埋め込む
  svg: ./custom-visual.svg
  waiver: "書籍の図版を忠実に再現するため"   # 理由必須。lint レポートに常に列挙される
```

`raw` は「一貫したデザインを 20 枚見せた後の意図的な 1 枚」(p.135) のための口です。禁止すると実務で破綻し、無制限だとスキーマが空洞化するので、「書けるが、理由を書かされ、レポートに常に現れる」という摩擦を付けます。

### レイアウト — グリッドと名前付きパターン (第 6 章)

配置は 2 段階で書けます。9 割は名前付きパターンで足り、残りをグリッド直接指定で書きます。どちらもグリッドセル単位であり、ピクセルは書けません。

```yaml
# 段階 1: 名前付きパターン (テンプレートの「コンテンツ」カテゴリ p.232 に相当)
layout: full-bleed-statement   # ほか: split-golden / triptych / diagram-stage / chart-stage / quote-stage ...

# 段階 2: グリッド直接指定
layout:
  areas:
    - { element: hero-img, cell: "1-3 / 1-4" }   # 列 / 行 の占有範囲
    - { element: headline, cell: "4 / 2-3" }
  whitespace_min: 0.3       # 面積の 3 割は空ける。既定値。下げると lint 警告 (p.126-127)
```

余白をパラメータとして明示しているのは、「余白は 1 つの要素」(p.126) を運用可能にするためです。詰め込みたい圧力は必ず発生するので、余白を「残ったスペース」ではなく「予約されたスペース」としてスキーマ側が先取りします。

### build と connect — 時間軸 (第 9 章)

アニメーションは自由なエフェクト指定ではなく、デュアルテの 5 つの役割 (p.204: 関係変化・演出・変化・連続性・強調) から導いた**意味語彙**だけを許します。

```yaml
build:
  - show: [problem]
  - show: [cause], dim: [problem]     # 済んだ要素はグレーに (p.165)
  - emphasize: [cause.root]           # 強調 (役割 5)
  - transform: { target: ball, to: flatten }   # 変化 (役割 3)
```

バウンス・スピンイン・ランダムワイプのような「機能があるから使う」動き (p.220 の 8 つの特徴) は語彙に存在しません。また `connect: push-left` の連鎖はパノラマ (p.210-212) を作りますが、push 接続されたスライド列ではヘッダ・フッタ要素が自動で外れます (つなぎ目に装飾が入らないように、p.212)。

## 5. 正しさの担保 — 2 段構え

### 書けない (correct by construction)

| 制約 | 実現方法 |
|------|---------|
| 色数超過・場当たりな色 | 色は palette スロット参照のみ。色値リテラルはスキーマ違反 |
| 3 書体目 | type スロットが display/body の 2 つしかない |
| 箇条書きのネスト | bullets.items は文字列の平坦な配列。ネスト構造が型として存在しない |
| チャートジャンク | 背景レイヤー・3D・装飾の指定フィールドがない |
| 意味のないデータ | chart.message が必須フィールド |
| ピクセルずれ・不揃い | 配置はグリッドセル単位のみ |
| 2D/3D の混在 | theme.space でデッキ単位に固定 (p.140) |

### 書けるが警告される (linter)

| ルール | 内容 | 出典 |
|--------|------|------|
| slideument | 可視テキスト合計が閾値超過。日本語は 100 字で警告、150 字でエラー (50 語/75 語相当。換算係数は要検証) | p.26, p.164 |
| one-idea | 主役級要素 (diagram/chart/statement) が 1 枚に 2 つ以上 | p.109, p.256 |
| bullet-count | bullets.items が 5 項目超 | p.171 |
| pie-rules | 円グラフ 9 項目以上・合計が 100% でない (12 時起点・時計回りはレンダラが保証) | p.91 |
| axis-lock | 連続する chart スライド間で軸位置が揃わないデータ範囲 | p.90 |
| contrast | 背景とのコントラスト不足、およびグレースケール変換で判別不能な系列 (色覚対応) | p.152, p.156 |
| whitespace | whitespace_min を既定値未満に下げた | p.126-127 |
| gaze | 人物画像の視線がコンテンツと逆向き (subject/gaze 宣言から判定) | p.117 |
| logo-bumper | opener/closer 以外のスライドにロゴ要素 | p.137 |
| raw-budget | raw 要素がデッキの 1 割超 — 語彙が現実に負けているサイン | p.135 |
| deck-size | 内容スライドが 10 枚超で情報表示 (エラーではない。10/20/30 は文脈依存のため) | p.254 |

linter を「エラーで止める」のではなく警告中心にしているのは、slide:ology 自体がルールの意図的な違反を認めている (p.135) ためです。ただし違反はすべてレポートに残り、沈黙のうちに常態化しない設計にします。

## 6. サンプル — 1 枚のスライド

第 4 章の「Sales Drivers」事例 (p.88) をこのスキーマで書くと次のようになります。

```yaml
- id: training-impact
  role: content
  idea: "3 月の研修開始が売上反転の起点だった"
  layout: chart-stage
  elements:
    - kind: statement
      text: "研修が売上を反転させた"
    - kind: chart
      intent: trend
      message: "3 月の研修開始と売上の底が一致する"
      data: { source: sales-2024.csv, x: month, y: revenue }
      emphasis:
        - { at: "2024-03", annotate: "販売研修 開始", style: highlight }
      detail: appendix
  build:
    - show: [chart]                       # まず全体の推移
    - emphasize: [chart.emphasis.0]       # 次に「意味」へ視線誘導
  notes: |
    この時期に他の組織改革は行われていない。売上の急上昇と
    研修開始を結びつけるのがこのスライドの狙い。
```

書き手が書いたのは「意味」だけで、色・グリッド線・フォントサイズ・アニメーション効果は一切書いていない点に注目してください。

## 7. 選択肢の比較と決定

取りうるアーキテクチャは 4 つありました。

**A 案 — Markdown 拡張 (Marp 路線の強化)。** front-matter とディレクティブで意図情報を注釈する。既存資産と書き味は最良。しかし本文が Markdown フローである限り、レイアウトと図は「本文の外の注釈」になり、注釈と本文の二重管理が発生する。根本原因 (§1) に触れない対症療法。

**B 案 — YAML 宣言スキーマ (本書の設計)。** 構造化データなので JSON Schema による検証・lint・LLM 生成との相性が良い。弱点は手書きの書き味。人間が YAML でスライドを量産するのは Markdown より苦痛。

**C 案 — コンポーネント DSL (Slidev/JSX 路線の徹底)。** 表現力の上限は最も高い。しかし自由度が高すぎて「正しさ」を静的に保証しにくく、規律がスキーマではなく書き手のスキルに依存する。今回の課題設定 (正しさの担保) と正面衝突する。

**D 案 — B のスキーマ + 既存ツールへのコンパイル。** スキーマは B で定義し、レンダラを自作せず HTML/SVG (または Slidev コンポーネント) へコンパイルする。B と排他ではなく実装戦略の選択。

**決定: B + D。** 書き手は Claude (スキルが人間への対話で聴衆・メッセージを深掘りし、YAML を生成。人間は `idea` と `notes` をレビュー) と確定したため、B 案の弱点である「手書きの書き味」は問題にならず、検証可能性の価値が最大化する。A 案に寄せるべき前提 (人間が手書きで量産する) は成立しない。最初の実装は HTML/SVG への直接レンダリングで始め、既存ツールへの依存には抽象化レイヤーを挟む。

## 8. 反証・撤退ライン・未決事項

**自分が間違っているとしたら何が起きるか。** 「意図を書けば配置は導出できる」という中心仮説が崩れるケース、つまり導出されたレイアウトが実用に耐えず、結局 raw や手動調整だらけになるケースです。そこで撤退ラインを先に決めます。実デッキを 3 本このスキーマで書き、(1) raw 要素が全要素の 1 割を超える、または (2) グリッド直接指定が名前付きパターンの利用を上回るなら、語彙の粒度設計が現実に負けています。form とパターンの語彙を増やすのではなく、導出モデル自体を見直します。

**10 分後・10 か月後の視点。** 10 分後の自分は「まず 1 枚レンダリングして見たい」はずで、それがこの設計の正しい次の一歩です (机上で語彙を増やすのではなく)。10 か月後の自分にとって価値が残るのは、レンダラの実装ではなくスキーマと lint ルールの定義です。スキーマを仕様 (JSON Schema) として独立させ、レンダラは差し替え可能にしておきます。

**意図的に先送りした問題。** 再生成と手編集の共存 — Claude が生成した YAML を人間が編集した後、対話で再生成すると手編集が失われうる。マージ戦略の設計は運用で実態を見てから行う (2026-07-04 決定)。ただし将来のマージに備え、スライド `id` の必須化 (安定キー) だけは最初のスキーマから入れておく。

**未決事項。** 次の点が残っています。

1. 日本語の文字数閾値 (100/150 字) は英語 50/75 語からの粗い換算で、実測での調整が必要
2. スピーカーノート駆動 (notes が主、スライドが従) の執筆フローをスキーマがどこまで支援するか — 第 11 章の「スライド依存からの脱却」をツールに込めるかは思想の選択
3. 配布資料 (appendix/handout) の出力仕様 — `detail: appendix` を導入した以上、スライドと配布資料の分離 (p.84) は仕様の一部。SPEC.md で扱う
4. grid-direct 上での diagram / chart / bullets — 現状 grid-direct のセルに置けるのは image / statement / quote / raw のみ。必要になった実デッキが現れた時点で対応する
5. image の treatment: cutout の本実装 (現状は contain 表示のみ)、gaze の静的検査

**決定済み (2026-07-04)。** skill は既存の presentation-roadmap スキルを置き換える新規作成とし、旧スキルとの互換は考慮しない。

## 9. レビューのフィードバックループ — serve と annotations (ADR-0011)

shot が作る PNG は「Claude が自分の目で確認する」ためのもの。人間のレビューには `hokuchi serve <outdir>` を使う。serve は出力を配信しながら agentation (React 製の注釈オーバーレイ) を配信時にのみ注入し、ブラウザ上で要素をクリックして付けたメモを `POST /__annotations` で受けて `<outdir>/annotations.md` に追記する。人間は注釈を送信して「アノテーションを見て」と言うだけで、Claude はセレクタ・位置つきの構造化フィードバックを読める。ディスク上の HTML は書き換えない (プレゼン本番と同一物を保つ)。agentation への依存はバンドルエントリ 1 ファイルに隔離されており、置き換え可能 (ADR-0011 撤退ライン)。
